# ADR-0011. Граница ядра и языкового модуля

- Статус: Принято
- Дата: 2026-10-24
- Связано: бриф §8 принцип 10; NFR-MAINT-04; 03 §4

## Контекст
VHDL, задачи на верификацию или другой язык должны добавляться новым модулем и профилем тулчейна без правок ядра. При этом бриф запрещает оверинжиниринг: проектировать «под все языки» заранее не нужно.

## Решение
- Всё SV-специфичное — в `judge/languages/systemverilog/`: precheck и проверка интерфейса (pyslang), нормализация AST, этапы Verilator/Yosys/SBY, разбор диагностик, протокол `apx_tb_pkg`.
- Ядро (`judge/core`, весь `backend`) оперирует только: `language` и `kind` задачи, `stage.type`, `stage_status`, `failure_kind`, `metrics_schema` + JSON, диагностиками в общем формате `{severity, code, file, line, col, message}`, артефактами по `kind`.
- Языковой модуль регистрируется в `judge.core.registry` под ключом `systemverilog` и отдаёт фабрику этапов и функцию хэша. Интерфейсы выделены по потребностям SV и будут пересмотрены при появлении второго языка.
- Фронтенд выбирает язык Monaco и расширение файла по `language` из API; вкладки результатов отображаются по `stage_type`, а не по языку.
- Правило import-linter в CI: `apparatica.*` и `judge.core.*` не импортируют `judge.languages.*` (кроме `judge.core.registry` через entry points).

## Последствия
- Новый язык = новый модуль + новый образ тулчейна + задачи с `language: <new>`; схема БД и API не меняются.
- Немного косвенности (реестр) уже в Ф0.

## Альтернативы
- Обобщённый «многоязычный» фреймворк этапов — оверинжиниринг до появления второго языка.
- SV-логика прямо в ядре — быстрее в Ф0, но дорогая переделка позже.
