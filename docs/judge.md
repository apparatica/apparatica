# Судья: ядро пайплайна

Как устроено ядро судьи `judge.core`: этапы, исполнители, события, лимиты, вердикт. Требования и целевое поведение — [specs/07](../specs/07-judge-pipeline.md); граница с языковыми модулями — [ADR-0011](adr/0011-language-module-boundary.md). Один и тот же код исполняет проверку в CLI `judge`, в CI и в воркере.

## Части

| Модуль | Что делает |
|---|---|
| `judge.core.stage` | протокол `Stage`, `StageContext`, `StagePlan`, `ExecResult`, `StageOutcome`, `StageResult` и общие модели: диагностика, тест-кейс, сводка этапа |
| `judge.core.pipeline` | `run_pipeline`: этапы `pipelines.practice.<kind>` по порядку, ранняя остановка, отмена |
| `judge.core.executor` | `LocalDockerExecutor` (контейнер образа тулчейна) и `HostExecutor` (подпроцессы на хосте); лимиты времени и вывода, отмена |
| `judge.core.events` | события пайплайна и приёмники: `ConsoleSink`, `JsonlSink`, `FanoutSink` |
| `judge.core.limits` | лимиты песочницы и этапов: класс ресурсов из `config/resource-classes.yaml`, переопределения из `problem.yaml` |
| `judge.core.verdict` | `aggregate`: итоговый статус отправки по результатам этапов (specs/04 §3.3) |
| `judge.core.registry` | языковые модули по ключу `language` через entry points |

Ядро не импортирует `judge.languages` (контракт import-linter): языковой модуль регистрируется в `pyproject.toml` судьи в группе entry points `apparatica.judge.languages` и отдаёт `LanguageModule` — имя и плагины этапов по типу. Модуль `systemverilog` зарегистрирован; его этапы появятся в T0.7a (precheck), T0.8 (lint) и T0.9 (sim).

## Этап

Этап — класс с атрибутами `stage_type` (значение `type` в `stages.<key>`), `config_model` (Pydantic-модель остальных полей `stages.<key>`), `metrics_schema` и двумя методами:

1. `plan(ctx) → StagePlan` — что выполнить: команды, входные файлы, какие файлы забрать после, таймаут и лимит вывода (обычно из `ctx.limits`), фильтр строк вывода.
2. `interpret(ctx, runs) → StageOutcome | StagePlan` — решение по результатам прогонов: статус, `failure_kind`, вид лимита, метрики, сводка, файлы для следующих этапов (`outputs`). Вернуть ещё один `StagePlan` — попросить следующий прогон (так `sim` перезапустит бинарник с окном трассы); всего не больше 4 прогонов на этап.

`StageContext` содержит конфиг этапа, задачу, каталог пакета, вид отправки, сид, код решения, лимиты и завершённые этапы с их `outputs`. Файлы между этапами передаются только через `outputs` → `inputs` следующего плана: каждый этап работает в чистом каталоге.

Фильтр строк (`StagePlan.line_filter`) получает каждую строку вывода и возвращает текст для консоли (или `None`, чтобы скрыть строку) и, если нужно, обновление прогресса теста — так языковой модуль разбирает строки `@@apx`, а ядро о них не знает.

## Пайплайн

`run_pipeline(job, language, executor, sink, resource_classes, cancel)`:

- До запуска проверяет, что у языка есть плагин для каждого `type`, и валидирует конфиги этапов; ошибка — `PipelineConfigError` (ошибка задачи, а не решения).
- Для каждого этапа пишет `stage_start`, выполняет планы, пишет `stage_end` с `StageResult`, в конце — `done`.
- После `failed` или `error` следующие этапы получают `skipped` с `skip_reason = previous_failed`. Отмена (`cancel`) прерывает текущую команду: этап получает `cancelled`, остальные — `skipped` с `skip_reason = cancelled`.
- Сбой исполнителя (`ExecutorError`: нет Docker, контейнер пропал) — этап `error` с кодом `EXECUTOR_FAILED`; исключение в плагине — `error` с кодом `STAGE_CRASHED`; бесконечные повторные прогоны — `STAGE_RUNS_EXCEEDED`. Текст ошибки идёт в лог этапа (канал `sys`).
- Превышение лимита вывода дополнительно даёт событие `truncated`.

Вердикт пайплайн не считает: это делает тот, кто владеет итоговым статусом, — CLI или ингестор — функцией `judge.core.verdict.aggregate`. Порядок: отмена, сбой платформы, первый `failed` по порядку этапов (`failure_kind` → статус), предупреждения, `accepted`. В `detail` — первый упавший этап и тест с тактом, вид лимита, этапы с предупреждениями, коды сбоев.

## Исполнители

Оба исполнителя выполняют команды плана по порядку до первого ненулевого кода выхода и соблюдают общие для плана правила:

- **Таймаут** `timeout_s` — на весь план, а не на команду; по истечении команда убивается, `timed_out`.
- **Лимит вывода** `output_limit` — байты строк обоих каналов; при превышении команда убивается, строки сверх лимита не передаются, `output_limited`.
- **Отмена** — проверяется каждые 50 мс; команда убивается, `cancelled`.
- **Файлы**: `inputs` записываются в свежий каталог этапа; из `collect` читаются существующие файлы не больше `collect_limit` байт, более крупные попадают в `oversized` и не читаются. Пути — только относительные внутри каталога этапа.

`LocalDockerExecutor(image, sandbox_limits)` — один контейнер на отправку с флагами specs/07 §5.1 (`sandbox_flags`), память, CPU и число процессов — из класса ресурсов. Каталог этапа — `/work/<stage_key>`; входные файлы загружаются tar-потоком через `docker exec` (`docker cp` не пишет в tmpfs), выходные читаются через `head -c` с ограничением. Команды идут через `docker exec -t … apx-run`: TTY даёт построчный вывод, `apx-run` помечает строки stderr. Убить клиент `docker exec` недостаточно, поэтому при таймауте, лимите, отмене и после каждого плана выполняется `kill -KILL -1` от пользователя песочницы — фоновый процесс этапа не доживает до следующего (S6). PID 1 контейнера пока `sleep infinity`; собственный `apx-init` из образа появится в T1.2a.

`HostExecutor` — подпроцессы во временном каталоге на хосте (`judge --no-docker`, тесты ядра). Изоляции нет; stdout и stderr читаются раздельно, на POSIX при убийстве завершается вся группа процессов.

## События

События — те же, что в стриме отправки воркера (specs/07 §4.1), без поля `attempt`: `stage_start`, `log` (`ch`: `out`, `err`, `sys`), `test`, `truncated`, `stage_end`, `done`. `ConsoleSink` печатает их для человека, `JsonlSink` пишет по событию в строке (`events.jsonl`), `FanoutSink` раздаёт нескольким приёмникам. Приёмник Valkey Stream — в воркере (Ф1).

## Лимиты

`config/resource-classes.yaml` задаёт для каждого класса ресурсов (`light`, `heavy`; NFR-LIM) CPU, память, число процессов, лимит вывода, размер FST, таймауты этапов по типу, таймаут по умолчанию и верхнюю границу таймаута. `limits` в `problem.yaml` переопределяют память, вывод, FST и таймауты по ключу этапа; таймаут выше границы класса — ошибка. `sandbox_limits` даёт лимиты контейнера, `stage_limits` — лимиты этапа (`ctx.limits`).

## Тесты

- `judge/tests/test_core_*.py` — пайплайн с фейковыми этапами (команды — однострочники Python через `HostExecutor`), исполнитель на хосте, вердикт, лимиты, реестр, события. Фейковые этапы — `judge/tests/core_helpers.py`.
- `toolchain/tests/test_executor.py` — `LocalDockerExecutor` против образа тулчейна: каналы, файлы, таймаут, лимит вывода, отмена, отсутствие выживших процессов. Запускается `just toolchain-test`.
