# S6. PTY, отмена и права под gVisor

- Дата: 2026-10-25
- Вопрос ([spikes-and-risks.md](../../specs/plan/spikes-and-risks.md)): `exec` с PTY — построчный вывод; лимит вывода; уничтожение процессов между этапами (`kill -KILL -1` от непривилегированного пользователя); `kill` контейнера во время компиляции; время старта контейнера; прототип `apx-sandboxd` и сравнение с rootless Docker + `runsc`.
- Критерий успеха: строки приходят ≤ 200 мс; отмена ≤ 1 с; нет зомби и выживших процессов; выбран способ управления контейнерами.
- Итог: **критерий выполнен** — при одном изменении: PID 1 контейнера должен быть собственный «жнец» `apx-init`, а не `sleep infinity` и не `docker run --init`. Способ управления — `apx-sandboxd` над обычным Docker (ADR-0003 подтверждён); rootless Docker с `runsc` не даёт лимитов ресурсов.
- Стенд: ветка `spike/s6-pty-cancel`, каталог `spikes/s6-pty-cancel/` (в основную ветку не переносится).

## Условия

Тот же VPS, что в [S2](s2.md): AEZA, Debian 13, 4 vCPU, Docker 29.9, gVisor `release-20261019.0` (`systrap`). Контейнеры с флагами specs/07 §5.1, образ тулчейна `2026.10.1`, обе среды — `runc` и `runsc`. Цифры ниже — для `runsc`, если не сказано иное; для `runc` они того же порядка (`results/`).

## Результаты

| Проверка | Результат |
|---|---|
| Строки бинарника Verilator через `docker exec -t` (+ `apx-run`) | приходят по мере печати: интервал 0,08 с, как в тестбенче |
| То же без TTY | все строки разом в конце (stdout буферизуется) — PTY необходим |
| Задержка доставки строки (`apx-run` под `exec -t`) | p50 0,8 мс, максимум 2,5 мс |
| Строки stderr через `apx-run` под `exec -t` | помечены `0x1E` |
| Лимит вывода: 1 МБ потока `yes` | набирается за 0,24 с |
| Процесс после того, как убит клиент `docker exec` | **продолжает работать** в контейнере |
| `sh -c 'kill -KILL -1'` от пользователя песочницы | 50–80 мс, выживших процессов нет |
| Зомби после `kill -1`, PID 1 = `sleep infinity` | **5 зомби остаются** (никто не забирает осиротевших) |
| То же, `docker run --init` (tini + `sleep infinity`) | зомби нет, но `kill -1` убивает `sleep` — **контейнер завершается** |
| То же, PID 1 = `apx-init` (прототип, 15 строк) | зомби нет, выживших нет, контейнер работает |
| `docker kill` посреди компиляции рантайма Verilator | 0,17 с (runc 0,08 с); клиент `exec` завершается одновременно |
| Старт контейнера / `docker exec true` / `docker rm -f` | 0,17 с / 59 мс / 0,08 с |
| `docker stop` контейнера с `apx-init` | 84 мс |

`apx-sandboxd` (прототип на asyncio, unix-сокет, JSON):

| Проверка | Результат |
|---|---|
| Полный цикл `create → put → exec (сборка, симуляция) → kill → destroy` | работает под `runc` и `runsc` |
| Поток вывода через демон | построчный, интервал 0,08 с |
| Накладные расходы `exec` | 47 мс через демон против 43 мс напрямую |
| `cwd` вне `/work`, `argv` строкой, чужой контейнер, флаги в имени рантайма, неизвестная операция | отвергнуты |
| `argv: ["--privileged"]` | исполняется как имя команды (код 127), а не как флаг Docker |

Rootless Docker 29.9 + `runsc`: без аргументов — `systemd error: Permission denied`; с `--rootless` — `Rootless mode not supported with "create"`; с `--ignore-cgroups` — запускается, но без лимитов памяти и CPU. Тестовый пользователь и пакеты удалены после проверки.

## Выводы

1. **PTY нужен и работает под gVisor**: с `exec -t` строки приходят за миллисекунды, без TTY Verilator выдаёт всё в конце. `apx-run` сохраняет построчность и помечает stderr.
2. **Убить клиент `docker exec` недостаточно** — процесс остаётся в контейнере. Лимит вывода и вытеснение Run выполняются изнутри: `kill -KILL -1` от пользователя песочницы (этап остаётся у контейнера) или `docker kill` (отмена отправки целиком).
3. **В образе нет `/bin/kill`** (нет `procps`): убивать через встроенную команду оболочки — `sh -c 'kill -KILL -1'`.
4. **PID 1 — собственный жнец `apx-init`.** `sleep infinity` оставляет зомби (они занимают `--pids-limit` до конца отправки), `docker run --init` выходит вместе со своим единственным ребёнком, которого убивает `kill -1`. `apx-init` — PID 1 под тем же UID: ядро не доставляет ему `kill -1`, а он забирает всех осиротевших и не завершается.
5. **Отмена быстрая**: `docker kill` останавливает контейнер посреди компиляции за 0,1–0,2 с, вместе со всем деревом процессов.
6. **Загрузка файлов** — потоком tar через `docker exec -i … tar -x` (`docker cp` не пишет в tmpfs; см. S2).
7. **Способ управления — `apx-sandboxd`** над обычным Docker: небольшой демон с фиксированными флагами и операциями добавляет ~5 мс к `exec`. Rootless Docker с `runsc` отпадает: без cgroup нет лимитов памяти и CPU, а они обязательны (specs/07 §5.1).

## Рекомендации

- T1.2a: `apx-init` в образе тулчейна как команда контейнера (новый профиль); `apx-sandboxd` с операциями прототипа на Docker Engine API (unix-сокет Docker), сокет демона — с группой пользователя оркестратора, а не `docker`; имена и идентификаторы контейнеров генерирует демон.
- T1.2b/T1.6: лимит вывода и вытеснение — `kill -KILL -1` изнутри, отмена отправки — `docker kill`; проверять, что клиент `exec` завершился.
- Набор `tests/security/` (T1.8): случаи «фоновый процесс между этапами», «зомби до `--pids-limit`», «поток вывода» из этого стенда.

## Что меняется в документах

- ADR-0003: S6 подтверждён, статус «Принято»; PID 1 — `apx-init`; rootless Docker отклонён по итогам S6.
- specs/07 §5.1–5.3: PID 1 `apx-init`, `kill` через оболочку, загрузка файлов через tar-поток, убийство клиента `exec` не останавливает процесс.
