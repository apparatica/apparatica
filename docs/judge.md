# Судья: ядро пайплайна

Как устроено ядро судьи `judge.core`: этапы, исполнители, события, лимиты, вердикт. Требования и целевое поведение — [specs/07](../specs/07-judge-pipeline.md); граница с языковыми модулями — [ADR-0011](adr/0011-language-module-boundary.md). Один и тот же код исполняет проверку в CLI `judge`, в CI и в воркере.

## Части

| Модуль | Что делает |
|---|---|
| `judge.core.stage` | протокол `Stage`, `StageContext`, `StagePlan`, `ExecResult`, `StageOutcome`, `StageResult` и общие модели: диагностика, тест-кейс, сводка этапа |
| `judge.core.pipeline` | `run_pipeline`: этапы `pipelines.practice.<kind>` по порядку, ранняя остановка, отмена |
| `judge.core.executor` | `LocalDockerExecutor` (контейнер образа тулчейна) и `HostExecutor` (подпроцессы на хосте); лимиты времени и вывода, отмена |
| `judge.core.events` | события пайплайна и приёмники: `ConsoleSink`, `JsonlSink`, `FanoutSink` |
| `judge.core.limits` | лимиты песочницы и этапов: класс ресурсов из `config/resource-classes.yaml`, переопределения из `problem.yaml` |
| `judge.core.verdict` | `aggregate`: итоговый статус отправки по результатам этапов (specs/04 §3.3) |
| `judge.core.registry` | языковые модули по ключу `language` через entry points |

Ядро не импортирует `judge.languages` (контракт import-linter): языковой модуль регистрируется в `pyproject.toml` судьи в группе entry points `apparatica.judge.languages` и отдаёт `LanguageModule` — имя и плагины этапов по типу. Модуль `systemverilog` зарегистрирован, в нём этапы `precheck`, `lint` и `sim` (ниже).

## Этап

Этап — класс с атрибутами `stage_type` (значение `type` в `stages.<key>`), `config_model` (Pydantic-модель остальных полей `stages.<key>`), `metrics_schema` и двумя методами:

1. `plan(ctx) → StagePlan` — что выполнить: команды, входные файлы, какие файлы забрать после, таймаут и лимит вывода (обычно из `ctx.limits`), фильтр строк вывода.
2. `interpret(ctx, runs) → StageOutcome | StagePlan` — решение по результатам прогонов: статус, `failure_kind`, вид лимита, метрики, сводка, файлы для следующих этапов (`outputs`). Вернуть ещё один `StagePlan` — попросить следующий прогон (так `sim` перезапустит бинарник с окном трассы); всего не больше 4 прогонов на этап. Первый план этапа получает чистый каталог, повторные выполняются в том же каталоге и видят оставленные файлы (`reuse_dir`), например собранный симулятор.

`StageContext` содержит конфиг этапа, задачу, каталог пакета, вид отправки, сид, код решения, лимиты и завершённые этапы с их `outputs`. Файлы между этапами передаются только через `outputs` → `inputs` следующего плана: каждый этап работает в чистом каталоге.

Фильтр строк (`StagePlan.line_filter`) получает каждую строку вывода и возвращает текст для консоли (или `None`, чтобы скрыть строку) и, если нужно, обновление прогресса теста — так языковой модуль разбирает строки `@@apx`, а ядро о них не знает.

## Пайплайн

`run_pipeline(job, language, executor, sink, resource_classes, cancel)`:

- До запуска проверяет, что у языка есть плагин для каждого `type`, и валидирует конфиги этапов; ошибка — `PipelineConfigError` (ошибка задачи, а не решения).
- Для каждого этапа пишет `stage_start`, выполняет планы, пишет `stage_end` с `StageResult`, в конце — `done`.
- После `failed` или `error` следующие этапы получают `skipped` с `skip_reason = previous_failed`. Отмена (`cancel`) прерывает текущую команду: этап получает `cancelled`, остальные — `skipped` с `skip_reason = cancelled`.
- Сбой исполнителя (`ExecutorError`: нет Docker, контейнер пропал) — этап `error` с кодом `EXECUTOR_FAILED`; исключение в плагине — `error` с кодом `STAGE_CRASHED`; бесконечные повторные прогоны — `STAGE_RUNS_EXCEEDED`. Текст ошибки идёт в лог этапа (канал `sys`).
- Превышение лимита вывода дополнительно даёт событие `truncated`.
- `StageOutcome.outputs` передаются следующим этапам, `StageOutcome.artifacts` — файлы для пользователя (FST, отчёты): их получает колбэк `on_artifact(stage_key, name, data)` — CLI сохраняет их на диск, воркер загрузит в хранилище.

Вердикт пайплайн не считает: это делает тот, кто владеет итоговым статусом, — CLI или ингестор — функцией `judge.core.verdict.aggregate`. Порядок: отмена, сбой платформы, первый `failed` по порядку этапов (`failure_kind` → статус), предупреждения, `accepted`. В `detail` — первый упавший этап и тест с тактом, вид лимита, этапы с предупреждениями, коды сбоев.

## Исполнители

Оба исполнителя выполняют команды плана по порядку до первого ненулевого кода выхода и соблюдают общие для плана правила:

- **Таймаут** `timeout_s` — на весь план, а не на команду; по истечении команда убивается, `timed_out`.
- **Лимит вывода** `output_limit` — байты строк обоих каналов; при превышении команда убивается, строки сверх лимита не передаются, `output_limited`.
- **Отмена** — проверяется каждые 50 мс; команда убивается, `cancelled`.
- **Файлы**: `inputs` записываются в каталог этапа — свежий или, с `reuse_dir`, оставшийся от прошлого прогона этого этапа; из `collect` читаются существующие файлы не больше `collect_limit` байт, более крупные попадают в `oversized` и не читаются. Пути — только относительные внутри каталога этапа.

`LocalDockerExecutor(image, sandbox_limits)` — один контейнер на отправку с флагами specs/07 §5.1 (`sandbox_flags`), память, CPU и число процессов — из класса ресурсов. Каталог этапа — `/work/<stage_key>`; входные файлы загружаются tar-потоком через `docker exec` (`docker cp` не пишет в tmpfs), выходные читаются через `head -c` с ограничением. Команды идут через `docker exec -t … apx-run`: TTY даёт построчный вывод, `apx-run` помечает строки stderr. Убить клиент `docker exec` недостаточно, поэтому при таймауте, лимите, отмене и после каждого плана выполняется `kill -KILL -1` от пользователя песочницы — фоновый процесс этапа не доживает до следующего (S6). PID 1 контейнера пока `sleep infinity`; собственный `apx-init` из образа появится в T1.2a.

`HostExecutor` — подпроцессы во временном каталоге на хосте (`judge --no-docker`, тесты ядра). Изоляции нет; stdout и stderr читаются раздельно, на POSIX при убийстве завершается вся группа процессов.

## SystemVerilog: `precheck`

Этап `precheck` (`judge/languages/systemverilog/stages/precheck.py`, specs/07 §2.1) — первый в пайплайне. Код решения разбирает pyslang, а это код атакующего, поэтому сама проверка выполняется в песочнице:

1. План загружает в каталог этапа `solution.sv` (код пользователя как есть), `job.json` (модуль, параметры и порты из `problem.yaml`, лимиты из `PrecheckConfig`) и раннер `sandbox/precheck_runner.py` и запускает `python3 -I precheck_runner.py job.json solution.sv`. Раннер — один файл на стандартной библиотеке и pyslang из образа; меняется вместе с судьёй, профиль образа для этого не нужен.
2. Раннер по шагам: лимиты размера; лексер ищет директивы препроцессора (до разбора — ни одна директива не выполняется); разбор; канонический текст без комментариев (символы комментариев заменены пробелами, строки и колонки сохраняются); белый список видов узлов slang и правила поверх него; элаборация с лимитами шагов; объём состояния; интерфейс при значениях параметров по умолчанию из `problem.yaml`. Первый шаг с замечаниями останавливает проверку. Результат — `result.json` и `canonical.sv`.
3. Судья читает оба файла как недоверенные (строгая схема `RunnerResult`, лимит размера) и решает: замечания → `failed` (`forbidden`, `compile` или `limit` с видом `size`/`memory`) с диагностиками по-русски и стабильными кодами; без замечаний → `passed`, канонический текст уходит следующим этапам как `solution.sv`, метрики `precheck/v1`: `code_hash` (sha256 канонического текста, судья считает его сам), `ast_hash` и `normalization_version` (ниже), `module`, `ports_ok`, `state_bits`. Таймаут, лимит вывода и гибель от нехватки памяти — `limit`; падение раннера без результата — `error` с `TOOL_FAILED`, неверный `result.json` — `OUTPUT_INVALID`.

Белый список видов узлов и таблица пояснений для частых запрещённых конструкций — в раннере; имена видов проверяются при загрузке модуля (`SyntaxKind.__members__[name]`), поэтому опечатка или вид, исчезнувший в новой версии slang, — ошибка импорта, а не пропущенное правило. Лимиты — поля `PrecheckConfig` (`stages.<key>` в `problem.yaml`), по умолчанию из NFR-LIM-01.

**Нормализованный AST-хэш** (specs/07 §6) считает раннер для прошедшего решения (`normalize_tokens`, `ast_hash`): поток токенов без trivia, имена модуля, портов и параметров из `problem.yaml` сохраняются, прочие идентификаторы — `_1`, `_2`, … по первому появлению, литералы с основанием свёрнуты в hex. Формат — `n<версия>:<sha256>`, версия — `NORMALIZATION_VERSION` раннера; любая правка нормализации увеличивает её, хэши разных версий не сравниваются. Хэш нужен только для группировки одинаковых решений в рейтинге и подсказки модератору; ключ кэшей — `code_hash`. Что хэш игнорирует и что различает, фиксирует `judge/tests/test_ast_hash.py`.

## SystemVerilog: `lint`

Этап `lint` (`judge/languages/systemverilog/stages/lint.py`, specs/07 §2.2) берёт канонический `solution.sv` из `outputs` предыдущего этапа (`stages/common.py`: без `precheck` перед ним этап не запускается) и выполняет `verilator --lint-only` с SARIF-выводом в файл. `LintConfig.flags` — только опции предупреждений `-W…` (по умолчанию `-Wall -Wno-UNUSEDPARAM`), `-Wno-DECLFILENAME` и `-Wno-fatal` этап добавляет сам. Консольный вывод Verilator идёт в лог этапа как есть, а решение принимается по SARIF: ошибки → `failed`/`compile`, предупреждения → `warning` (или `failed` при `warnings_fail`), иначе `passed`. В `summary.diagnostics` — до 200 диагностик (первая строка сообщения, правило, позиция в `solution.sv`), метрики `lint/v1` считают все. Verilator 5.052 пишет невалидный SARIF при пустом списке правил; `parse_sarif` вставляет пропущенную запятую ровно в этом месте и разбирает снова (фикстуры `judge/tests/data/lint/` — настоящий вывод Verilator из образа).

## SystemVerilog: `sim`

Этап `sim` (`judge/languages/systemverilog/stages/sim.py`, specs/07 §2.3) собирает и запускает тестбенч задачи. `SimConfig`: `testbench` (id из `testbenches`), `groups`, `max_cycles`, `design` (`<stage>.<output>` — симулировать выход другого этапа, например нетлист, вместо решения), `trace` и окно `trace_before`/`trace_after` (по умолчанию 64/16 тактов), `build_jobs` (по умолчанию 1).

1. План: исходники тестбенча из пакета (`pkg/…`, только внутри каталога пакета), канонический `solution.sv` (или `design.v`), две команды — `apx-verilate` с `apx_tb_pkg` первым и запуск `obj_dir/V<tb.top>` с сидом отправки, группами, новым nonce, лимитом тактов и случайной инициализацией.
2. Фильтр строк: строки прогресса `@@apx` с nonce этого прогона становятся событиями `test`; скрытые тесты в них анонимны (`hidden-N`); служебная строка `$finish` из `apx_tb_pkg` скрыта.
3. Итог по файлу результатов (`tbproto.parse_result`): упавший тест → `wrong`; `suite_abort` по `max_cycles` → `limit`/`cycles`; ошибка тестбенча → `error`/`TB_ERROR`; нет итога (симуляция упала) → `wrong`; нарушение протокола → `error`/`OUTPUT_INVALID`; сборка не прошла → `compile`; таймаут, вывод, память (код 137) → `limit`. `summary.tests` — открытые тесты с расхождениями и подсказками, `summary.hidden_tests` — счётчики скрытых, метрики `sim/v1`.
4. Если упал открытый тест, `interpret` возвращает второй план: тот же бинарник, тот же сид, `+apx_trace_from/to` вокруг первого расхождения, в том же каталоге этапа. Совпало первое расхождение — FST уходит в `artifacts` (`trace.fst`, не больше `fst_mb`), иначе `metrics.trace = nondeterministic` и окно не показывается.

## События

События — те же, что в стриме отправки воркера (specs/07 §4.1), без поля `attempt`: `stage_start`, `log` (`ch`: `out`, `err`, `sys`), `test`, `truncated`, `stage_end`, `done`. `ConsoleSink` печатает их для человека, `JsonlSink` пишет по событию в строке (`events.jsonl`), `FanoutSink` раздаёт нескольким приёмникам. Приёмник Valkey Stream — в воркере (Ф1).

## Лимиты

`config/resource-classes.yaml` задаёт для каждого класса ресурсов (`light`, `heavy`; NFR-LIM) CPU, память, число процессов, лимит вывода, размер FST, таймауты этапов по типу, таймаут по умолчанию и верхнюю границу таймаута. `limits` в `problem.yaml` переопределяют память, вывод, FST и таймауты по ключу этапа; таймаут выше границы класса — ошибка. `sandbox_limits` даёт лимиты контейнера, `stage_limits` — лимиты этапа (`ctx.limits`).

## Тесты

- `judge/tests/test_core_*.py` — пайплайн с фейковыми этапами (команды — однострочники Python через `HostExecutor`), исполнитель на хосте, вердикт, лимиты, реестр, события. Фейковые этапы — `judge/tests/core_helpers.py`.
- `judge/tests/test_precheck_runner.py` — раннер в процессе (pyslang — dev-зависимость судьи той же версии, что в образе): корпус легальных решений и более 60 запрещённых и вредоносных случаев из S7, сообщения, позиции, интерфейс, лимиты. `judge/tests/test_precheck_stage.py` — план и разбор результата, включая недоверенный вывод.
- `toolchain/tests/test_precheck.py` — этап в образе через `LocalDockerExecutor`; канонический текст собирается Verilator.
- `judge/tests/test_lint_stage.py` — план и разбор SARIF lint; `toolchain/tests/test_lint.py` — пайплайн `precheck → lint` в образе через `run_pipeline`.
- `judge/tests/test_sim_stage.py` — план, разбор результатов, окно трассы, анонимность скрытых тестов; `toolchain/tests/test_sim.py` — пайплайн `precheck → lint → sim` в образе на пакете-фикстуре `judge/tests/data/packages/counter` (принятое решение, падение открытого теста с FST, падение скрытого).
- `toolchain/tests/test_executor.py` — `LocalDockerExecutor` против образа тулчейна: каналы, файлы, таймаут, лимит вывода, отмена, отсутствие выживших процессов. Запускается `just toolchain-test`.
