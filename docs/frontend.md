# Фронтенд

Next.js-приложение в `web/`: как оно устроено, откуда берутся цвета, шрифты и строки, как переключается тема, какие есть компоненты и как они тестируются. Экраны и состояния — [specs/08](../specs/08-screens.md), дизайн — `brief/apparatica-handoff/`.

## Стек

Next.js 16 (App Router), React 19, TypeScript 6 (`strict`), Tailwind CSS 4, next-intl 4, TanStack Query 5, иконки `lucide-react`. Базовые контролы — по образцу shadcn/ui на Radix UI (пакет `radix-ui`), палитра команд — `cmdk`, уведомления — `sonner`, варианты классов — `class-variance-authority`; `cn()` — в `src/lib/utils.ts`. Истории компонентов — Storybook 10 (`@storybook/nextjs-vite`). Редактор — Monaco (`monaco-editor` через `@monaco-editor/react`), панели страницы задачи — `react-resizable-panels`.

```sh
pnpm -C web dev          # http://localhost:3000
pnpm -C web build        # just build-js
pnpm -C web test         # just test-js: Vitest
pnpm -C web typecheck    # just typecheck-js: типы маршрутов Next.js и tsc
pnpm -C web storybook    # just storybook: http://localhost:6006
```

## Токены и тема Tailwind

- **`src/styles/tokens.css`** — копия `brief/apparatica-handoff/design/tokens.css`. Значения меняются только вместе с дизайном.
- **`src/app/globals.css`** переносит `tailwind.theme.ts` из пакета передачи в `@theme` Tailwind 4: цвета (`bg-sf`, `text-mu`, `border-bc`, `bg-acs text-ac` …), шрифты, радиусы, шкала типографики, тени `shadow-window` и `shadow-pop`.
- **Палитра Tailwind по умолчанию удалена** (`--color-*: initial`). Утилиты есть только у токенов, поэтому цвет не из `tokens.css` в классах не сработает.
- **Заголовки — `text-title-1` и `text-title-2`.** В теме передачи они называются `h1` и `h2`, но `text-h1` … `text-h4` уже заняты цветами тепловой карты. Остальные размеры — как в передаче: `text-display`, `text-statement`, `text-body`, `text-caption`, `text-label`, `text-code`, `text-metric`.
- **Имена shadcn/ui** (`bg-primary`, `text-muted-foreground`, `border-input`, `ring` …) сопоставлены токенам по `components.md`. Это те же цвета под другими именами, своих значений у них нет.
- **Отступы** — шкала Tailwind по умолчанию (шаг 4 px). Она совпадает со шкалой передачи.
- **`cn()` знает шкалу типографики.** Без этого `tailwind-merge` принял бы `text-caption` за цвет и в `cn("text-caption text-mu")` выбросил бы размер.
- **`--shim`** — блик скелетона. Его нет в `tokens.css`: значение взято из исходников макетов (`source/*.dc.html`) и задано в `globals.css` для обеих тем, как и анимация `animate-shim`.
- **Контур фокуса** задаёт `tokens.css` (`:focus-visible`, 2 px `--ac` со смещением 2 px). Это правило вне слоёв Tailwind и перебивает утилиты, поэтому изменить его у отдельного элемента можно только утилитой с `!` (`outline-none!`, `focus-visible:-outline-offset-2!`).

Тёмная тема — те же переменные под `data-theme="dark"` на `<html>`, поэтому варианты `dark:` не нужны.

## Шрифты

IBM Plex Sans и IBM Plex Mono, начертания 400, 500 и 600, из пакетов `@fontsource/*`. Файлы собираются в приложение, сеть при сборке не нужна. Подмножества (кириллица, латиница и другие) подключены через `unicode-range`, поэтому браузер загружает только нужные. Лицензия — OFL-1.1 (ADR-0012).

## Тема: светлая, тёмная, системная

По умолчанию тема системная. Явный выбор хранится в cookie `ap_theme` (`light`, `dark`, `system`; год, весь сайт).

- **Явный выбор** сервер читает из cookie и рендерит `<html data-theme>` сразу. Страница не мигает и без JavaScript.
- **Системная тема.** Сервер её не знает, поэтому `<html>` приходит без атрибута. Встроенный в `<head>` скрипт (`THEME_SCRIPT`) ставит атрибут по `prefers-color-scheme` до первой отрисовки и следит за сменой темы в ОС. CSP пропускает его по хэшу текста ([security.md](security.md#csp-сайта)).
- **Выбор** — в меню гостя («Гость» в шапке) или пользователя и в палитре команд (specs/08 §2). Оба меняют тему через общий контекст `ThemeProvider` (`src/components/shell/theme.tsx`).

Layout читает cookie, поэтому страницы рендерятся на каждый запрос (динамически).

## Оболочка

Шапка 40 px: знак и «Apparatica», «Быстрый поиск» с подсказкой Ctrl K (на телефоне — только значок без рамки), справа — чип «Гость» с меню (тема, «Документы») или аватар и ник вошедшего пользователя (макет Dashboard; на телефоне — только аватар). Левая рейка разделов шириной 48 px. На ширине меньше 640 px вместо неё нижняя навигация, высота целей нажатия от 44 px. Разделы перечислены в `src/components/shell/nav.ts`: «Задачи» и «Рейтинг» (общий рейтинг); «Дашборд» появится вместе со своей страницей (specs/08 §6). Вошедшему внизу рейки — свой профиль (макет Profile), на телефоне «Профиль» — последний раздел нижней навигации; у гостя профиля нет. Гостю рядом с чипом — кнопка «Войти»: она ведёт на `/login?next=<текущий путь>` (`loginHref`, `src/lib/session.ts`); на страницах входа её нет.

**Меню пользователя** (`user-menu.tsx`): имя и почта, «Профиль», «Настройки», тема, «Документы», «Выйти». В палитре команд вошедшему есть «Мой профиль». Cookie сессии `httpOnly`, но сервер сайта её видит: корневой layout передаёт оболочке `signedIn`, если cookie `ap_session` есть, а оболочка кладёт его в контекст `SessionProvider` (`src/features/account/session.tsx`). `useAccount()` отдаёт пользователя из `GET /me` (`useMe`): `undefined`, пока он грузится, — на месте чипа скелетон, а не «Гость»; `null` без cookie или на `401` (сессия кончилась) — показывается «Гость». `useGuest()` — точно гость; по нему страница задачи предлагает войти и выбирает тексты о том, где хранятся код и отправки. Выход перезагружает страницу (`afterLogout.reload()` в `src/features/account/api.ts`): в памяти не остаётся ничего от пользователя — кэша запросов, его отправок и статусов, сохранения черновика на сервер. Вход тоже заканчивается загрузкой страницы, поэтому, чей это браузер, решается один раз при загрузке ([данные вошедшего](#каталог)).

**Телефон** (FR-MOB-01, макеты MobCatalog и MobTask) — окно уже 640 px, граница `sm` Tailwind. То, что на телефоне только выглядит иначе, задают классы `max-sm:` и `sm:`. Где рендерятся другие компоненты (карточки каталога вместо таблицы, страница задачи без редактора), решает `usePhone()` (`src/lib/viewport.tsx`): после гидратации — `matchMedia("(max-width: 639.98px)")` и его изменения, а сервер ширины не знает и рендерит по догадке корневого layout — телефон, если `userAgent()` из `next/server` называет устройство `mobile`. Узкое окно компьютера сервер поэтому рендерит широким, и после гидратации страница перестраивается. Шапка телефона: путь заменяет заголовок страницы — «Задачи» рядом со знаком (без «Apparatica») или «‹» назад к разделу и название задачи (без знака). Уведомления на телефоне поднимаются над нижней навигацией.

**Баннер гостя** (FR-GST-02, лист Guest, `guest-banner.tsx`) — полоса над шапкой: «Вы решаете как гость. Черновики хранятся только в этом браузере, а решения не попадут в рейтинг.» и крестик. Закрытый баннер помнит cookie `ap_guest_banner=closed` (год, `src/lib/guest-banner.ts`): корневой layout читает её и не рисует баннер, страница не прыгает. Кнопка «Войти» ведёт на страницу входа с возвратом на текущую страницу. Вошедшему (есть cookie сессии) баннер не рисуется, на страницах входа — тоже.

**Баннер удаления** (FR-USR-05, без макета; `DeletionBanner` в `src/features/account/deletion.tsx`) — полоса под шапкой на всех страницах, пока аккаунт ждёт удаления (`Me.delete_at`): «Аккаунт будет удалён 11 ноября. Профиль уже скрыт. До этой даты удаление можно отменить.» и кнопка «Отменить удаление» (`POST /me/restore`). Цвета — как у полосы потери сети (`--wn` на `--wns`); закрыть её нельзя.

**Путь в шапке и строка состояния** — параллельные маршруты (слоты) корневого layout: `src/app/@breadcrumbs` и `src/app/@statusbar`. Страница каталога пишет «Задачи», страница задачи — «Задачи / ‹название›» и строку состояния под всем окном (specs/08 §2). Пока сервер готовит задачу, на их месте скелетон и «Загружаем задачу…» (`loading.tsx` слотов). Слот без страницы для нового адреса после перехода внутри сайта оставляет содержимое прошлого, поэтому у каждого маршрута есть страница в обоих слотах (пустая, если показывать нечего); `default.tsx` — для 404.

**Полоса сети** (`network-banner.tsx`) — под шапкой, пока сервер не отвечает ([ошибки и уведомления](#ошибки-и-уведомления)).

**Палитра команд** (`command-palette.tsx`) открывается по Ctrl+K (⌘K на Mac) или кнопкой «Быстрый поиск», закрывается по Esc или тому же сочетанию. Группа «Задачи» — до 8 задач из `GET /problems?q=` (поиск в названии и тегах), пока строка не пуста, справа — компактный `DifficultyBadge` уровня из `GET /config`; группа «Действия» — «Перейти к задачам» и выбор темы, фильтруется по вводу. Стрелки выбирают пункт, Enter выполняет.

## Каталог

`/problems` (`src/features/catalog/`, макеты `Catalog` и «Ничего не найдено» из `PageErrors`): заголовок, сводка прогресса по уровням, поиск и фильтры, таблица, страницы.

**Адрес — источник состояния** (FR-CAT-02). Поиск `q`, уровни `difficulty`, теги `tag`, статусы `status` (`solved`, `attempted`, `not_started`; параметры повторяются для нескольких значений), сортировка `sort` и страница `page` живут в адресе (`query.ts`). Неизвестные значения отбрасываются, значения по умолчанию в адрес не пишутся. Страницу рендерит сервер: `page.tsx` разбирает адрес и читает API (`load.ts`: `GET /config`, `GET /tags`, `GET /problems`). Контролы меняют адрес через `router.replace` в переходе (`useTransition`): контролы сразу показывают новое состояние (`useOptimistic`), а строки старого запроса бледнеют, пока сервер готовит новые. Любое изменение фильтров возвращает на первую страницу. Поиск уходит в адрес через 300 мс после последнего нажатия. Страницы — ссылки, они добавляют запись в историю браузера.

**Контролы.** Сложность, теги и статус — меню с флажками, меню не закрывается между выбором; на кнопке — число выбранных. Сортировки — по номеру (в обе стороны), по сложности (сначала простые или сложные), по проценту принятых (больше или меньше). Выбранные фильтры видны под панелью снимаемыми чипами (`TagChip removable`) с кнопкой «Сбросить фильтры»; она сбрасывает и поиск, а сортировку оставляет.

**Таблица** (FR-CAT-01): статус, номер и название, уровень (`DifficultyBadge`), теги (`TagChip` с подписью из `GET /tags`), процент принятых (`acceptance` из API, округлён до целого; «—», пока Submit с вердиктом нет). Вся строка — ссылка на задачу. Размер страницы — `catalog.per_page` из `GET /config`. Без совпадений — «Ничего не найдено» с текстом запроса и кнопкой сброса; пустой каталог без фильтров — «Задач пока нет».

**На телефоне** (макет MobCatalog) заголовок страницы — в шапке, сводки прогресса нет. Под поиском — строка кнопок, которая прокручивается вбок: «Все N» (все задачи каталога, `progress` API), кнопка на каждый уровень (можно включить несколько), меню «Теги» и «Статус». Ниже — «Всего N задач» и сортировка без слова «Сортировка». Чипы выбранных уровней не дублируются — уровни видны по кнопкам. Вместо таблицы — карточки (`problem-list.tsx`): номер, название, уровень, «N% принято» (без процента, пока нет данных), теги с многоточием, справа значок и статус. Вся карточка — ссылка на задачу.

**Статусы вошедшего** (FR-CAT-03) приходят с сервера. Страница каталога читает cookie сессии и передаёт API только её (`sessionApi` в `src/lib/api/server.ts`): API отдаёт статусы задач, решённые по уровням в `progress` и фильтрует по статусу сам (`loadCatalog(query, session)`, `CatalogData.own`). Сервер сайта рисует их сразу, без скелетонов. Отметки гостя этого браузера вошедшему не показываются, а после выхода возвращаются: перенос гостевых решений — Ф4 (T4.5). Если сессия кончилась (`401` или ответ без статусов), каталог читается как гостевой.

**Статусы гостя** (FR-CAT-03) берутся из локальной истории браузера (`src/features/guest/history.ts`), поэтому сервер их не знает. Сервер и первая отрисовка показывают на месте статусов и чисел сводки скелетоны, после гидратации их заменяет история. Фильтр по статусу работает в браузере: с ним сервер берёт все задачи, подходящие под остальные фильтры (`per_page=100`, при необходимости несколько страниц), а браузер отбирает их по статусу и делит на страницы. До гидратации на месте строк — скелетоны. Сводка «N из M»: M — задачи уровня из `progress` API, N — решённые задачи этого уровня из истории.

**Локальная история гостя.** `localStorage`, ключ `ap_history`: `{"v": 1, "problems": {"<slug>": {"status": "solved" | "attempted", "difficulty": "<уровень>"}}}`. Её пишет `useSubmission`, когда проверка заканчивается (в том числе восстановленная при открытии страницы): принятый Submit (`accepted`, `accepted_with_warnings`) — «решено», любая другая завершённая проверка — «пробовал»; решённая задача решённой и остаётся. Уровень хранится, чтобы сводка считала решённые по уровням без запроса всех задач. `useHistory()` читает историю через `useSyncExternalStore`: изменения в этой и в других вкладках (событие `storage`) сразу видны каталогу; на сервере и во время гидратации — `null`. Испорченная или недоступная история считается пустой. История переживает удаление гостевых отправок на сервере (14 дней).

**Отправки гостя** (FR-GST-03, `src/features/guest/submissions.ts`). `localStorage`, ключ `ap_submissions`: `{"v": 1, "items": [{id, problem, version, kind, status, verdict_detail, created_at, gone?}]}`, новые первыми, не больше 500 (старые забываются). `useSubmission` пишет туда показанную отправку — созданную, восстановленную и перечитанную после `finalized` — со статусом её живой проверки (`queued`, `running`, итог). При открытии страницы задачи список сервера (`GET /submissions?problem=…&limit=100`) дополняет историю и обновляет статусы; более старый ответ не возвращает завершённую отправку в `queued`. Если на сервере все отправки задачи уместились в одну страницу, завершённая отправка, которой там нет, помечается `gone`: сервер удалил её по сроку хранения (или cookie гостя сменилась). Незавершённую так не помечают — её могли создать после запроса. Отправка, на которую сервер ответил `404`, тоже становится `gone`. Общий код хранилищ — `local-store.ts`: значение парсится один раз на изменение строки, вкладки узнают об изменениях из события `storage`.

**Данные вошедшего.** История и отправки в `localStorage` принадлежат гостю этого браузера. Пока пользователь вошёл, хранилища `local-store.ts` держат свои значения только в памяти страницы (`setStoreOwner("user")`): тот же код пишет туда список сервера и живые проверки, но `ap_history` и `ap_submissions` гостя не меняются. Владельца ставит `SessionProvider` до первого чтения хранилищ — по cookie сессии, а когда `GET /me` отвечает `401`, возвращает гостя. Список вошедшего — его отправки на сервере с любого устройства, без срока хранения, поэтому `gone` у него не бывает.

**Данные на сервере.** Сервер Next.js ходит в API по `API_URL` (в стенде `http://api:8000`, без неё — `http://localhost:8000`), минуя Caddy ([api.md](api.md#клиент-во-фронтенде)). Ошибка API роняет страницу: её место занимает карточка сбоя ([ошибки](#ошибки-и-уведомления)).

## Вход

`/login` (FR-AUTH-01, макет Login, `src/features/account/login-page.tsx`, `login-card.tsx`) рендерит сервер: кнопки входа — провайдеры из `GET /config` (`auth_providers`, [api.md](api.md#пользователи-и-вход-ф2-контракт)) в их порядке. Слева — что такое платформа и пример принятой проверки; пример показывает только то, что проверяется сейчас (линт и симуляция), синтез, формал и рейтинг добавятся со своими фазами. Уже 1024 px остаётся только карточка входа. Отклонения от макета — specs/08 §4.

- **Провайдер** (`kind: oauth`) — ссылка на `/api/v1/auth/<key>/login?next=…`: вход — переход браузера, а не запрос. Если вход не удался, API возвращает на `/login?error=<причина>`, и карточка объясняет причину (`access_denied`, `invalid_state`, `provider_error`, `rate_limited`, остальное — «Не удалось войти»).
- **Почта** (`kind: email`) — поле адреса и «Получить ссылку для входа» (`POST /auth/email/request`). Адрес проверяется до запроса; после `202` на месте формы — «Проверьте почту» с адресом, «Отправить ещё раз» и «Другой адрес». `429` — сколько ждать (из `retry_after_s`), `428 CAPTCHA_REQUIRED` (флаг `captcha`) — диалог капчи, после него ссылка запрашивается с решением.
- Без провайдеров — «Вход сейчас недоступен». Ниже — «Продолжить как гость» и строка согласия со ссылками на `/legal/terms` и `/legal/privacy` (FR-AUTH-06, [ниже](#документы)).

**`next`** — куда вернуться после входа. Страница берёт его из адреса, только если это путь сайта (`sitePath`, `src/lib/session.ts`: то же правило, что у API), и передаёт провайдеру и в запрос ссылки. Ссылки «Войти» в шапке, баннере гостя и настройках строит `loginHref(path)`; страницы входа и `/` в `next` не попадают.

**Ссылка из письма** — `/login/email/verify#token=…` (`verify-login.tsx`, рендерит браузер). Страница читает токен из фрагмента, сразу убирает его из адреса и истории и один раз (в том числе в strict mode) отправляет в `POST /auth/email/verify`. Успех — полная загрузка `next` из ответа (не путь сайта — `/`): оболочка, баннер гостя и кэш запросов гостя рисуются заново для вошедшего. Неизвестная, использованная или истёкшая ссылка и ссылка без токена — «Ссылка не подходит» с «Получить новую ссылку»; `429` и выключенный вход по почте (`404`) — свои тексты; сбой сети — карточка ошибки с повтором.

## Настройки

`/settings` (specs/08 §1, без макета; `src/features/account/settings.tsx`) рендерит браузер: страница читает `GET /me`. Гостю — «Войдите, чтобы открыть настройки» со ссылкой на `/login?next=/settings`. Вошедшему — две карточки:

- **Профиль** (FR-AUTH-02): ник, имя и почта (только для чтения, «Не публикуется»). Ник набирается сразу в нижнем регистре и проверяется до запроса (3–24 символа `a-z 0-9 _ . -`). «Сохранить» активна, когда что-то изменилось, и отправляет в `PATCH /me` только изменённые поля; пустое имя — `display_name: null`. Пока ник сменить нельзя (`nick_change_available_at`), поле выключено, а под ним дата следующей смены. `NICK_TAKEN` и `NICK_CHANGE_TOO_SOON` показываются ошибкой под полем ника, остальные ошибки — уведомлением.
- **Сеансы** (FR-AUTH-04): «Выйти на всех устройствах» (`POST /auth/logout-all`).
- **Данные** (FR-USR-05): «Скачать данные» читает `GET /me/export` и сохраняет файл `apparatica-<ник>.json` (имя — из `Content-Disposition`, `src/lib/download.ts`). Ошибка — уведомление.
- **Удаление аккаунта** (FR-USR-05): «Удалить аккаунт» открывает диалог «Удалить аккаунт?» — что удалится через 7 дней, что принятые решения останутся под именем «удалённый участник», что профиль скроется сразу и что сначала можно скачать данные. Кнопка удаления в диалоге доступна, когда введён ник аккаунта (без учёта регистра); она отправляет `DELETE /me` и показывает уведомление с датой. Пока удаление ждёт, вместо кнопки — дата удаления и «Отменить удаление», как в баннере удаления.

Привязанные входы (Ф4) появятся здесь же.

## Профиль

`/u/<ник>` (FR-USR-04, макет Profile, мобильный — без макета; `src/features/profile/`) рендерит сервер из `GET /users/{nick}` и `GET /config`: страницу видят поисковики и превью ссылок, в описании страницы — «решено N из M задач». Ник с заглавными буквами перенаправляется на адрес в нижнем регистре (`308`), неизвестный — 404 «Участник не найден». В хлебных крошках только ник: страницы участников нет. Вместе с профилем сервер читает первые 5 публичных решений (`GET /users/{nick}/solutions?per_page=5`).

- **Шапка**: аватар 64 px с инициалами, ник, имя и «На платформе с <дата>», «Поделиться профилем» (Web Share, где он есть, иначе ссылка копируется; общий код — `src/lib/share.ts`). Свой профиль подписан «так профиль видят другие участники».
- **Плитки** (на телефоне — по две в ряд): «Место» — место в общем рейтинге «из N участников» и сдвиг за неделю (`WeekShift`, общий с общим рейтингом; без очков — «—», «нет очков в общем рейтинге»); «Очки» — «за решённые задачи и места»; «Решено» — N из M опубликованных задач; «Принято» — доля принятых Submit, «20 из 63 отправок» (без отправок — «—»). Серия и активность появятся с дашбордом (Ф4).
- **«Решено по уровням»** — полоса на каждый уровень `config/difficulties.yaml`, цвет уровня.
- **«Решённые задачи»** — новые первыми, первые 8; «Все N» раскрывает список на месте. Дата — «21 окт.», год — только не текущий. Пустой список: чужой — «Пока ни одной решённой задачи», свой — со ссылкой на каталог.
- **«Лучшие места в рейтингах»** — `best_places`: «8 из 412», задача (ссылка на её рейтинг) и «по метрике: задержка» — первая метрика формулы.
- **«Публичные решения»** (`solution-item.tsx`) — строка-ссылка на страницу решения: шеврон, задача, две метрики (задержка, площадь, …) и «место N», если решение держит место в рейтинге задачи, дата как в рейтингах («сегодня», «4 окт.»). «Все N →» ведёт на `/u/<ник>/solutions`.
- Пустые «Лучшие места» и «Публичные решения»: чужие — «Пока нет …», свои — объяснение и ссылка на каталог.

**Публичные решения пользователя** — `/u/<ник>/solutions` (`solutions-page.tsx`, без макета): сервер читает страницу `GET /users/{nick}/solutions` (20 решений, номер страницы — `?page=N` в адресе), строки — те же, что в профиле, под списком — «К профилю», «Решения 21–40 из 52» и `Pagination`. Хлебные крошки — «ник / Решения», ник ведёт в профиль; неизвестный ник — 404 профиля.

Аватар провайдера (`avatar_url`) не показывается: CSP пускает картинки только с сайта, а загрузка с GitHub сообщила бы ему о каждом посетителе профиля (политика конфиденциальности обещает, что за пределы ЕС уходит только то, что пользователь сам передал GitHub).

## Документы

`/legal` — список юридических документов, `/legal/terms`, `/legal/privacy`, `/legal/cookies` — документ (FR-AUTH-06, specs/08 §1, без макета; `src/features/legal/`). Рендерит сервер: тексты — Markdown из `web/content/legal/`, оператор (`{{operator.name}}` и др.) подставляется из `GET /config` (`legal.operator`), рендер — `Statement`, как у условия задачи. Под заголовком соглашения и политики — «Редакция от …» (`legal.versions`), пока `legal.draft` — плашка «Черновик». Неизвестный документ — 404. Шапка ведёт в `/legal` из меню гостя и пользователя (пункт «Документы»), страница входа — на соглашение и политику. Как менять тексты и версии — [legal.md](legal.md).

## Страница задачи

`/problems/<slug>` (`src/features/problem/`, макеты Bench, BenchEmpty, Loading): слева условие, справа сверху редактор, снизу результаты (FR-PRB-01).

**Сервер** (`load.ts`) читает задачу (`GET /problems/{slug}`: текущая версия и процент принятых), уровни (`GET /config`) и теги. Страница, её метаданные и оба слота оболочки просят эти данные в одном запросе к сайту, `cache` из React читает API один раз. Условие, шапка и таблица портов рендерятся на сервере (`problem-statement.tsx`), поэтому они есть в HTML без JavaScript (FR-PRB-04). Метаданные: `title` — название задачи, `description` и `og:description` — первый абзац условия одной строкой до 200 символов (`src/lib/statement/summary.ts`). Картинка для ссылок — OG-карточка задачи ([«Поделиться» и OG-картинки](#поделиться-и-og-картинки)).

**Шапка условия** (FR-PRB-02): название, `DifficultyBadge`, теги — ссылки на каталог с фильтром по тегу, «принято N%» («—» до первого Submit с вердиктом). Справа от названия — значок «Поделиться задачей» (на телефоне его нет: там ссылку отдаёт предложение решать на компьютере). Кнопки «Пожаловаться» (Ф5) нет: она появится вместе со своим окном.

**Вкладки левой панели** (`TabsList variant="panel"`): «Условие», «Мои отправки N», «Решения», «Рейтинг» (только у задачи с рейтингом, `leaderboard` не `null`) и «Эталон» (только у задачи с эталоном, `reference` не `null`; пока он закрыт — с замком). Открытая вкладка и показанная отправка хранятся в адресе (`?tab=submissions|solutions|leaderboard|reference`, `?submission=<id>`, `page-query.ts`) без перехода: `history.replaceState`. Сервер рендерит страницу с вкладкой из адреса.

**Мои отправки** (FR-PRB-06, макеты LeftTabsA/B, `submissions-tab.tsx`). Отправки задачи — гостя из локальной истории ([отправки гостя](#каталог)), вошедшего — из списка сервера ([данные вошедшего](#каталог)) — в `SubmissionList`; число в ярлыке вкладки появляется после гидратации. Краткая причина (`submissions-view.ts`) берётся из `verdict_detail.first_failure` списка, этапы не читаются: «тест 7 из 32» (число открытых тестов — только у отправки текущей версии), «скрытый тест 3 из 8», «строка 16: expected ';'» у ошибки компиляции и запрещённой конструкции, какой лимит превышен, «замечания линта», коды сбоя. Пустое состояние — «Отправок пока нет» с клавишами Run и Submit (LeftTabsB). Пока в списке есть незавершённая отправка, которую страница не показывает (её проверка идёт в другой вкладке или страница переключилась на другую), открытая вкладка раз в 5 с перечитывает список сервера. Под списком — где что хранится: у гостя — в этом браузере, у вошедшего — в аккаунте. Общая история по всем задачам с фильтрами (FR-USR-03) уже есть в API (`GET /submissions?status=`), её экран появится с дашбордом (Ф4).

**Решения** (FR-PRB-07, листы LeftTabsA/B, `features/leaderboard/solutions-tab.tsx`) — публичные решения задачи всех версий из `GET /problems/{slug}/solutions`: принятые Submit вошедших, и лучшее решение автора, и остальные. Порядок — кнопки по формуле рейтинга: первая метрика — порядок мест (`sort=rank`, «По задержке»), следующие — по своей метрике в её направлении («По площади»), и «Новые» (`-submitted_at`). Строка — место в рейтинге (у решения, которое не запись автора, — «—»), аватар, ник (ссылка на профиль), «версия N» у решений прошлых версий, три метрики строкой («0,71 нс · 744 µm² · 162 ячейки»: сначала формула) и «совпадает с решением ‹ник›» у дубликата. По 20 решений, «Показать ещё» дочитывает следующую страницу; внизу «Показано N из M» и «Полный рейтинг →». Пока у посетителя нет своего принятого Submit задачи (`code_locked`, ОВ-2), вместо списка — замок: «Решения других откроются после вашего Accepted» и «Перейти к редактору» (фокус в редактор). Нет решений — «Решений пока нет». Шеврон в конце строки открывает [страницу решения](#публичное-решение).

**Рейтинг** (FR-PRB-07, лист LeftTabsA, `features/leaderboard/leaderboard-tab.tsx`) — первые 5 строк `GET /problems/{slug}/leaderboard?per_page=5` по основной метрике («Рейтинг по: задержка · 304 участника», значение с единицей); своя запись ниже пятёрки — после разрыва «· · ·». Без своего места — пояснение: вошедшему «Вашего места пока нет: оно появится после первой отправки со статусом «Принято»», гостю — что решения гостей в рейтинг не попадают, со ссылкой на вход. Пустой рейтинг — «Рейтинг пока пуст». Внизу — «Полный рейтинг →».

Обе вкладки читают данные, только когда открыты, с ключами под `leaderboardKeys.problem(slug)`: завершённая проверка с местом или принятый Submit (у гостя места нет, но код чужих решений открывается) сбрасывает их все. Строки «Рейтинга» тоже ведут на страницу решения шевроном.

**Эталон** (FR-REF-01, лист LeftTabsB, `src/features/reference/`) сервер читает вместе со страницей задачи: `GET /problems/{slug}/reference` с cookie посетителя — сессии и гостя (`loadReference` в `features/problem/load.ts`, `visitorApi` в `lib/api/server.ts`), только у задачи с `reference`. Открытый эталон сервер и рендерит (`reference-view.tsx`), как условие: по каждому эталонному решению — «Эталон 1 из 2» (у единственного — «Эталон»), название, метрики на профиле по умолчанию (не измерены — словами), пояснение микроархитектуры (Markdown тем же рендером, что условие, картинки — из `assets/` версии) и код в `CodeViewer` с подсветкой, справа — «Сравнить с эталоном»; у `visibility: public` внизу «Автор задачи открыл эталон для всех». `REFERENCE_LOCKED` — замок: «Эталон откроется после вашего Accepted», почему так и «Перейти к редактору» (`reference-tab.tsx`); ошибка чтения — «Эталон не загрузился» и «Повторить» (`router.refresh`). Принятый Submit на странице, пока эталон закрыт, один раз перечитывает страницу (`RefreshOnAccepted`): сервер отдаёт открытый эталон, вкладка теряет замок, а редактор и проверка остаются (клиентское состояние `router.refresh` не сбрасывает).

**«Сравнить с эталоном»** (FR-REF-02, `compare.tsx`; макета нет, specs/08 §6) — широкий диалог поверх страницы: слева своё решение, справа эталон в diff-виде Monaco только для чтения (`features/editor/diff-viewer.tsx`, грузится лениво, в узком окне — изменения в одну колонку), ниже таблица метрик «Ваше / Эталон / Лучшее» с оценкой относительно эталона («↓ 8% лучше эталона»; первое место — `leaderboardKeys.top`). Своё решение — принятый Submit на экране (код — `GET /submissions/{id}`, метрики — его синтез), иначе код редактора в момент открытия, без метрик («синтез запускает только Submit»). Несколько эталонных решений переключаются кнопками. Открывают диалог кнопка баннера принятого Submit и кнопки вкладки «Эталон» (`CompareProvider` в `Bench`: пока эталон закрыт, кнопок нет).

**На телефоне** (FR-MOB-02/03, макет MobTask, `problem-view.tsx`) редактора нет: страница не грузит ни Monaco, ни проверку. Вкладки «Условие», «Решения», «Рейтинг» (у задачи с рейтингом) и «Отправки» — «Мои отправки» с короткой подписью; полоса вкладок прокручивается вбок, если не помещается. `?tab=` — как на компьютере, адрес вкладки «Эталон» открывает условие. «Решения» и «Рейтинг» — те же компоненты, что на компьютере; у замка «Решений» нет «Перейти к редактору». **Эталон** на телефоне — блок в конце условия (`phone-reference.tsx`): метрики лучшего эталона из `GET /problems/{slug}/leaderboard?per_page=1` (они публичны при любой видимости кода; первые три колонки рейтинга одной строкой, «0,91 нс · 902 µm² · 201 ячейка»), под ними «Показать код эталона» раскрывает вкладку «Эталон», отрендеренную сервером, а закрытый код — «Код эталона откроется после вашего первого Accepted…». «Сравнить с эталоном» на телефоне нет: нет редактора, а diff нужен широкий экран. Список отправок только читается — открыть отправку некуда, — и открытая вкладка один раз сверяет его со списком сервера. Отправки гостя видны только в браузере, где их сделали (cookie гостя), поэтому на телефоне список обычно пуст, о чём и говорит пустое состояние. Внизу над навигацией закреплён блок «Решать удобнее на компьютере» (`desktop-offer.tsx`): «Поделиться ссылкой» (Web Share, где браузер его умеет) и «Скопировать ссылку» с уведомлением; ссылка — адрес задачи без параметров. «Прислать ссылку на почту» — вошедшим (Ф2, ОВ-15). Скелетон загрузки на телефоне — только условие.

**Открыть отправку** (`open-submission.tsx`). Клик по строке читает отправку (`GET /submissions/{id}`), ставит её код в редактор одной правкой (Ctrl+Z возвращает прежний код), показывает её результаты и пишет `?submission=<id>` в адрес. Если код редактора не совпадает ни с кодом этой отправки, ни с кодом показанной, ни с шаблоном, сначала диалог «Открыть код отправки?». Удалённая сервером отправка — уведомление «Отправка удалена по сроку хранения», строка становится `gone`. Новая проверка убирает `?submission` из адреса. Страница, открытая с `?submission=<id>`, показывает результаты этой отправки (если сервер её не знает — последней), а код редактора не меняет: черновик не заменяется без вопроса.

**Панели** — `react-resizable-panels`: условие и рабочая колонка (условие по умолчанию 38 %), в колонке редактор и результаты (по 50 %). Разделитель шириной 1 px тянется мышью или стрелками с клавиатуры. Размеры, которые задал пользователь, хранятся в cookie `ap_bench` (путь `/problems`, год; `layout.ts`): сервер рендерит страницу сразу с ними, и панели не прыгают после гидратации. Испорченное значение даёт размеры по умолчанию. Страница занимает окно без шапки и строки состояния, условие и результаты прокручиваются внутри панелей.

**Редактор** (FR-EDT-01, `src/features/editor/`). Monaco собирается вместе с приложением, без CDN. `monaco.ts` подключает ядро (`monaco-editor/editor`), нужные функции (поиск, сворачивание, комментарии, подсказки по словам, переход к ошибкам и другие), грамматику SystemVerilog и воркер (`editor.worker.ts`), затем передаёт этот экземпляр в `@monaco-editor/react`. Модуль загружается лениво (`next/dynamic` без SSR, NFR-PERF-06), до загрузки на месте редактора скелетон строк. Язык и расширение файла выбираются по `language` задачи (`languages.ts`, ADR-0011): для `systemverilog` — язык Monaco `systemverilog` и файл `<top>.sv`.

**Маркеры** (FR-EDT-05). Диагностики этапов `precheck` и `lint` последней проверки, которые указывают на строку файла решения, показываются в редакторе (`code-editor.tsx`): волнистое подчёркивание (маркер Monaco: подсказка при наведении, F8 переходит к следующему), значок на полях (`circle-x`, `triangle-alert`, `info`) и подкрашенная строка (`--ers`, `--wns`, `--ins`; стили — в `globals.css`). Списком диагностики служит консоль: каждая диагностика есть там строкой со ссылкой. Новая проверка убирает маркеры прошлой, правка кода их сдвигает вместе с текстом. Поле значков есть всегда, чтобы код не сдвигался при первой диагностике.

**Темы** `bench-light` и `bench-dark` (`themes.ts`) — значения из `brief/apparatica-handoff/design/monaco-themes.ts`. Грамматика Monaco пишет `$display` как `variable.predefined`, а каждое ключевое слово — как `keyword.<слово>`. Поэтому к теме передачи добавлены два правила: системные задачи и типы данных (`logic`, `int`, `bit` …) окрашены так же, как в условиях. Раскраска парных скобок выключена: SystemVerilog считает скобками `module`/`endmodule` и `begin`/`end`, а дизайн красит их как ключевые слова. Тема следует за `data-theme` на `<html>` (`useResolvedTheme` в `theme.tsx`) и меняется вместе с темой сайта и ОС.

**Черновик** (FR-EDT-02). Код сохраняется в `localStorage` через 1 с после последнего изменения, а также при уходе со страницы и закрытии вкладки. Ключ — `ap_draft:<slug>`, значение — `{"v": 1, "code": …, "version": <версия задачи>, "savedAt": <ISO 8601>}` (`src/features/guest/drafts.ts`). Редактор открывается с черновиком, без него — с шаблоном. Время последнего сохранения показывают «Автосохранение HH:MM» в строке состояния (время браузера) и галочка у имени файла. Если хранилище недоступно или переполнено, индикатор показывает последнее удачное сохранение. Код, черновик и события редактора ведёт `Workspace` (`workspace.ts`) — хранилище вне React, как у `useSubmission`.

**Черновик вошедшего** сохраняется и на сервере (`PUT /me/drafts/{slug}`, `server-draft.ts`), локальный остаётся резервом. Страница задачи читает серверный черновик при отрисовке на сервере (`loadServerDraft` в `load.ts`, с cookie сессии), и редактор открывается с более новым из двух: черновиком другого устройства или этого браузера до входа. Сохранение на сервер идёт вместе с локальным; одновременно — одно, после него — самый новый код, а при закрытии вкладки код уходит сразу (`keepalive`). Неудачное сохранение ждёт следующего изменения, на `401` (сессия кончилась) редактор сохраняет только локально. Индикатор показывает локальное сохранение, а если хранилище недоступно — серверное.

**Новая версия задачи** (FR-PRB-05). Если черновик написан для более старой версии, страница читает шаблон той версии (`GET /problems/{slug}/versions/{version}`). Если шаблон изменился или версию прочитать не удалось, над редактором появляется «Задача обновлена до версии N» с `changelog` текущей версии и кнопками «Сбросить к шаблону» и «Оставить черновик». Любой из ответов, как и следующее автосохранение, записывает черновик под текущей версией.

**Сброс к шаблону** (FR-EDT-03) — кнопка со значком в панели редактора и подтверждение в диалоге. Шаблон заменяет код одной правкой Monaco, поэтому Ctrl+Z возвращает код. Сброс выполняется после закрытия диалога: фокус уходит в редактор, а не на кнопку.

**Run и Submit** (FR-EDT-04) — кнопки с подсказками и сочетаниями: Run — Ctrl+Enter, Submit — Ctrl+Shift+Enter (на Apple — ⌘). Сочетания слушает окно в фазе перехвата (`shortcuts.ts`): они работают и в редакторе, где Monaco иначе вставил бы строку, и вне его; в диалогах не срабатывают. Перед проверкой черновик сохраняется. Пока отправка создаётся и проверка идёт, у её кнопки значок загрузки, а другая кнопка недоступна. Ошибка создания (`problem+json` или сеть) показывается уведомлением, кроме исчерпанного лимита (панель в результатах) и капчи (диалог) — см. [лимиты гостя](#лимиты-гостя-и-капча).

Внутренняя ошибка — «это не вина вашего решения», коды сбоя и «Повторить» (та же проверка с кодом редактора). Принято — с местом из `placement` проверки (`leaderboard` отправки или события `finalized`) «Принято · место N из M» и «Решение стало публичным и попало в рейтинг задачи» (место держит более раннее решение автора или решение — дубликат более раннего: свой текст), замечания линта и формала — следом; без места — «Принято» или «Принято · N замечаний линта», вошедшему — «решение стало публичным», гостю у задачи с рейтингом — «Войдите, чтобы решения попадали в рейтинг задачи». - **Консоль** (FR-CON-*, `console-view.ts`, `results-console.tsx`). Судья присылает только сырой вывод инструментов, поэтому остальные строки консоль строит из событий: разделитель `── <этап> ──` на старте этапа (и у этапа из кэша, пришедшего без старта); пройденные тесты подряд одной строкой («тесты 1–3 из 32 пройдены», скрытые считаются отдельно: «скрытые тесты 1–2 из 2 пройдены»); упавший тест — номер, название, такт и первое расхождение (у скрытого — только номер); диагностики этапа, которых нет в его выводе (у `precheck` вывода нет), — «solution.sv:16:19: expected ';'»; итог этапа — «lint: пройден · 1,4 с», «sim_run: <подпись судьи> · 14,7 с», «превышен лимит вывода», «отменён», «сбой платформы»; «… вывод усечён на 16 кБ»; «┄┄ соединение потеряно в HH:MM:SS ┄┄». Пропущенные этапы строк не дают. Цвет вывода: системные строки (`ch: sys`) — информация, у SystemVerilog строки `%Warning…` и `%Error…` Verilator — предупреждение и ошибка (`outputTones` в `languages.ts`), остальное — обычный текст. Ссылки ведут в редактор только для файла решения (FR-CON-02). Пока проверка идёт, под выводом — идущий тест («тест 4 из 32 выполняется…») и шаг со временем («<заметка heartbeat или этап> · 4,2 с», FR-CON-04); после обрыва — «ожидаем поток…». Консоль завершённой отправки приходит тем же потоком из архива (FR-CON-06).
- **Тесты** (FR-TST-*, `tests-view.ts`, `results-tests.tsx`) — раздел `TestList` на каждый этап блока «Симуляция» конвейера проверки (тесты `netlist_sim` — часть блока «Синтез», во вкладке их нет) («Открытые тесты · Run», «Открытые и скрытые тесты · Submit»; при нескольких этапах — с ключом этапа). Открытые тесты нумеруются по порядку в `summary.tests`: пройденные подряд сворачиваются в «Тесты 1–6» с названиями в подписи и суммой времён (если время есть у каждого), незапущенные подряд — в «Тесты 8–12» с числом и причиной: «прогон остановлен на тесте 7», «предыдущий этап не пройден», «проверка отменена», «этап остановлен» (лимит или сбой). Тесты, о которых проверка ещё не сообщила, считаются по `tests` задачи: пока этап идёт или не начат, они «ожидают запуска», после — не запускались. Тест, который шёл, когда этап остановили, — «прерван». У упавшего — «упал на такте N», «такт N» справа и раскрытие: все расхождения из `mismatches`, подсказки автора («Подсказка: …») и «Тест «…» · сид N» (`seed` отправки). Скрытые тесты — одна строка с замком «Скрытые тесты · M» (FR-TST-03): на Run — «запускаются только на Submit; подробности расхождений не показываются»; на Submit, пока идут, — «выполняется тест K · пройдено N из M» (из анонимных событий `test`), после этапа — из `summary.hidden_tests`: «пройдено M из M», «упал скрытый тест K · пройдено N из M» или «пройдено N из M, остальные не запускались: …». Счётчик вкладки — пройдено из всех (на Run — только открытые, на Submit — с скрытыми); красный, если тест упал, зелёный, если пройдены все; до первого теста счётчика нет.
- **Волны** (FR-WAV-*, `waves-view.ts`, `use-waves.ts`, `results-waves.tsx`, макет BenchWave, лист CmpC) — `WaveformPanel` с трассой упавшего открытого теста: FST этапа первого расхождения из `artifacts` отправки. Шапка — «Такты 0–46 · окно вокруг первого расхождения» и «47 тактов · FST 2,4 кБ»; в норме справа «К расхождению» (курсор и центр на расхождении), «Всё окно» и «Скачать FST». Масштаб и прокрутку даёт сам Surfer (Ctrl+колесо, колесо). «Показать на диаграмме» в баннере неверного ответа и у упавшего теста с трассой открывает вкладку и ставит курсор на расхождение (FR-WAV-03). Пустое состояние объясняет, почему волн нет: проверка идёт, ни один открытый тест не упал, упал скрытый тест, трасса не записана. Истёкший FST — «Волны удалены по сроку хранения» и «Пересоздать волны» (`POST /submissions/{id}/waveform`, FR-WAV-05): пока FST `pending`, страница раз в 2 с перечитывает отправку; неудачное пересоздание — ошибка с «Повторить», исчерпанная квота — уведомление с минутами до следующей попытки. У Run в шапке во всех состояниях есть «Открыть трассу целиком» (`aside` панели): гостю и вошедшему одинаково, в общей квоте волн. Первое нажатие записывает весь упавший тест (`scope: full_test`) — «Записываем весь тест…», затем трасса в просмотрщике с шапкой «Такты 7–22 · весь тест «…»» и скачиванием `&scope=full_test`; уже записанный тест открывается без запроса. «К окну расхождения» возвращает окно; новая проверка начинается с окна. Тест больше лимита FST — ошибка «Весь тест не помещается в лимит FST» без «Повторить»; не удалась запись по другой причине — «Повторить». Какая трасса показана, выбирает `wavesView(…, scope)`: у всего теста, который ещё не запрашивали, вид `unrequested`. FST больше `limits.waveforms.view_max_mb` из `GET /config` (`config/limits.yaml`) — «Слишком большой файл» и только скачивание; у профиля без просмотрщика (`waveview_url: null`) — «Просмотрщик волн недоступен» и скачивание (FR-WAV-06).
- **Синтез** (FR-SYN-03, `synth-view.ts`, `results-synth.tsx`, макет BenchAccepted, лист CmpB) — карточки `MetricCard` метрик `synth/v1` (`SynthCards` из `features/leaderboard/synth-cards.tsx`, их же показывает страница решения): задержка пути (нс, рядом частота из `fmax_mhz`: «≈ 1,69 ГГц»), площадь (µm²), ячейки, триггеры; пояснение — в подсказке по наведению и фокусу. Сравнение — с эталоном (`reference` рейтинга задачи) словами и в процентах: лучше — `ok` и ↓, хуже — `wn` и ↑, равно — «= как у эталона»; направление метрики берётся из формулы рейтинга (остальные лучше, когда меньше), опорные числа — «эталон · лучшее» (первое место). Эталон и первое место читаются одной строкой `GET /problems/{slug}/leaderboard?per_page=1` (`features/leaderboard/api.ts`, ключ `leaderboardKeys.top`); завершённая проверка с местом или принятый Submit сбрасывает кэш рейтинга задачи. Без сравнения карточка говорит почему: «сравниваем с эталоном…», «эталон ещё не измерен», «у задачи нет эталона», «у задачи нет рейтинга», «сравнение не загрузилось». Под карточками — «Проверка нетлиста»: ожидает, идёт, прошла («синтезированная схема прошла те же тесты · пройдено 4 из 4»), упала (подпись судьи и подсказка), не запускалась, сбой. Ниже — «Место в рейтинге задачи · задержка → площадь → время»: «12 из 304», полоса места (`role=meter`) и «лучше, чем у N% решений» из `better_than`; гостю вместо неё — приглашение войти. Пока синтез идёт — скелетоны карточек; несинтезируемое решение, пропущенный синтез и сбой — пустое состояние с причиной.
- **Просмотрщик** (`src/features/waveview/viewer.ts`) — Surfer в iframe `sandbox="allow-scripts"` с адреса `waveview_url` отправки ([waveview.md](waveview.md)). `Viewer` — хранилище вне React, как у `useSubmission`: ждёт `ready` (до 30 с), прячет меню и панели Surfer, ставит тему сайта (`apparatica-light` или `apparatica-dark`, следует за `data-theme`) и показывает трассу: `load` с копией байтов, `signals` в порядке судьи (такт цветом `Clock`, шины — `Bus`, `exp_<порт>` — «<порт> ожидалось» цветом `Expected`), `fit`, курсор и метка «такт N». Ответы принимаются только от окна своего iframe. Паника, тайм-аут или ошибка команды — «Не удалось загрузить волны · Просмотрщик не смог открыть файл», «Повторить» пересоздаёт iframe. Тайм-ауты: `load` — 5 с в адаптере, остальные команды — 10 с. Surfer выполняет каждую команду на кадре анимации, а скрытой вкладке браузера кадров не достаётся, поэтому тайм-ауты идут, только пока страница видна (`visibilityState`), и после возвращения на вкладку начинаются заново; шаги, ещё не отправленные в iframe, ждут возвращения. iframe создаётся, когда упал тест (Surfer грузится, пока читается FST) или открыта вкладка, и остаётся для следующих проверок. Вкладка волн всегда в странице, под открытой вкладкой: браузер не рисует скрытый (`display: none`, `visibility: hidden`) iframe чужого origin, а Surfer работает на кадрах анимации, поэтому и неактивную вкладку, и состояния панели закрывает слой, а не CSS-скрытие. Слой почти непрозрачный (утилита `over-viewer` в `globals.css`, `opacity: 0.99`): iframe, целиком закрытому непрозрачным слоем, браузер даёт кадр раз в секунду, и 11 сигналов грузились бы 30 с вместо 0,2 с.
- **Скринридер** узнаёт статус из скрытой строки `aria-live` («Проверка: Неверный ответ»), а не из баннера: время в баннере меняется каждые 100 мс. Строки консоли не зачитываются (`role="log"` с `aria-live="off"`).

- **Счётчик** «Проверок: N из M в час» стоит в строке «Конвейер проверки», когда осталось 3 проверки и меньше (при нуле — цветом `wn`). Остаток — из `quota` ответа на создание отправки или списка отправок. Гостю под результатами ещё плашка «Осталось 3 проверки из 10 в этот час. Вошедшим доступно больше. Войти →» (`QuotaHint`); при исчерпанной квоте её нет — вход предлагает панель лимита.
- **Лимит исчерпан.** На `429 RATE_LIMITED` с `params.quota` `checks` или `checks_per_ip` вместо баннера проверки — «Лимит проверок исчерпан» с таймером из `retry_after_s` («Следующая проверка будет доступна через 12:41») и недоступной кнопкой «Run · 12:41», у гостя перед ней — «Войти и продолжить»; вкладки прошлой проверки остаются. До первой проверки та же панель стоит на месте подсказки. Код остаётся в редакторе. Кнопки Run и Submit не блокируются: повтор просто получит новый ответ API. Когда время выходит, панель исчезает, а остаток квот перечитывается (`GET /submissions?limit=1`); после каждого `429` тоже — квоту могли потратить в другой вкладке.
- **Капча.** На `428 CAPTCHA_REQUIRED` открывается диалог «Подтвердите, что вы человек» с виджетом ALTCHA (`src/features/captcha/altcha-widget.tsx`): пакет `altcha` грузится только для капчи, задачу виджет берёт по `params.challenge_url`, решает в воркерах и отдаёт решение. Строки виджета — из `messages/ru.json` (`captcha.widget`), цвета — токены. «Продолжить» повторяет тот же Run или Submit с текущим кодом и решением в `captcha`. Текст зависит от `params.reason`; при `frequent` диалог показывает и ожидание из `retry_after_s` («Без неё можно подождать 0:42»), а когда оно выходит, «Продолжить» отправляет без капчи. Неверное или устаревшее решение (`invalid`) открывает диалог снова с новой задачей; «Отмена» закрывает его до следующего отказа API. Капчу перед проверкой спрашивают только у гостя, поэтому под виджетом — «Для вошедших участников лимиты выше, а проверок капчи меньше. Войти →»; в диалоге страницы входа этой подсказки нет.
- Все «Войти» страницы задачи ведут на `/login?next=<путь задачи>`: после входа браузер возвращается к задаче, код ждёт в черновике браузера.

**Строка состояния** (specs/08 §2): «Практика», уровень, «Автосохранение HH:MM», справа язык и «Стр N, Стлб M». Это слот оболочки, поэтому курсор и время сохранения редактор передаёт через `editor-status.ts`. На телефоне строки нет.

**Скелетоны** (макет Loading, `skeletons.tsx`): пока сервер готовит страницу, `loading.tsx` показывает условие, редактор и результаты в размерах по умолчанию.

## Рейтинг решений задачи

Сломанные значения отбрасываются; метрика, которой нет в колонках задачи (API отвечает 422), заменяется порядком мест. По 20 строк.

Заголовок колонки — ссылка сортировки (`aria-sort`): основная метрика стоит за порядком мест, первый щелчок по другой колонке ставит лучшие значения сверху, даты — новые сверху; сортировка мест не меняет. Группа совпадающих решений раскрывается на месте (до 50 решений из ответа, остальные — «и ещё N»). Своя запись не на этой странице — после разрыва внизу таблицы.
- **Низ**: «Места 1–20 из 304 · одна лучшая запись на участника» и `Pagination`. Пустой рейтинг — «Рейтинг пока пуст» с «Решить задачу».

Шеврон в конце строки (и у раскрытых совпадающих) открывает страницу решения.

**На телефоне** (FR-MOB-03, без макета) в таблице — место, автор, одна метрика и шеврон: метрика сортировки, а при сортировке по месту или дате — основная (`phoneColumn`, `query.ts`). Заголовки скрытых колонок не сортируют, поэтому рядом с «Группировать совпадающие» стоит меню сортировки (`sm:hidden`): «По месту», остальные колонки лучшими значениями вперёд, «Сначала новые» (`phoneSorts`); сортировка из адреса вне этого списка подписана «‹По площади›, наоборот» или «Сначала старые». Таблица не прокручивается вбок.

## Условие задачи

`src/lib/statement/` (FR-PRB-03): `renderStatement(markdown, options)` превращает Markdown в HTML-дерево (hast), компонент `Statement` — в React-элементы через `hast-util-to-jsx-runtime`. Рендер синхронный и идёт на сервере: в браузер уходит готовый HTML формул, диаграмм и подсветки, а не KaTeX, WaveDrom и Shiki. Тот же код проверяет условия в `judge validate` (`scripts/statement-check.ts`, [judge.md](judge.md)).

**Конвейер** (`render.ts`, unified): `remark-parse` → `remark-gfm` (таблицы, списки) → `remark-math` → абзац из одной формулы `$$…$$` становится блочной формулой (так пишут авторы, а `remark-math` считает блочными только `$$` на отдельных строках) → `remark-rehype` → `rehype-raw` (HTML автора) → `rehype-sanitize` → KaTeX → WaveDrom → подсветка SV → картинки и ссылки. Санитизация идёт до рендереров: она убирает скрипты, стили, обработчики событий и `javascript:` из HTML автора по схеме GitHub, а разметку KaTeX, WaveDrom и Shiki добавляют уже после неё.

- **Формулы** — `rehype-katex`: `$…$` в строке, блочные — в `.katex-display` с горизонтальной прокруткой; стили и шрифты — `katex/dist/katex.min.css`. Ошибка формулы видна в тексте цветом `--er`, а в `messages` — с номером строки.
- **Временные диаграммы** (`wavedrom.ts`). Блок ` ```wavedrom ` с объектом WaveDrom (JSON5) становится `<figure class="wavedrom">` с SVG (`role="img"`, подпись «Временная диаграмма»). WaveDrom рисует SVG с глобальным `<style>` и одинаковыми `id` у каждой диаграммы, поэтому `<style>` выбрасывается, а классы его скина раскрашены токенами в `statement.css`. Цвета из атрибутов и встроенных стилей (`#000`, `#888`, `#0041c4`, белый фон) заменяются токенами, а `id` и ссылки на них получают префикс диаграммы (`wd0-`, `wd1-` …). Сломанный блок остаётся кодом, ошибка идёт в `messages`.
- **Код** (`highlight.ts`). Блоки ` ```sv ` (`systemverilog`, `verilog`, `v`, `svh`) подсвечивает Shiki с грамматикой SystemVerilog и JavaScript-движком регулярных выражений (синхронно, без WASM). Цвета — токены кода, как в темах Monaco: ключевые слова `--kw`, типы `--ty`, числа и строки `--nm`, комментарии `--cm`, системные задачи `--fn`, операторы `--mu`; одна разметка подходит обеим темам. Остальные блоки — без подсветки.
- **Картинки** — только из `assets/` пакета (`assets/…` без `..`), адрес даёт `assetUrl`. Markdown кодирует адрес картинки (`%20`, кириллица), поэтому рендер сначала декодирует его и проверяет правила `assets/` на имени файла: это имя получают `assetUrl` и список `assets`, по нему же `statement-check` ищет файл. Страница задачи строит адрес `/api/v1/problems/<slug>/versions/<version>/assets/…` с кодированием сегментов ([api.md](api.md#картинки-условия-ф1)), картинки грузятся лениво (`loading="lazy"`). Без `assetUrl` картинки опускаются. Внешние картинки и картинки вне `assets/` убираются с сообщением. В моках у демо-задач картинок нет, обработчик отвечает 404.
- **Ссылки** на `http(s)` открываются в новой вкладке с `rel="noopener noreferrer nofollow"`.
- **Вид** (`statement.css`) — по макету Bench: текст 13,5/22 px, код в строке — чип mono 12 px на `--sf2`, блоки кода и диаграммы — на `--ed` с рамкой `--bd`, у таблиц шапка на `--sf2`. Только токены, поэтому обе темы берутся из `tokens.css`.

Таблицу портов строит `PortTable` из `interface` задачи ([доменные компоненты](#доменные-компоненты)), в тексте условия её нет ([problem-authoring.md](problem-authoring.md#условие)). Истории — `Statement/Statement` в Storybook: полное условие, очистка HTML, ошибки.

## Проверка: `useSubmission`

Хук страницы задачи (`src/features/submission/`): Run и Submit создают отправку, поток её событий ([api.md](api.md#события-проверки)) ведёт состояние панели результатов. Панель результатов берёт данные только из хука.

```ts
const s = useSubmission({
  problem: "sync-fifo",
  version: 1,
  title: "Синхронный FIFO",
  difficulty: "medium",
});
s.start({ kind: "run", code }); // s.starting === "run", пока API создаёт отправку
s.check; // живое состояние проверки, null до первой
s.cancel();
s.reconnect();
await s.showLatest(); // перейти к последней отправке задачи, если она новее показанной
```

Что отдаёт хук:

| Поле                                  | Что это                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check`                               | состояние проверки, которое собрано из событий потока (`machine.ts`): `status`, `seed` (сид отправки, строкой), `queue` (позиция и ожидание), `attempt`, `stages` (как `StageResult`, начатый этап — `running` до `stage_end`, тесты заменяются по `id`), `heartbeat` молчаливого шага, `runningSince` (с какого момента по часам браузера идёт этап), `console`, `done`, `verdict` |
| `submission`                          | отправка из `GET /submissions/{id}`: как создана или восстановлена, после `finalized` перечитывается (артефакты, FST)                                                                                                                                                                                                                                                               |
| `connection`                          | поток: `connecting`, `open`, `waiting` (номер переподключения из скольких и его время), `failed`, `closed` (после `finalized`)                                                                                                                                                                                                                                                      |
| `quota`                               | остаток квот из ответа `POST` или `GET /submissions`                                                                                                                                                                                                                                                                                                                                |
| `restoring`, `starting`, `cancelling` | идёт поиск последней отправки, создание (`run` или `submit`), отмена                                                                                                                                                                                                                                                                                                                |
| `cancelRequested`                     | отменить проверку попросила эта страница, а не другая вкладка или новая проверка                                                                                                                                                                                                                                                                                                    |
| `error`                               | ошибка последнего `start` или `cancel`: `problem+json` (`RATE_LIMITED`, `CAPTCHA_REQUIRED` …) или сетевая. Текущая проверка при этом остаётся                                                                                                                                                                                                                                       |

**Машина состояний.** `status` — `queued`, затем `running` с первым `stage_start`, затем статус из `finalized`; итог берётся только из него. Событие воркера с номером попытки больше текущего сбрасывает этапы, тесты и консоль: проверка началась заново. События с ID не больше последнего применённого пропускаются, поэтому повтор после переподключения ничего не дублирует. Если `finalized` пришёл, пока этап шёл (отмена, сбой), этап становится `cancelled` или `error`. Консоль — записи в порядке потока: старт этапа, строки его вывода, завершённый тест (`passed` или `failed`), отметка `truncated`, итог этапа (из `stage_end`, а у этапа, прерванного `finalized`, — с его новым статусом) и отметка «соединение потеряно» со временем (FR-CON-05); в слова их переводит панель результатов.

**Поток событий** читается через `fetch`, а не `EventSource` (`sse.ts`, `stream.ts`): нужны свои задержки переподключения и `Last-Event-ID` после последнего применённого события, и в jsdom нет `EventSource`. Обрыв потока без `finalized` или сетевая ошибка — переподключение через 1, 2, 4, 8, 15 с (specs/07 §4.2); любое пришедшее событие сбрасывает счётчик. После пятой неудачи поток ждёт `reconnect()` («Подключиться сейчас»), он же переподключает сразу во время ожидания. Отметка в консоли ставится один раз на обрыв, а не на каждую попытку. `404` — отправки больше нет: `failed` с ошибкой, без переподключений.

**Восстановление** (FR-RUN-06). При открытии страницы хук берёт отправки задачи (`GET /submissions?problem=…&limit=100`: они же обновляют [отправки гостя](#каталог)), затем последнюю из них или отправку из `?submission=` (параметр `wanted`) — `GET /submissions/{id}` — и читает её поток с начала. У незавершённой проверки так дочитываются события, у завершённой API отдаёт консоль из архива; без журнала остаются этапы из базы. Если пользователь успел запустить новую проверку, восстановление её не заменяет.

**Локальная история.** Завершённая проверка записывается в историю гостя (`difficulty` — уровень задачи), а показанная отправка — в отправки гостя ([каталог](#каталог)).

**Отправка из списка.** `show(submission)` показывает отправку, как «Смотреть новую»: результаты, поток с начала. Уже показанная остаётся как есть.

**Проверка вне страницы** (FR-RUN-08). Когда страница задачи закрывается (переход в каталог, на другую задачу), незавершённая проверка уходит в фон (`background.ts`): её поток дочитывается до `finalized` с того же события, итог пишется в историю и отправки гостя (каталог сразу показывает статус), а уведомление говорит о вердикте. Открытая снова задача забирает проверку обратно, фоновый поток закрывается. Проверка, которая закончилась на открытой странице в скрытой вкладке, тоже даёт уведомление. Фоновые проверки живут, пока открыта вкладка: перезагрузка их забывает.

**Новая проверка** заменяет предыдущую: поток старой закрывается, её события больше не применяются. Хук держит проверку только открытой задачи (`problem`): при переходе на другую задачу состояние сбрасывается и ищется её последняя отправка. Живое состояние хранится во внешнем хранилище (`store.ts`, `useSyncExternalStore`): события меняют его без `setState` в эффектах. Запросы к API идут через TanStack Query, `QueryProvider` подключён в layout.

**Связь с сервером** (`src/lib/connectivity.ts`). Связь теряется по событию браузера `offline` и когда запрос к API не получил ответа: клиент API (`browserApi`) и поток событий сообщают о `TypeError` из `fetch`; отмена запроса и ответы API с ошибкой связь не роняют. Пока связи нет, `GET /health` спрашивается через 2, 5, 10, 15, 30 с, дальше каждые 30 с; событие `online` и «Повторить сейчас» проверяют сразу. Ответ ниже 500 возвращает связь: 502–504 шлюза значат, что API за ним недоступен, а `503` самого API — что недоступна база, без которой сайт тоже не работает. После возврата запросы TanStack Query, упавшие за это время, читаются заново.

**Полоса сети** (`src/components/shell/network-banner.tsx`) под шапкой: «Нет связи с сервером. Проверьте интернет. Ваш код сохранён в браузере и не потеряется. Следующая попытка через N с», «Повторить сейчас», «Работать офлайн». «Работать офлайн» прячет полосу до следующей потери связи, проверки продолжаются. Пока ту же потерю показывает карточка страницы, полосы нет. Скринридер объявляет только заголовок (`role="status"`), не каждую секунду отсчёта.

**Уведомление о завершении** (FR-RUN-08, `src/features/submission/finish-notices.tsx`, в layout). Проверка, которая закончилась вне страницы задачи ([проверка вне страницы](#проверка-usesubmission)) или в скрытой вкладке, даёт уведомление: заголовок — вердикт (у принятого Submit с местом — «Принято · место N из M»), подпись — «Submit · ‹задача›», тон — по статусу (`ok` принято, `wn` замечания и лимиты, `er` ошибки и сбой, `in` отмена). Вне страницы под подписью ссылка «Открыть результаты» — `/problems/<slug>?submission=<id>`. Уведомление висит 10 с; Sonner не считает время, пока вкладка скрыта. В скрытой вкладке вердикт встаёт перед заголовком («Неверный ответ · Синхронный FIFO · Apparatica», `src/lib/tab-title.ts`), пока вкладку не откроют.

## Тесты и моки

- **Vitest** с jsdom и Testing Library, тесты лежат рядом с кодом (`*.test.ts(x)`).
- **Провайдеры.** `renderWithProviders` (`src/test/render.tsx`) оборачивает компонент провайдерами layout (next-intl, TanStack Query, подсказки), `Providers` — то же для `renderHook`. У каждого теста свой `QueryClient` без повторов запросов.
- **Monaco в jsdom не работает.** Тесты страницы задачи подменяют `CodeEditor` полем ввода с теми методами редактора, которые нужны `Workspace` (`bench.test.tsx`). Размеров у элементов в jsdom нет, и `react-resizable-panels` принимает любой клик за разделитель, поэтому фокус в поле ставится напрямую.
- **Тема ОС и ширина окна.** В jsdom нет `matchMedia`: `src/test/dom.ts` отвечает «не совпадает» на любой запрос (широкое окно), `mockColorScheme` и `mockPhone` (`src/test/match-media.ts`) задают тему ОС и окно телефона; `vi.unstubAllGlobals()` их снимает.
- **Radix и cmdk в jsdom.** `src/test/dom.ts` добавляет то, чего в jsdom нет: `ResizeObserver`, `scrollIntoView`, захват указателя.
- **Запросы к API** перехватывает MSW (`src/mocks/`). Данные моков типизированы схемой API (`Schemas["ConfigResponse"]` …), поэтому изменение контракта ломает их при компиляции.
- **Запрос без обработчика роняет тест.** Свой обработчик для теста задаётся через `server.use(...)`.
- **Вошедший пользователь.** В Node MSW читает cookie только из заголовка `Cookie`, а браузер сам отправляет cookie своего origin. `signIn(nick)` (`src/test/session.ts`) ставит cookie сессии мока и подменяет `fetch`: запросы к своему origin несут `document.cookie`, а `Set-Cookie` ответов попадает в `document.cookie`, как в браузере. `signOut()` после теста стирает cookie и снимает подмену.
- **Состояние моков** (созданные отправки), `localStorage` (история гостя), фоновые проверки и состояние связи сбрасываются после каждого теста. `configureMocks({ speed: Infinity })` завершает проверки мгновенно; `eventsHandler({ dropAfter: N })` обрывает поток событий после N событий.

e2e-тесты против стенда с настоящим воркером (Playwright и axe) — в `e2e/`, см. [stand.md](stand.md#e2e-тесты).

## Моки для разработки

Обработчики MSW из `src/mocks/handlers.ts` работают и в тестах, и вместо бэкенда при разработке:

```sh
just dev-mocks    # http://localhost:3000; то же, что NEXT_PUBLIC_API_MOCKING=enabled pnpm -C web dev
```

С флагом `NEXT_PUBLIC_API_MOCKING=enabled` запросы браузера к API перехватывает service worker (`public/mockServiceWorker.js`), а запросы сервера Next.js — `src/instrumentation.ts`. Содержимое страницы гидратируется после старта worker'а, поэтому и первые запросы получают моки. Запросы без обработчика уходят в сеть. У браузера и сервера состояние моков своё. Новые обработчики добавляет PR контракта каждой фазы (specs/05 §0). `GET /health` всегда отвечает `ok`: проверку связи в моках проверяют режимом офлайн в DevTools.

**Каталог.** `GET /problems` (`src/mocks/problems.ts`) отдаёт пять демо-задач из `problems/` (`fixtures.problems`, проценты принятых придуманы, у `sync-fifo` — `null`) с фильтрами и сортировками API: поиск `q` в названии, slug и подписях тегов, `difficulty`, `tag`, `sort`, страницы. `GET /tags` — теги из `problems/tags.yaml`. `GET /problems/{slug}` и `GET /problems/{slug}/versions/{version}` (только для текущей версии) отдают демо-задачи из `src/mocks/problem-versions.json`, процент принятых — из `fixtures.problems`. Файл не пишется вручную: его создаёт `just mock-problems` (`scripts/mock_problems.py`) из пакетов `problems/`, а тест бэкенда `test_mock_scenarios.py` сверяет его со схемой API и пакетами. Тот же скрипт пишет `src/mocks/reference-solutions.json` — эталоны пакетов с кодом и пояснениями.

**Проверки.** Отправка в моках воспроизводит записанный сценарий: события потока с настоящими задержками, а `GET /submissions/{id}` показывает состояние на текущий момент. Сценарий выбирается меткой в коде решения, например `// mock: wrong-answer`. Без метки Run воспроизводит `run-passed`, а Submit — `accepted`. Задача и версия отправки — из запроса, остальное — из записи.

| Сценарий                               | Что показывает                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| `run-passed`, `accepted`               | Run и Submit приняты                                                                          |
| `accepted-with-warnings`               | Submit принят с замечанием линта                                                              |
| `wrong-answer`                         | Run упал на открытом тесте; есть FST-трасса окна ошибки                                       |
| `wrong-answer-hidden`                  | Submit упал на скрытом тесте                                                                  |
| `compile-error`, `forbidden-construct` | precheck: ошибка компиляции, запрещённая конструкция                                          |
| `output-limit`                         | превышен лимит вывода (`truncated`; в записи лимит снижен до 16 КБ, чтобы файл был небольшим) |
| `cancelled`                            | проверка отменена во время симуляции                                                          |
| `internal-error`                       | сбой платформы на этапе (`EXECUTOR_FAILED`)                                                   |
| `retry`                                | воркер первой попытки пропал, проверка прошла со второй (`attempt: 2`)                        |
| `accepted-param-sets`                  | Submit `sync-fifo` принят при двух наборах параметров, `default` и `narrow` (`sim_full@narrow`…) |
| `wrong-answer-param-set`               | Submit упал на открытом тесте при наборе `narrow`, следующие экземпляры пропущены; есть FST    |

Кнопка «Отменить» в моках работает в любом сценарии: открытый поток сразу отдаёт события до момента отмены и заканчивается `finalized` со статусом `cancelled`, не дожидаясь следующего события сценария. Квота гостя из фикстуры конфига (10 проверок в час) расходуется созданными отправками; на одиннадцатой мок отвечает `429 RATE_LIMITED`. Отправки принадлежат вошедшему пользователю мока или единственному гостю, как в API: чужая — `404`, у вошедшего квоты пользователя (60 в час), капчи нет, а `scope: full_test` отвечает `501`. Быстрее всего её тратит сценарий `compile-error`. Состояние моков в браузере живёт до перезагрузки страницы.

Капча в моках (`src/mocks/captcha.ts`): `GET /captcha/challenge` выдаёт настоящую задачу ALTCHA (`maxnumber` 20 000), так что виджет её решает. Метка `// mock-captcha: frequent` отвечает на отправку `428 CAPTCHA_REQUIRED` с `reason: frequent` и `retry_after_s: 42`, `// mock-captcha: always` — с `reason: always`, пока отправка не принесёт решение. Мок проверяет решение как API, кроме подписи, и принимает его один раз; повтор — `reason: invalid`.

**Вход и аккаунт** (`src/mocks/users.ts`, [api.md](api.md#пользователи-и-вход-ф2-контракт)). В фикстуре конфига включены провайдеры GitHub и email. Сессия мока — cookie `ap_session=mock.<id>` без `HttpOnly`; пользователи живут в памяти. У `ada` постоянный id, поэтому её сессия переживает перезагрузку страницы (после входа по ссылке страница перезагружается) и известна мокам сервера; созданные пользователи живут до перезагрузки. Готовый пользователь `ada` (ada@example.com) решил `mux4` и `carry-adder` и пробовал `seq-detector`; завершённые проверки пользователя в моке решают и пробуют задачи по правилам ингестора. Вошедшему каталог отдаёт статусы, фильтр `status` и число решённых по уровням, гостю — `null`, а фильтр `status` без входа — `401`. `POST /auth/email/request` печатает ссылку входа в консоль браузера (`[mock] login link …`); любой токен годится, токен со словом `expired` — `LOGIN_LINK_INVALID`. Ссылка на новый адрес создаёт пользователя со случайным ником `user-xxxxxx`, как API (`created: true`). Вход через GitHub всегда входит как `ada` и возвращает на `next`, но это переход браузера, а service worker MSW переходы не перехватывает: в `just dev-mocks` кнопка GitHub ведёт на 404, работают тесты и вход по ссылке. Ник, удаление и отмена удаления, экспорт (с отправками мока) и черновики работают как в API, включая `NICK_TAKEN`, `NICK_CHANGE_TOO_SOON` и `CODE_TOO_LARGE`. CSRF мок не проверяет. В тестах `src/test/setup.ts` сбрасывает пользователей вместе с остальными моками.

**Рейтинги и решения** (`src/mocks/leaderboards.ts`, [api.md](api.md#рейтинги-и-решения-ф3)). Судьи в моках нет, поэтому метрики синтеза придуманы: каждая задача ранжируется по задержке, затем площади (поле `leaderboard` задачи), у эталона — свои придуманные метрики. Этапы публичного решения — этапы Submit задачи, у `synth` — эти метрики. Соперники — постоянная толпа без аккаунтов, одна и та же в браузере и на сервере Next.js: у `sync-fifo` 304 участника, у остальных задач меньше. Среди них есть общие места и решения с деревом разбора эталона, сгруппированные под самым ранним. Их профили открываются (`/u/rtl_fan` и т. п.); код соперника — эталон с комментарием. Вошедшие пользователи попадают в рейтинги с решениями `ada` (`mux4`, `carry-adder`) и своими принятыми Submit: метрики считаются от хэша кода, а код эталона измеряется как эталон и группируется с ним. Такой Submit становится публичным, а его место приходит в отправке и в событии `finalized`. Гость или пользователь без принятого Submit задачи видят замок на чужом коде и `REFERENCE_LOCKED` на эталоне. Этапа синтеза в сценариях проверок пока нет: вкладка «Синтез» получит его с записью сценариев на профиле 2 тулчейна.

Волны в моках ([api.md](api.md#артефакты-и-волны)): FST сценария `wrong-answer` скачивается по presigned URL мока. Вторая метка `// mock-fst: expired` показывает его истёкшим: «Пересоздать волны» (`POST /waveform`) тратит квоту волн (5 в час), FST 2 с остаётся `pending`, затем снова `ready`. Метка `// mock-fst: large` называет FST размером 48 МБ — больше порога просмотра. Готовый или пересоздающийся FST мок, как и API, возвращает без траты квоты. `scope: full_test` у Run записывает «весь тест» — тот же FST с тактами от 0, 2 с `pending`, в той же квоте; у Submit — `404`. Метка `// mock-fst: full-too-large` кончает запись всего теста `failed` с `TRACE_TOO_LARGE`.

Просмотрщик в моках — адрес из `NEXT_PUBLIC_MOCK_WAVEVIEW_URL`, без него `waveview_url` отправок равен `null` («Просмотрщик волн недоступен»). Собранный сайт (`just waveview-build`, [waveview.md](waveview.md)) отдаёт `just waveview-serve` с заголовками стенда на http://localhost:3901:

```sh
just waveview-serve
NEXT_PUBLIC_MOCK_WAVEVIEW_URL=http://localhost:3901/2026.10.1/index.html just dev-mocks
```

**Запись сценариев.** Сценарии в `src/mocks/scenarios/*.json` не пишутся вручную. Их записывает `just record-scenarios` (`scripts/record_scenarios.py`): он проверяет решения демо-задач в образе тулчейна и добавляет к событиям пайплайна то, что добавят воркер, API и ингестор (specs/07 §4.1). Это `attempt`, склейка строк лога, heartbeat на молчаливых шагах, `queue` до прогона и `finalized` после. Тест бэкенда `test_mock_scenarios.py` сверяет файлы со схемами API. Поэтому при изменении событий или отправки нужно перезаписать сценарии: `just record-scenarios` или `just record-scenarios wrong-answer`. ID событий в файле задают время воспроизведения; `queue` мок отдаёт без `id:`, как API ([api.md](api.md#события-проверки)).

Сценарии с наборами параметров (`accepted-param-sets`, `wrong-answer-param-set`) — Submit задачи `sync-fifo`, которая проверяет симуляцию, синтез и симуляцию нетлиста при наборах `narrow` и `wide` ([api.md](api.md#наборы-параметров-ф3а)): эталон и мутант с жёстко заданной глубиной, который падает на открытом тесте набора `narrow`. Остальные сценарии записаны до появления наборов у демо-задач; при перезаписи Submit задач с параметрами в них появятся экземпляры этапов, которые панель результатов показывает с T3a.6.
