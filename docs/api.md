# API

HTTP API платформы: где лежит контракт, как его менять и как его использует фронтенд. Требования к API и список эндпоинтов по фазам — [specs/05](../specs/05-api.md).

## Контракт

Источник правды — код бэкенда: Pydantic-схемы (`schemas.py` модулей) и роуты FastAPI (`api.py`). Из них FastAPI строит документ OpenAPI 3.1, а он коммитится в двух видах:

| Файл | Что это | Чем создаётся |
|---|---|---|
| `backend/openapi.json` | документ OpenAPI | `apparatica openapi` |
| `web/src/lib/api/schema.d.ts` | типы TypeScript для клиента | `openapi-typescript` из `openapi.json` |

Оба файла пересоздаёт одна команда:

```sh
just openapi
```

Вручную файлы не правятся. Устаревший файл ловят проверки:
- `backend/tests/test_openapi.py` сравнивает `openapi.json` с документом, построенным из кода (`just test`, job Python в CI);
- `just check-api` сравнивает `schema.d.ts` с `openapi.json` (job JS в CI);
- `just typecheck-js` находит код фронтенда, который не совпадает с новыми типами.

Работающий сервер отдаёт тот же документ на `/api/v1/openapi.json` и интерактивную документацию на `/api/v1/docs`.

## Как изменить API

1. Измените схемы и роуты в коде бэкенда.
2. Выполните `just openapi`.
3. Закоммитьте код вместе с `openapi.json` и `schema.d.ts`. На ревью дифф `openapi.json` показывает изменение контракта.

Фаза с новыми эндпоинтами начинается с PR контракта (`T<фаза>.0`, specs/05 §0): схемы, роуты-заглушки с ответом `501 NOT_IMPLEMENTED`, `openapi.json`, типы клиента и моки. Заглушка проверяет параметры (`422`) и уходит, когда задача реализации влита.

## Что объявляется в коде явно

FastAPI не выводит из кода всё, что нужно клиенту:

- **Ошибки.** Все ошибки — `application/problem+json`. В компонентах OpenAPI схема ошибки называется `Error`; имя `Problem` занято задачами. Любая операция может вернуть `500 INTERNAL`: этот ответ добавляется ко всем роутерам при подключении в `apparatica.main`. Остальные ошибки роут перечисляет сам: `responses=problem_responses(ErrorCode.NOT_FOUND, …)` из `apparatica.core.errors`. Роут с параметрами объявляет `VALIDATION_ERROR` (422), иначе FastAPI вставит в схему свой ответ 422 в другом формате; тест падает, если в документе есть ошибка не в формате `problem+json`.
- **Поток SSE.** `GET /submissions/{id}/events` объявлен с классом ответа `EventStreamResponse` (`apparatica.core.http`) и `responses={200: {"model": SubmissionEvent}}`. Так `text/event-stream` в документе ссылается на компонент `SubmissionEvent`, и в TS-клиенте есть типы событий. Встроенный `fastapi.sse.EventSourceResponse` не подходит: с ним обработчик обязан быть генератором и не может ответить ошибкой `problem+json` до начала потока.
- **Фаза.** Каждая операция помечается `openapi_extra={"x-phase": N}`.
- **Имена операций.** `operationId` — имя функции-обработчика (`list_problems`, `create_submission`). Переименование обработчика меняет контракт.

## Общие правила

Описаны в specs/05 §1–2 и реализованы так:

- **Префикс** `/api/v1`, JSON, `snake_case`, время — ISO 8601 с часовым поясом, идентификаторы — UUIDv7 строкой.
- **Числа больше 2⁵³** передаются строкой: так передаётся `seed` отправки (63 бита).
- **Ошибки.** `code` — стабильный машинный код. По нему фронтенд показывает текст из `messages/ru.json`, подставляя `params`. Поля `title` и `detail` — английские и предназначены для разработчиков. В теле ошибки есть все поля схемы `Error`; незаданные равны `null`, как и описывают типы клиента.
- **CSRF.** Изменяющие запросы несут заголовок `X-CSRF-Token` со значением cookie `ap_csrf` и приходят с origin сайта; иначе — `403 CSRF_FAILED` ([подробнее](#пользователи-и-вход-ф2-контракт)).
- **Кэш.** Публичные данные отдаются с `ETag` и `Cache-Control: public, max-age=60, stale-while-revalidate=300`; на `If-None-Match` сервер отвечает 304. Версия задачи неизменяема: `public, max-age=31536000, immutable`. Ответы про отправки — `private, no-store`.

## Картинки условия (Ф1)

`GET /api/v1/problems/{slug}/versions/{version}/assets/{path}` отдаёт файл `assets/<path>` пакета версии (FR-PRB-03). Версия видна по тем же правилам, что `GET /problems/{slug}/versions/{version}`: опубликованная задача, не новее текущей. Путь — по правилам рендера условия (без `..`, пустых сегментов, `?`, `#`, `\`), только PNG, JPEG, GIF, SVG и WebP; всё остальное, как и отсутствующий файл, — `404 NOT_FOUND`.

Импорт кладёт каждую картинку в бакет `packages` отдельным объектом `<slug>/<version>-<content_hash>/assets/…` рядом с архивом пакета ([development.md](development.md#импорт-задач)), и API отдаёт её байты сам, а не редиректом на presigned URL: адрес не протухает, картинка приходит с того же origin, что и сайт, и кэшируется как версия — `public, max-age=31536000, immutable` с `ETag`. Ответ несёт `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` и `nosniff`: SVG, открытый отдельной вкладкой, не исполнит скрипты на origin сайта (в `<img>` браузер их не исполняет и так). Код — `apparatica.problems.assets`, роут `get_problem_asset`.

## Отправки (Ф0)

`POST /api/v1/submissions` создаёт Run или Submit и отвечает `202` с отправкой и заголовком `Location`. Дальше её берёт воркер ([architecture.md](architecture.md#оркестратор)).

1. **Размер кода** проверяется по `limits.solution` из `config/limits.yaml`, то есть по тем же значениям, что отдаёт `GET /config`. Байты считаются в UTF-8, строки — по `\n`. Превышение — `413 CODE_TOO_LARGE`, в `params` лимиты и фактические значения. Код с символом NUL или с одиночным суррогатом — `422`.
2. **Версия задачи.** Отправить можно только на текущую версию опубликованной задачи. Иначе `409 PROBLEM_VERSION_OUTDATED` с `params.current_version`; неизвестная задача — `404`.
3. **Профиль тулчейна.** Отправка проверяется профилем по умолчанию для языка задачи. Если такого профиля нет — `503 JUDGE_UNAVAILABLE`. Профили регистрирует `apparatica-admin toolchain add` ([development.md](development.md#профили-тулчейна)).
4. **Сид.** Для каждой отправки выбирается случайное 63-битное число. Версия задачи, профиль и сид вместе делают прогон воспроизводимым (specs/04 §1).
5. **Очередь.** После коммита отправка уходит в очередь `judge.<resource_class>` заданием для воркера: код, сид, пакет, образ тулчейна, токен задания ([architecture.md](architecture.md#очередь-проверок)). Пока отправка ждёт, `queue_position` — её место в очереди, начиная с 1. Оценка ожидания `eta_s` пока не считается: для неё нужна медиана длительности проверок от ингестора. Если очередь недоступна — `503 JUDGE_UNAVAILABLE`, а отправка сохраняется как `internal_error` с кодом `QUEUE_UNAVAILABLE`. Без `APX_QUEUE_URL` (разработка без воркеров) задание только пишется в лог.

**Токен задания** (specs/07 §5.3) — подписанные HMAC-SHA256 поля `{submission_id, attempt_max, exp}` в формате `v1.<payload>.<mac>` (base64url). Ключ — `APX_JOB_TOKEN_KEY`, срок жизни — `APX_JOB_TOKEN_TTL_S` ([configuration.md](configuration.md)). Ингестор (Ф1) примет результат воркера только с действительным токеном этой отправки.

`GET /api/v1/submissions/{id}` возвращает отправку с этапами (в порядке конвейера) и артефактами. В списке артефактов только виды, которые можно скачать: `log`, `events`, `fst`. Файл результатов тестбенча (`tb_result`) не показывается: в нём ожидаемые значения скрытых тестов (specs/07 §4.4). Сначала идут логи и журнал событий, затем по одному FST на этап в порядке конвейера ([артефакты](#артефакты-и-волны)). Отправку видит только её автор ([авторы](#авторы-и-лимиты)).

## Отправки (Ф1): контракт

PR контракта Ф1 (T1.0) объявил эндпоинты Ф1, теперь все они реализованы. Фронтенд работает с ними и через моки ([frontend.md](frontend.md#моки-для-разработки)).

| Эндпоинт | Ответ | Реализация |
|---|---|---|
| `GET /submissions?problem=&status=&cursor=&limit=` | `SubmissionPage`: свои отправки, новые первыми, `next_cursor` и остаток квот `quota`, см. [авторы](#авторы-и-лимиты) | работает (T1.7a, фильтр `status` — T2.7a) |
| `GET /submissions/{id}/events` | поток событий проверки, см. ниже | работает (T1.5) |
| `POST /submissions/{id}/cancel` | `202` без тела; итог приходит событием `finalized` со статусом `cancelled`. Завершённая отправка — `409 SUBMISSION_FINISHED`, нет Valkey — `503 JUDGE_UNAVAILABLE`. Как работает — [architecture.md](architecture.md#отмена) | работает (T1.6) |
| `GET /submissions/{id}/artifacts/{kind}?stage=` | `302` на presigned URL файла; истёкший файл — `404`, см. [артефакты](#артефакты-и-волны) | работает (T1.17a) |
| `POST /submissions/{id}/waveform` | `202` с артефактом FST, см. [артефакты](#артефакты-и-волны) | работает (T1.17a) |
| `GET /captcha/challenge` | задача ALTCHA `CaptchaChallenge`, см. [капча](#капча) | работает (T1.7b) |

Что изменилось в эндпоинтах Ф0:

- `POST /submissions` принимает `captcha`: решённую задачу ALTCHA после ответа `428 CAPTCHA_REQUIRED`. Добавлены ошибки `429 RATE_LIMITED` и `403 HEAVY_NOT_ALLOWED` ([авторы](#авторы-и-лимиты)). Ответ `SubmissionCreated` — это отправка и остаток квот `quota` после неё.
- В отправке появилось поле `eta_s`: оценка ожидания в очереди в секундах.
- `verdict_detail.first_failure` (первый непройденный этап) кроме `stage`, `test` и `cycle` несёт `test_number` — номер упавшего открытого теста в порядке прогона, с 1; `hidden` — сводку скрытых тестов (`total`, `passed`, `failed_index`), если упал скрытый; `diagnostic` — первую ошибку этапа (`Diagnostic`: файл, строка, сообщение). Этого хватает для краткой причины в списке отправок без чтения этапов (FR-PRB-06). У вердиктов, записанных раньше, этих полей нет.
- В отправке появилось поле `waveview_url`: страница просмотрщика волн профиля тулчейна этой отправки, для изолированного iframe; `null`, если у профиля нет просмотрщика или не задан `APX_WAVEVIEW_URL` ([waveview.md](waveview.md)).
- У артефакта вместо `expired` теперь `state`: `ready`, `expired` (удалён по сроку хранения), `pending` (FST пересоздаётся), `failed`. Поле `size_bytes` равно `null`, пока файла нет. `waveform` у FST описывает трассу: тест, `scope` (`failure_window` — окно вокруг первого расхождения, `full_test` — весь тест), такты от и до, такт и время курсора, сигналы для просмотрщика.

**Квоты** (`QuotaStatus`): `checks` — проверки, `waveforms` — пересоздания и полные трассы волн. В каждом окне `limit` и `remaining` считаются за час. `reset_at` — когда освободится следующая попытка; пока попытки есть, оно равно `null`. Остаток квот приходит в ответах `POST /submissions` и `GET /submissions`: этого хватает и для счётчика «Проверок: 3 из 10 в час», и для панели «Лимит исчерпан» с таймером (FR-GST-04). Лимиты гостя и вошедшего разные ([авторы](#авторы-и-лимиты)).

### Артефакты и волны

**Список.** Логи (`log`, по одному на этап) и журнал событий (`events`, без этапа) показываются как хранятся. FST — один на этап: последний файл или, если после него запрошено пересоздание, его состояние (`pending` или `failed`, `size_bytes: null`). Что покрывает FST, API берёт из метрик этапа (`sim/v1`, [judge.md](judge.md)):

| Поле `waveform` | Что это |
|---|---|
| `test`, `scope` | упавший тест; `failure_window` — окно вокруг первого расхождения |
| `from_cycle`, `to_cycle` | такты окна: от 64 до расхождения до 16 после |
| `cursor_cycle`, `cursor_time_ps` | такт первого расхождения и его время в FST, в пикосекундах. Ось Surfer — время, а не такты: курсор ставится по времени |
| `signals` | что показать и в каком порядке: такт (`clock`), входы (`input`), затем каждый выход (`output`) и ожидаемое значение модели (`expected`, сигнал `exp_<порт>`). `path` — полное имя в FST, `port` — порт интерфейса задачи. У трасс, записанных до T1.17a, список пуст |

**Скачивание** (FR-WAV-06). `GET /submissions/{id}/artifacts/{kind}?stage=<этап>` — `302` на presigned URL последнего хранимого файла этого вида и этапа (у `events` этапа нет). Файл сохраняется как `<id>-<этап>.fst`, `<id>-<этап>.log.zst`, `<id>-events.jsonl.zst`: логи и события хранятся сжатыми zstd. URL подписан для адреса хранилища, по которому его видит браузер (`APX_S3_PUBLIC_URL`, на стенде `http://s3.localhost:8080`), и живёт `APX_ARTIFACT_URL_TTL_S` секунд (5 минут). Истёкший файл, чужая отправка, этап без файла — `404`; `tb_result` не скачивается (`422`).

**Пересоздание** (FR-WAV-05). `POST /submissions/{id}/waveform` с `scope: failure_window` пересоздаёт окно трассы упавшего открытого теста:

- FST ещё хранится или уже пересоздаётся — ответ `202` с ним как есть, квота не тратится;
- иначе (файл истёк, прошлое пересоздание не удалось) тратится квота `waveforms`, в очередь задачи уходит задание `judge_waveform` ([architecture.md](architecture.md#очередь-проверок)), ответ — FST в состоянии `pending`;
- готовность клиент узнаёт, опрашивая `GET /submissions/{id}`, пока `state` не станет `ready` или `failed`: стрим событий к этому времени давно истёк, а его архив неизменяем;
- нет такой отправки, она не завершена или окна трассы в ней нет (тест прошёл, упал скрытый тест, тестбенч недетерминирован) — `404`; квота исчерпана — `429` с `params.quota: waveforms`; очередь недоступна — `503 JUDGE_UNAVAILABLE`, заявка сохраняется как `failed`.

`scope: full_test` (весь тест) — только для вошедших: гостю — `401 UNAUTHENTICATED`, вошедшему — `501 NOT_IMPLEMENTED`, пока запись целого теста не сделана (T2.12).

### События проверки

`GET /submissions/{id}/events` — поток Server-Sent Events (specs/07 §4). Каждое событие приходит в трёх полях:

```
id: 1793003352739-1
event: stage_start
data: {"type":"stage_start","stage":"lint","stage_type":"lint","ordinal":1,"attempt":1}
```

`id` — ID записи Valkey Stream (миллисекунды и номер), по нему клиент дочитывает поток после обрыва (`Last-Event-ID` или `?from=`; если есть оба, берётся заголовок). `event` — тип события, `data` — событие `SubmissionEvent`, объединение по полю `type`:

| `type` | Кто пишет | Что значит |
|---|---|---|
| `queue` | API | позиция в очереди и оценка ожидания; раз в 2 с, пока отправка ждёт; без `id:` — в стриме его нет, и при переподключении оно не дочитывается |
| `stage_start`, `stage_end` | воркер | этап начат; этап завершён с результатом `StageResult` |
| `log` | воркер | целые строки консоли, каждая с переводом строки, склеенные за ~75 мс или до 8 КБ |
| `heartbeat` | воркер | раз в секунду, пока этап молчит (сборка C++, ABC, SAT) |
| `test` | воркер | тест начат или завершён; тест заменяется по `id` целиком |
| `truncated` | воркер | вывод этапа превысил лимит, этап остановлен |
| `done` | воркер | конвейер попытки завершён |
| `finalized` | ингестор | итоговый статус и `verdict_detail` — последнее событие потока |

У событий воркера есть `attempt`. Событие с новым номером попытки значит, что проверка началась заново, и клиент сбрасывает результаты. Итоговый статус клиент берёт только из `finalized`.

Модели событий воркера — это события пайплайна `judge.core.events` с полем `attempt` (`apparatica.submissions.events`). Тест проверяет, что у каждого события пайплайна есть пара в потоке.

Как поток устроен на сервере (`apparatica.submissions.live`, `apparatica.submissions.streams`):

- **Живой поток.** Эндпоинт отдаёт записи стрима `sub:<id>` после ID клиента, затем новые — от единственного читателя стримов процесса (`StreamHub`: один `XREAD BLOCK` по всем стримам, у которых есть зрители; соединение Valkey на клиента не открывается). Поток заканчивается после `finalized`.
- **Ожидание.** Пока отправка в очереди и событий воркера ещё нет, раз в 2 с приходит `queue` с позицией.
- **Keepalive.** Комментарий `: keepalive` каждые 15 с без событий. Ответ несёт `Cache-Control: private, no-store` и `X-Accel-Buffering: no`: прокси не должен буферизовать поток.
- **Архив.** Когда проверка завершена, а стрим истёк (через 10 минут после `finalized`), события берутся из журнала `events.jsonl.zst` последней попытки в бакете `artifacts` с теми же ID, а `finalized` — из базы с ID после последнего события. Если журнала нет (проверка не запускалась, журнал удалён по сроку хранения), поток состоит из одного `finalized`.
- **Ошибки до потока.** `404 NOT_FOUND` — нет отправки; `503 JUDGE_UNAVAILABLE` — проверка не завершена, а Valkey не настроен (`APX_QUEUE_URL`).

## Авторы и лимиты

Автор отправки — вошедший пользователь ([сессия](#пользователи-и-вход-ф2-контракт)), иначе гость (FR-GST-01, ADR-0010). У отправки есть `user_id` или `guest_id`, но не оба. Вошедший — автор, даже если в браузере осталась cookie гостя: прежние гостевые отправки ему не видны, пока их не перенесёт импорт (Ф4, FR-GST-06), а после выхода гость снова видит только свои. Код — `CurrentAuthor` в `apparatica.submissions.api`, `Author` в `apparatica.submissions.quotas`.

**Cookie `ap_guest`.** Первая отправка без сессии и без cookie создаёт гостя: случайный UUID, подписанный HMAC-SHA256 ключом `APX_GUEST_COOKIE_KEY` (`<uuid>.<mac>`, base64url). Cookie `HttpOnly`, `SameSite=Lax`, `Path=/`, срок — год; `Secure` выключается только для стенда по HTTP (`APX_COOKIE_SECURE`). Cookie с неверной подписью не принимается: запрос считается запросом без гостя, а следующая отправка создаёт нового. Код — `apparatica.auth.guests`.

**Доступ.** `GET /submissions/{id}`, его поток событий, артефакты, пересоздание волн и отмену получает только автор. Чужая отправка и запрос без сессии и cookie получают `404 NOT_FOUND`, как будто отправки нет. `GET /submissions` без них — пустой список и полные квоты гостя.

**Список** (FR-USR-03). `GET /submissions` — отправки автора по всем задачам, новые первыми, с фильтрами `problem` (slug) и `status` (любой из перечисленных статусов отправки). Страница — `limit` записей (по умолчанию 20, не больше 100) и `next_cursor`: его передают как `cursor` за следующей страницей; на последней странице он равен `null`. Курсор — непрозрачная строка; испорченный курсор — `422`.

**Квоты** (specs/07 §3, значения — `quotas.guest` и `quotas.user` в `config/limits.yaml`: гостю 10 проверок в час и одна одновременно, вошедшему 60 и две) проверяются при создании отправки, в таком порядке:

1. Тяжёлая задача (`resource_class: heavy`): гостю — `403 HEAVY_NOT_ALLOWED`; вошедшему — квота тяжёлых проверок в сутки (`heavy_per_day`), скользящее окно за 24 часа.
2. Проверок в час — скользящее окно за последние 60 минут. Считаются отправки автора в Postgres, кроме `internal_error`: сбой платформы попытку не тратит.
3. Одновременных проверок — отправки автора в `queued` и `running`. Незавершённый Run той же задачи не считается, если новая отправка — Run: новый Run его вытесняет (FR-JDG-10).
4. Капча, если она нужна ([ниже](#капча)); вошедшему она не нужна.
5. Проверок с одного адреса в час (`checks_per_ip`, ниже) — на случай гостя, который сбрасывает cookie.

Отправки одного автора создаются по очереди: проверка квот и запись идут в одной транзакции под advisory lock автора, поэтому два параллельных запроса не займут одну последнюю попытку. Остаток квот (`QuotaStatus`) приходит в ответах `POST` и `GET /submissions`. Квота волн (`waveforms`) — скользящее окно в `valkey-cache`; её тратит `POST /submissions/{id}/waveform`, когда ставит задание.

**Rate limit** (NFR-SEC-06, `config/rate-limits.yaml`) защищает платформу от злоупотреблений: скользящие окна библиотеки `limits` в `valkey-cache`. Все изменяющие эндпоинты, кроме сохранения черновика, ограничены числом запросов с одного адреса (`requests_per_ip`) и от одного автора — вошедшего пользователя, иначе гостя (`requests_per_author`). У автосохранения черновика своё окно на пользователя (`drafts_per_user`, 120 в минуту): набор кода не тратит запросы автора и адреса, который делит класс. Начало входа (`GET /auth/{provider}/login`, `POST /auth/email/request`) и вход по ссылке (`POST /auth/email/verify`) ограничены ещё и числом входов с адреса (`logins_per_ip`, 100 за 10 минут: класс входит с одного адреса); вход через провайдера — переход браузера, поэтому вместо `429` он перенаправляет на `/login?error=rate_limited`. Адрес — IPv4 или сеть IPv6 /64, после прокси (`--forwarded-allow-ips`). Хранится только HMAC-SHA256 адреса с солью `APX_IP_HASH_SALT` (NFR-PRIV-01); он же записывается в `submissions.client_ip_hash`. Счётчики могут пропасть (кэш вытесняет ключи), а при недоступном `valkey-cache` запросы проходят с предупреждением в логе: эти окна не обещают пользователю точных чисел. Без `APX_CACHE_URL` (разработка) счётчики живут в памяти процесса. Код — `apparatica.core.ratelimit`, `apparatica.auth.throttle`.

**Ответ `429 RATE_LIMITED`.** В `params.quota` — какой лимит исчерпан, в `params.limit` — его значение:

| `quota` | Что исчерпано | `window_s`, `retry_after_s` |
|---|---|---|
| `checks` | проверки автора в час | да |
| `heavy` | тяжёлые проверки вошедшего в сутки | да |
| `concurrent` | одновременные проверки | нет: попытка освободится, когда закончится проверка |
| `checks_per_ip` | проверки с одного адреса | да |
| `requests` | запросы к изменяющим эндпоинтам с адреса или от автора, сохранения черновиков | да |
| `logins` | входы с одного адреса | да |
| `waveforms` | пересоздания волн в час | да |

Если `retry_after_s` есть, тот же срок в секундах приходит в заголовке `Retry-After`.

**Срок хранения.** Завершённые гостевые отправки удаляются через 14 дней вместе с артефактами (ОВ-13), отправки вошедших остаются, хэш адреса в отправке обнуляется через 30 дней (NFR-PRIV-01); сроки — в `config/retention.yaml`, удаляет ингестор ([architecture.md](architecture.md#ingest)). Черновики и история гостя остаются в браузере.

### Капча

ALTCHA (FR-GST-05, ADR-0010): задача proof-of-work без сторонних сервисов и cookie. Код — `apparatica.captcha`.

**Когда нужна.** Только гостю. С флагом `captcha` — перед каждой проверкой гостя. Без флага — когда гость или адрес уже отправили `captcha.per_guest` / `captcha.per_ip` гостевых проверок за окно (по умолчанию 3 и 10 за минуту, `config/rate-limits.yaml`). Окна — скользящие, в `valkey-cache`, как rate limit: при недоступном кэше капча не требуется. Пока окно заполнено, капчу просит каждая следующая проверка. Если капча не нужна, поле `captcha` не проверяется.

**Протокол.** На `POST /submissions` без нужной капчи — `428 CAPTCHA_REQUIRED` с `params.challenge_url` (`/api/v1/captcha/challenge`) и `params.reason`: `always` (флаг), `frequent` (частые проверки), `invalid` (решение неверное, истёкшее или уже использованное). Если капчу просят частые проверки, `params.retry_after_s` — через сколько секунд освободятся все заполненные окна и капча станет не нужна (и у `frequent`, и у `invalid` в этом случае); у `always` его нет. Клиент берёт задачу `GET /captcha/challenge`, виджет ALTCHA находит число и отдаёт решение — base64 JSON `{algorithm, challenge, number, salt, signature}` (виджет v3 добавляет `took`, сервер его не читает); клиент повторяет отправку с ним в поле `captcha`.

**Задача.** `challenge = sha256(salt + number)` в hex для случайного `number ≤ maxnumber` (`captcha.max_number`, 100 000 — доли секунды в браузере); соль заканчивается на `?expires=<unix time>` (`captcha.expires_s`, 10 минут); `signature` — HMAC-SHA256 задачи ключом `APX_CAPTCHA_KEY`. Сервер не хранит выданные задачи: решение проверяется по подписи, хэшу и сроку. Повтор закрыт окном `captcha:used:<signature>` в `valkey-cache` на срок задачи: решение принимается один раз.

## Пользователи и вход (Ф2): контракт

PR контракта Ф2 (T2.0) объявил эндпоинты Ф2. Пока задача реализации не влита, эндпоинт отвечает `501 NOT_IMPLEMENTED`, но параметры уже проверяет (`422`), а CSRF и rate limit — тоже (T2.1b). Работают выход и `GET /me` (T2.1a), вход по ссылке из письма (T2.2) и через GitHub (T2.3), черновики и статусы задач (T2.7a). Фронтенд работает с ними через моки ([frontend.md](frontend.md#моки-для-разработки)). Код — `apparatica.auth.api` и `apparatica.users.api`.

| Эндпоинт | Ответ | Реализация |
|---|---|---|
| `GET /auth/{provider}/login?next=` | `302` на страницу провайдера; в Ф2 провайдер — `github` | работает (T2.3) |
| `GET /auth/{provider}/callback` | `302`: вошёл — на `next`, не вышло — на `/login?error=<причина>` | работает (T2.3) |
| `POST /auth/email/request` | `202` без тела: письмо со ссылкой отправлено, если адрес может войти | работает (T2.2) |
| `POST /auth/email/verify` | `EmailLogin`: пользователь, `created` (аккаунт создан этим входом), `next` | работает (T2.2) |
| `POST /auth/logout`, `POST /auth/logout-all` | `204`; выход на всех устройствах без сессии — `401` | работает (T2.1a) |
| `GET /me`, `PATCH /me` | `Me`; гостю — `401 UNAUTHENTICATED` | работает (T2.1a, T2.4) |
| `DELETE /me`, `POST /me/restore` | `Me` с датой удаления `delete_at` или без неё | T2.9 |

**Провайдеры входа** — поле `auth_providers` в `GET /config`: `key`, `title` и `kind` (`oauth` — кнопка ведёт на `/api/v1/auth/{key}/login`, `email` — форма адреса). Приходят настроенные провайдеры, не выключенные флагом `auth_<key>` ([configuration.md](configuration.md#feature-flags)): `github`, если заданы ключи OAuth-приложения (`APX_GITHUB_CLIENT_ID` и `APX_GITHUB_CLIENT_SECRET`), затем `email`, если задан `APX_SMTP_URL`. Порядок — порядок кнопок страницы входа. Отдельного `GET /auth/providers` нет: фронтенд и так загружает конфиг первым.

**Сессия** (ADR-0010, FR-AUTH-04). Вход ставит cookie сессии `ap_session` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). В cookie — случайный токен (32 байта), в таблице `sessions` — только его SHA-256. Сессия живёт `APX_SESSION_TTL_S` (30 дней) с последнего использования: запрос, которому нужна сессия, продлевает её не чаще раза в час — сдвигает `expires_at` и `last_seen_at` строки и заново ставит cookie с тем же токеном. Истёкшая, неизвестная или завершённая сессия — то же, что её отсутствие: гость, а у маршрутов для вошедших — `401 UNAUTHENTICATED`. `POST /auth/logout` удаляет сессию запроса и стирает cookie; `POST /auth/logout-all` удаляет все сессии пользователя, включая текущую. Истёкшие строки удаляет ингестор ([architecture.md](architecture.md#ingest)). Найденные сессии API кэширует в `valkey-cache` на 60 с (ключ `session:<хэш>`), выход удаляет их ключи; без кэша или при его недоступности сессия читается из базы. Кэшу доверяют как базе: доступ к `valkey-cache` есть только у `api` и `ingest`. Создают сессии входы (по ссылке — T2.2, через провайдера — T2.3), код — `apparatica.auth.sessions`.

**CSRF** (NFR-SEC-05, ADR-0010) проверяет middleware `apparatica.auth.csrf` у всех изменяющих запросов (`POST`, `PUT`, `PATCH`, `DELETE`), в том числе у эндпоинтов Ф1 и у гостей. Запрос проходит, если:
- его `Origin` — origin сайта, то есть адрес, по которому пришёл сам запрос (сайт и API на одном origin, хост сохраняет Caddy, схему API берёт из `X-Forwarded-Proto`). Без `Origin` сравнивается origin из `Referer`; запрос без обоих заголовков — не со страницы браузера, его решает токен;
- его заголовок `X-CSRF-Token` равен cookie `ap_csrf` (double submit): страница чужого сайта не прочтёт cookie и не поставит заголовок без preflight CORS, а CORS API не разрешает.

Иначе — `403 CSRF_FAILED`. Cookie `ap_csrf` — случайный токен (32 байта) без `HttpOnly`, со `SameSite=Lax`, на год; её ставит любой ответ API на запрос без действительной cookie, в том числе ответ `CSRF_FAILED`. Клиент сайта (`browserApi`) копирует cookie в заголовок и повторяет отказанный запрос один раз, если отказ принёс новый токен ([ниже](#клиент-во-фронтенде)). Токен принадлежит браузеру, а не сессии: вход и выход его не меняют. Swagger UI (`/api/v1/docs`) заголовок не ставит: его изменяющие запросы получают `CSRF_FAILED`.

**Роли** (FR-AUTH-07): `user` (по умолчанию), `author` — автор задач, `moderator`, `admin`; у гостя роли нет. Маршрут для ролей объявляет зависимость `require_role(...)` (`apparatica.auth.roles`): без сессии — `401 UNAUTHENTICATED`, с другой ролью — `403 FORBIDDEN`; администратору доступно всё. Роль читается из `users` при каждом таком запросе, поэтому изменение действует сразу. Роль меняет администратор: до админки (T3.12) — командой `apparatica-admin users set-role <ник> <роль>` ([development.md](development.md#пользователи)), так назначается и первый администратор.

**Первый вход** (FR-AUTH-02) создаёт аккаунт и вход (`identities`: провайдер и его идентификатор пользователя, у почты — адрес). Аккаунт ищется по входу, а не по почте: вход через GitHub с тем же адресом — другой аккаунт (ADR-0010). Ник нового аккаунта берётся у провайдера (логин GitHub в нижнем регистре, не длиннее 24 символов); если он занят или короче 3 символов — с суффиксом из дефиса и 4 случайных символов `a-z 0-9` (`ada-x7k2`). Ник аккаунта, созданного входом по почте, случайный — `user-` и 6 символов (`user-k3f9qz`): адрес почты не публичен, а ник виден в профиле. Сменить ник можно в настройках (`PATCH /me`, ниже). Ник, имя и аватар провайдера берутся только при создании аккаунта: следующие входы их не меняют.

**Согласие** (FR-AUTH-06). Отдельного шага регистрации нет: страница входа говорит, что, продолжая, пользователь принимает соглашение и политику (макет `Login`). Первый вход записывает в `consents` текущие редакции обоих документов из `config/legal.yaml`; они попадают в экспорт (`consents`). Редакции и оператор приходят сайту в `GET /config` (`legal`: `draft`, `operator`, `versions`), подробнее — [legal.md](legal.md).

**`next`** — путь сайта, куда вернуться после входа: начинается с `/`, но не с `//` или `/\`, без пробелов. Адрес другого сайта — `422`.

**Вход через провайдера** — переходы браузера, а не запросы `fetch`: кнопка ведёт на `/api/v1/auth/github/login?next=…`. Ошибки колбэка — тоже переход, на `/login?error=<причина>`:

| `error` | Что случилось |
|---|---|
| `access_denied` | пользователь отказался на странице провайдера |
| `invalid_state` | вход устарел или начат в другом браузере (нет или не совпал `state`) |
| `provider_error` | провайдер не ответил или ответил ошибкой |
| `rate_limited` | с адреса слишком часто начинают вход (`logins_per_ip`, [выше](#авторы-и-лимиты)) |

Неизвестный или выключенный провайдер — `404 NOT_FOUND`.

**Как устроен вход** (FR-AUTH-01, ADR-0010, код — `apparatica.auth.oauth`). `GET /auth/github/login` перенаправляет на страницу GitHub со случайным `state` и PKCE (`S256`). `state`, `code_verifier` и `next` ждут возврата в cookie `ap_oauth` (`HttpOnly`, `SameSite=Lax`, 10 минут, `Path` — путь колбэка). GitHub возвращает браузер на колбэк `<APX_PUBLIC_BASE_URL>/api/v1/auth/github/callback` (этот адрес указывается в настройках OAuth-приложения) с кодом. `state` запроса должен совпасть со `state` cookie: колбэк чужого входа, открытый в другом браузере (login CSRF), и вход старше 10 минут дают `invalid_state`. Колбэк стирает cookie при любом исходе, повторить вход — начать его заново. Код и `code_verifier` API меняет на токен доступа, токеном читает `GET /user`. Токен не хранится. Таймаут запросов к провайдеру — `APX_OAUTH_TIMEOUT_S`.

Вход не запрашивает scope: GitHub спрашивает доступ только к публичным данным, и API получает только их (NFR-PRIV-01, NFR-PRIV-05). Из ответа берутся `id` — ключ входа (`identities.subject`, логин GitHub можно сменить), логин — для ника, имя (`display_name`, до 60 символов), `avatar_url` и публичный адрес почты, если он есть. Вход через провайдера ставит cookie новой сессии и завершает прежнюю сессию этого браузера, как вход по ссылке. Лимит `logins_per_ip` считает начала входов; колбэк без своего `state` до GitHub не доходит.

**Вход по ссылке** (FR-AUTH-05, код — `apparatica.auth.email_login`). Работает, если задан почтовый сервер (`APX_SMTP_URL`) и включён флаг `auth_email`; иначе оба эндпоинта отвечают `404 NOT_FOUND` ([configuration.md](configuration.md#переменные-окружения)). `POST /auth/email/request` всегда отвечает `202`: ответ не выдаёт, есть ли аккаунт, — первый вход по ссылке его создаёт. Письмо уходит после ответа, поэтому время ответа не зависит от почтового сервера; не ушедшее письмо видно только в логе и в метрике `apparatica_mail_letters_total{result="failed"}`. Лимиты — `429 RATE_LIMITED` с `quota: logins`: на IP (`logins_per_ip`) и на адрес почты (`logins_per_email`, 5 писем в час, кто бы их ни запрашивал); адрес сравнивается без учёта регистра. Капча (`428 CAPTCHA_REQUIRED`, поле `captcha`, как у отправок) — только с флагом `captcha`: частые запросы ограничивают лимиты, а не капча.

Ссылка в письме — `<APX_PUBLIC_BASE_URL>/login/email/verify#token=<token>`: адрес сайта берётся из настройки, а не из `Host` запроса, иначе запрос с чужим `Host` отправил бы жертве ссылку на чужой сайт. Токен во фрагменте не попадает в логи сервера и в `Referer`, а страница сайта (`/login/email/verify`, [frontend.md](frontend.md#вход)) сама отправляет его в `POST /auth/email/verify`, поэтому превью ссылки в почтовом клиенте или мессенджере токен не тратит. Токен — 32 случайных байта, в таблице `email_tokens` — его SHA-256, адрес и `next`. Токен одноразовый, действует 15 минут; неизвестный, использованный или истёкший — `400 LOGIN_LINK_INVALID`. Вход по ссылке ставит cookie новой сессии и завершает прежнюю сессию этого браузера, если она была; истёкшие токены удаляет ингестор.

**Аккаунт** (FR-AUTH-02, код — `apparatica.auth.accounts`). `PATCH /me` меняет ник и отображаемое имя: отсутствующее поле не меняется, `display_name: null` убирает имя. Пробелы по краям имени отбрасываются, имя из одних пробелов — `422`. Ник — 3–24 символа `a-z 0-9 _ . -`; занят — `409 NICK_TAKEN`. Ник меняется не чаще раза в 30 дней — `409 NICK_CHANGE_TOO_SOON` с `params.available_at`; то же время — в `Me.nick_change_available_at`, `null` — сменить можно сейчас. Отсчёт идёт от последней смены (`users.nick_changed_at`): ник, полученный при создании аккаунта, не считается, поэтому случайный ник входа по почте можно сменить сразу. Тот же ник — не смена. Старый ник освобождается сразу; служебные ники не зарезервированы. Запрос, в котором ник отклонён, не меняет и имя.

**Удаление** (FR-USR-05). `DELETE /me` отвечает `202` с `Me`, где `delete_at` — через 7 дней; повтор дату не сдвигает. Профиль сразу скрывается (`GET /users/{nick}` — `404`), сессии остаются, чтобы удаление можно было отменить в настройках: `POST /me/restore` обнуляет `delete_at`. В срок персональные данные удаляются, публичные решения анонимизируются (ОВ-12).

**Экспорт** — `GET /me/export`: один JSON (`format: apparatica-export/1`) вложением (`Content-Disposition: attachment`) с профилем, входами, согласиями, хранящимися отправками с кодом и черновиками.

**Черновики** (FR-EDT-02) — по одному на задачу: код и версия задачи, для которой он написан, и время сохранения `updated_at` (время сервера). `PUT` сохраняет черновик опубликованной задачи, последнее сохранение выигрывает; код больше лимита решения — `413 CODE_TOO_LARGE`, нет задачи — `404`. У сохранения своё окно rate limit ([выше](#авторы-и-лимиты)). Оба ответа — `private, no-store`. Код — `apparatica.users.drafts`, таблица `drafts`.

**Статусы задач** (FR-CAT-03, FR-USR-06). В `GET /problems` у задачи есть `status` (`solved`, `attempted`, `not_started`), а в `progress` — `solved` по уровню (среди опубликованных задач уровня, без учёта фильтров); у гостя оба равны `null`, его статусы хранит браузер. Фильтр `status` (любой из перечисленных) — для вошедших, гостю — `401 UNAUTHENTICATED`. Ответ вошедшему зависит от пользователя и отдаётся как `private, no-store`, гостю — как раньше, публичным; оба несут `Vary: Cookie`, чтобы браузер не показал после входа гостевой ответ из кэша. Статус ведёт ингестор в таблице `user_problem_status` в той же транзакции, что и вердикт ([architecture.md](architecture.md#ingest)): любая завершённая проверка — `attempted`, принятый Submit — `solved` с временем первого решения `first_solved_at`; решённая задача остаётся решённой. Правила те же, что у истории гостя в браузере. Код — `apparatica.problems.progress`.

## Клиент во фронтенде

`web/src/lib/api/client.ts` создаёт типизированный клиент `openapi-fetch` по типам из `schema.d.ts`:

```ts
import { createApiClient } from "./lib/api/client"; // путь от web/src

const api = createApiClient();
const { data, error } = await api.GET("/api/v1/problems/{slug}", {
  params: { path: { slug: "sync-fifo" } },
});
// data — ProblemDetail, error — ApiError (problem+json)
```

Пути в схеме начинаются с `/api/v1`, поэтому `baseUrl` — origin API; пустая строка означает тот же origin, что у сайта. Готовые клиенты: `browserApi` (`browser.ts`) — для браузера, на origin сайта; он ставит изменяющим запросам заголовок `X-CSRF-Token` из cookie `ap_csrf` и один раз повторяет запрос, получивший `CSRF_FAILED` вместе с новым токеном (`csrf.ts`, [выше](#пользователи-и-вход-ф2-контракт)); `serverApi` (`server.ts`) — для серверных компонентов Next.js, по переменной окружения `API_URL` (в стенде `http://api:8000`, без неё — `http://localhost:8000`): сервер ходит в API напрямую, а не через Caddy. Схемы доступны как `Schemas["ProblemDetail"]`, ошибка — `ApiError`, коды — `ErrorCode`.
