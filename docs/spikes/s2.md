# S2. Сборка Verilator в песочнице gVisor

- Дата: 2026-10-25
- Вопрос ([spikes-and-risks.md](../../specs/plan/spikes-and-risks.md)): работает ли gVisor на VPS AEZA целевой конфигурации и сколько стоит Run на FIFO: runc против runsc, с предсобранным рантаймом и без, `--trace-fst` и `--x-initial unique`, `-j`, уровень оптимизации; CPU-секунды на проверку.
- Критерий успеха: Run p50 < 10 с на 2 vCPU под gVisor; цифры CPU-секунд для бюджета.
- Итог: **критерий выполнен с большим запасом** — Run p50 **3,1 с** под gVisor (`systrap`), 3,1 CPU-секунды на проверку. Риски R2 и R3 сняты для задач уровня FIFO.
- Стенд: ветка `spike/s2-gvisor-verilator`, каталог `spikes/s2-gvisor-verilator/` (в основную ветку не переносится).

## Условия

VPS AEZA (Нидерланды) — сервер будущего воркера: Debian 13, ядро 6.12, 4 vCPU AMD Ryzen 9 7950X3D, 8 ГБ. Вложенной виртуализации нет (`vmx`/`svm` и `/dev/kvm` отсутствуют), поэтому gVisor работает на платформе `systrap` — платформа `kvm` недоступна.

Установлено: Docker CE 29.9 из репозитория Docker, gVisor `release-20261019.0` из репозитория gVisor; `runsc install` добавил рантайм `runsc` в `/etc/docker/daemon.json`. Cgroup v2, драйвер systemd. Образ тулчейна профиля `2026.10.1` (GHCR-пакет приватный — образ передан `docker save | ssh docker load`).

Каждый повтор делает то, что будет делать оркестратор: создаёт контейнер с флагами specs/07 §5.1 (`--cpus=2`, `--memory=2g`, `--read-only`, tmpfs, `--network=none`, `--cap-drop=ALL`, `--pids-limit=256`), загружает файлы через `docker exec -i … tar -x` (`docker cp` в tmpfs не пишет), выполняет этапы через `docker exec` и удаляет контейнер. Этапы: precheck (прототип S7 на pyslang), lint (`verilator --lint-only -Wall`), сборка (`apx-verilate`), симуляция (тестбенч S5, случайные push/pop, 3000 тактов). Решение — FIFO 16×8 из корпуса S7. Время — с хоста, от создания до удаления контейнера; CPU — `usage_usec` cgroup контейнера (с Sentry gVisor).

## Результаты

Полный Run, 7–9 повторов на конфигурацию:

| Конфигурация | Run p50 | Run max | Сборка p50 | CPU на Run (хост) |
|---|---|---|---|---|
| runc | 2,22 с | 2,42 с | 1,53 с | 1,9 с |
| **runsc (systrap) — целевая** | **3,06–3,15 с** | 3,25 с | 2,2 с | **3,1 с** |
| runc, рантайм Verilator компилируется | 5,9 с | 6,7 с | 5,2 с | — |
| runsc, рантайм Verilator компилируется | 7,7 с | 8,4 с | 6,8 с | 13,8 с |
| runsc, без `--trace-fst`, рантайм компилируется | 5,9 с | 6,2 с | 5,0 с | — |
| runsc, `-j1` | 3,14 с | 3,30 с | 2,2 с | — |
| runsc, `OPT_FAST=-O0` | 2,96 с | 3,07 с | 2,05 с | — |
| runsc, `OPT_FAST=-O2` | 3,44 с | 3,63 с | 2,54 с | — |
| runsc, без `--x-assign/--x-initial unique` | 3,16 с | 3,23 с | 2,2 с | — |

|---|---|---|

## Выводы

1. **gVisor на AEZA работает** на `systrap` без вложенной виртуализации. Его цена — около +0,9 с на Run (+40 % к runc), почти целиком в сборке C++ (файловые и процессные системные вызовы). Исполнение симуляции не замедляется: длинный прогон под runsc идёт так же быстро, как под runc.
2. **Предсобранный рантайм Verilator (T0.3) — главная оптимизация**: 7,7 → 3,1 с и 13,8 → 3,1 CPU-секунды на Run. Без него критерий тоже выполнялся бы, но с вчетверо большим расходом CPU.
3. **`-j` не нужен**: с предсобранным рантаймом компилируется одна единица трансляции модели, `-j1` и `-j2` равны. Этапу `sim` достаточно `-j 1` — второй CPU остаётся параллельному слоту.
4. **`-O0` экономит 0,2 с сборки**, но замедлит длинные симуляции; `-O2` дороже на 0,3 с. Оставляем умолчание Verilator (`-Os`). `--x-assign/--x-initial unique` на время сборки не влияет.
5. **Трасса FST** вкомпилирована всегда (ADR-0004); её стоимость в сборке модели с предсобранным рантаймом отдельно не мерилась — с компиляцией рантайма разница 1,8 с приходится в основном на сам рантайм FST, который теперь в образе.
6. **Два слота на 4 vCPU** друг другу почти не мешают (+0,2 с к Run). Пропускная способность одного воркера — порядка 2 Run / 3,3 с ≈ 35 Run в минуту; прогноз ОВ-8 (тысячи проверок в месяц, единицы в минуту в пике) покрывается одним VPS с огромным запасом.
7. **Бюджет:** ~3 CPU-секунды на Run. Submit добавит полный набор тестов, синтез и симуляцию нетлиста (Ф3) — его стоимость нужно измерить в T3.1b; квоты `config/limits.yaml` защищают от злоупотреблений, а не от нехватки мощности (specs/09 §3).

## Рекомендации

- T0.9: `-j 1` по умолчанию в конфиге этапа `sim`; `OPT_FAST` не менять.
- T1.2a/T1.23: рантайм `runsc` с платформой `systrap` (умолчание gVisor), Docker с драйвером cgroup systemd; загрузка файлов в контейнер — потоком tar через `exec` (`docker cp` не пишет в tmpfs); учёт CPU отправки — `usage_usec` cgroup контейнера (включает Sentry).
- Образ тулчейна в GHCR сейчас приватный: для воркеров сделать пакет публичным или выдать токен на чтение (T1.23).
- Регрессия производительности: повторить этот замер на каждом новом профиле тулчейна и версии gVisor.
