# ADR-0006. Формула и хранение рейтингов

- Статус: Принято (ОВ-3а, ОВ-4 — решения заказчика, 2026-10-24)
- Дата: 2026-10-24
- Связано: бриф §2.1, §5.3, §7.2; FR-LB-*

## Контекст
Рейтинг решений задачи сортируется по метрике задачи (по умолчанию: задержка → площадь → время отправки), одна запись на пользователя, совпадающие по AST решения группируются с приоритетом раннего автора. Метрики сравнимы только в пределах профиля тулчейна. Бриф предлагает считать рейтинги в Redis sorted sets.

## Решение
**Рейтинг решений задачи**
- Ключ рейтинга: `(problem_id, leaderboard_epoch, toolchain_profile_id, formula_version)`; показывается профиль по умолчанию и текущая эпоха.
- Формула — лексикографический порядок `leaderboard.order` из `problem.yaml`. Решения с равными значениями всех метрик делят одно место (стандартное соревновательное ранжирование: 1, 2, 2, 4; решение ОВ-3а о равных метриках); внутри места строки упорядочены по времени отправки. Значения хранятся в `leaderboard_entries.sort_values numeric[]`; Postgres сравнивает массивы лексикографически, индекс покрывает сортировку.
- Метрики округляются до точности инструмента перед сравнением (задержка — 1 пс, площадь — 0,01 µm²), чтобы шум не создавал ложных различий.
- В режиме «Практика» предупреждения линта на место **не влияют**. В индустриальном режиме (Ф7) у рейтинга своя формула: по умолчанию первый ключ — число предупреждений строгого линта (меньше — выше), затем метрики синтеза (решение ОВ-3а).
- Группировка: ведущая запись группы — самая ранняя с данным `ast_hash`; остальные получают `group_leader_entry_id` и не занимают места. Санкций нет.
- Места (`rank`, функция `RANK()`) пересчитываются ингестором одним SQL-запросом с оконной функцией при каждом принятом Submit задачи (сотни–тысячи строк — миллисекунды). Ответы API кэшируются в valkey-cache с инвалидацией по задаче.

**Общий рейтинг пользователей**
- Очки по формуле из конфига с версией: Easy 1, Medium 3, Hard 6 за решённую задачу + 3/2/1 за 1–3 место в рейтинге задачи (решение ОВ-4); при общем месте бонус получают все его участники.
- `user_ratings` в Postgres — источник правды; Redis sorted set `rating:global:<formula>` (score = очки, при равенстве — раньше достигший) для быстрых «позиция N из M» и «вокруг меня»; восстанавливается из БД командой.

**Отличие от брифа:** для рейтинга задачи Redis sorted sets не используются: многоуровневый лексикографический ключ и группировка плохо ложатся на один `double`-score, а объёмы малы. Решение пересматривается при нагрузочном тесте (Ф6).

## Последствия
- Изменение формулы задачи = новый `formula_version`, рейтинг пересчитывается, старый сохраняется.
- Смена профиля тулчейна требует rejudge (09 §2) перед переключением.

## Альтернативы
- Взвешенная оценка (например, `delay × area`) — одно число, но произвольные веса и непрозрачность для новичка; можно ввести как другую формулу задачи.
- Redis sorted sets с упакованным score — быстрее на больших объёмах, но хрупко и требует ограничений на диапазоны метрик.
