# Судья: ядро пайплайна

Как устроено ядро судьи `judge.core`: этапы, исполнители, события, лимиты, вердикт. Требования и целевое поведение — [specs/07](../specs/07-judge-pipeline.md); граница с языковыми модулями — [ADR-0011](adr/0011-language-module-boundary.md). Один и тот же код исполняет проверку в CLI `judge`, в CI и в воркере.

## Части

| Модуль | Что делает |
|---|---|
| `judge.core.stage` | протокол `Stage`, `StageContext`, `StagePlan`, `ExecResult`, `StageOutcome`, `StageResult` и общие модели: диагностика, тест-кейс, сводка этапа |
| `judge.core.pipeline` | `run_pipeline`: этапы `pipelines.practice.<kind>` по порядку, ранняя остановка, отмена |
| `judge.core.executor` | `ContainerExecutor` (контейнер песочницы через интерфейс `Container`), `LocalDockerExecutor` (он же через docker CLI), `HostExecutor` (подпроцессы на хосте); лимиты времени и вывода, отмена |
| `judge.core.jobs` | задание проверки для очереди (`JudgeJob`), имя актора и очередей: общий контракт API и воркера ([architecture.md](architecture.md#очередь-проверок)) |
| `judge.core.events` | события пайплайна и приёмники: `ConsoleSink`, `JsonlSink`, `FanoutSink` |
| `judge.core.limits` | лимиты песочницы и этапов: класс ресурсов из `config/resource-classes.yaml`, переопределения из `problem.yaml` |
| `judge.core.verdict` | `aggregate`: итоговый статус отправки по результатам этапов (specs/04 §3.3) |
| `judge.core.leaderboard` | `leaderboard_metrics`: попадает ли Submit в рейтинг задачи и с какими метриками формулы (FR-LB-02, FR-JDG-13) |
| `judge.core.registry` | языковые модули по ключу `language` через entry points; у модуля — плагины этапов, этапы проверки шаблона, шаблон пакета и правила пакета (`package_rules`) |

Ядро не импортирует `judge.languages` (контракт import-linter): языковой модуль регистрируется в `pyproject.toml` судьи в группе entry points `apparatica.judge.languages` и отдаёт `LanguageModule` — имя и плагины этапов по типу. Модуль `systemverilog` зарегистрирован, в нём этапы `precheck`, `lint`, `sim` и `synth` (ниже).

## Этап

Этап — класс с атрибутами `stage_type` (значение `type` в `stages.<key>`), `config_model` (Pydantic-модель остальных полей `stages.<key>`), `metrics_schema` и двумя методами:

1. `plan(ctx) → StagePlan` — что выполнить: команды, входные файлы (`executable` — какие из них записать исполняемыми), какие файлы забрать после, таймаут и лимит вывода (обычно из `ctx.limits`), фильтр строк вывода, строка `note` для консоли (канал `sys`) перед командами, `cache` — план детерминирован и его прогон можно взять из кэша (ниже).
2. `interpret(ctx, runs) → StageOutcome | StagePlan` — решение по результатам прогонов: статус, `failure_kind`, вид лимита, метрики, сводка, файлы для следующих этапов (`outputs`). Вернуть ещё один `StagePlan` — попросить следующий прогон (так `sim` перезапустит бинарник с окном трассы); всего не больше 4 прогонов на этап. Первый план этапа получает чистый каталог, повторные выполняются в том же каталоге и видят оставленные файлы (`reuse_dir`), например собранный симулятор.

`StageContext` содержит ключ экземпляра этапа (`key`, ниже «Наборы параметров»), конфиг этапа, задачу, каталог пакета, вид отправки, сид, код решения, лимиты, набор параметров экземпляра (`param_set`: `id` и значение каждого параметра интерфейса; у этапа только с основным набором — основной), завершённые экземпляры с их `outputs` по ключу и кэш сборки `build_cache` (ниже). `ctx.instance(stage_key)` — ключ экземпляра другого этапа при том же наборе: так `sim` с `design` находит нетлист своего набора. Файлы между этапами передаются только через `outputs` → `inputs` следующего плана: каждый этап работает в чистом каталоге.

**Кэш сборки** (`judge.core.cache`, ADR-0003, specs/07 §2.3) — то, что этап собрал один раз, для следующих проверок того же кода: `get(key)` и `put(key, data)`, сбой — промах, а не ошибка проверки. Ключ — `plan_key(stage_type, plan)`: sha256 команд и всех входных файлов плана сборки, поэтому другие флаги, тестбенч или дизайн дают другой ключ. Тулчейн в плане не виден: ключи разделяет тот, кто даёт кэш (воркер — по профилю и образу, [architecture.md](architecture.md#кэш-сборки)). Этап, взявший результат из кэша, ставит `StageOutcome.cached`, и он попадает в `StageResult.cached`. `judge run` и `validate` кэша не имеют (`NoCache`).

**Кэш детерминированных планов** (FR-JDG-11) — тот же кэш, но им распоряжается пайплайн, а не этап. План с `cache = true` обещает, что всё, что он читает, названо в его командах и входных файлах, а прогон не оставляет в каталоге этапа ничего для следующих планов. Перед запуском пайплайн ищет `plan_key` такого плана: при попадании прогон не выполняется, а восстанавливается из кэша (`ExecResult.cached`) — коды выхода команд, вывод консоли и забранные файлы; в консоль идут строка `result from the cache: this code was checked earlier on this toolchain` и сохранённый вывод (канал `out`), а этап разбирает прогон как обычно, и у него `cached = true`. Свежий прогон попадает в кэш, только если этап закончился тем, что этот код получит всегда: `passed`, `warning` или `failed` не по лимиту. Лимиты зависят от песочницы, ошибки — от платформы, такие прогоны не кэшируются, как и прогоны, остановленные по времени, выводу, отмене или памяти. Запись в кэше — JSON со строгой схемой (`_StoredRun`, файлы в base64, не больше 32 МиБ); испорченная запись — промах. Так кэшируется `synth`.

Фильтр строк (`StagePlan.line_filter`) получает каждую строку вывода и возвращает текст для консоли (или `None`, чтобы скрыть строку) и, если нужно, обновление прогресса теста — так языковой модуль разбирает строки `@@apx`, а ядро о них не знает.

## Пайплайн

`run_pipeline(job, language, executor, sink, resource_classes, cancel, build_cache=…)`:

- До запуска раскрывает этапы пайплайна в экземпляры по наборам параметров (ниже), проверяет, что у языка есть плагин для каждого `type`, валидирует конфиги этапов и число дополнительных наборов (`check_param_sets`: граница класса ресурсов могла измениться после `judge validate`); ошибка — `PipelineConfigError` (ошибка задачи, а не решения).
- Для каждого экземпляра пишет `stage_start`, выполняет планы, пишет `stage_end` с `StageResult`, в конце — `done`.
- После `failed` или `error` следующие этапы получают `skipped` с `skip_reason = previous_failed`. Отмена (`cancel`) прерывает текущую команду: этап получает `cancelled`, остальные — `skipped` с `skip_reason = cancelled`.
- Сбой исполнителя (`ExecutorError`: нет Docker, контейнер пропал) — этап `error` с кодом `EXECUTOR_FAILED`; исключение в плагине — `error` с кодом `STAGE_CRASHED`; бесконечные повторные прогоны — `STAGE_RUNS_EXCEEDED`. Текст ошибки идёт в лог этапа (канал `sys`).
- Превышение лимита вывода дополнительно даёт событие `truncated`.
- План с `cache` сначала ищется в кэше (раздел «Этап»); найденный прогон не выполняется.
- `StageOutcome.outputs` передаются следующим этапам, `StageOutcome.artifacts` — файлы для пользователя (FST, отчёты): их получает колбэк `on_artifact(key, name, data)` с ключом экземпляра — CLI сохраняет их на диск, воркер загрузит в хранилище.

**Наборы параметров** (ADR-0014, specs/07 §2). Этап с `param_sets` раскрывается в экземпляры: ключ экземпляра основного набора — ключ этапа (`synth`), дополнительного — `<ключ>@<id набора>` (`synth@narrow`); `@` в ключе этапа запрещён схемой (`[a-z][a-z0-9_]*`). Порядок — `Problem.instance_keys`: по этапам, внутри этапа основной набор, затем дополнительные в порядке `interface.param_sets`. Дальше экземпляр — обычный этап: свой `ordinal`, результат, артефакты и каталог, ранняя остановка и место в вердикте. У результата и события `stage_start` — `param_set` (`id` и значения всех параметров интерфейса), у этапа только с основным набором — `null`. Таймаут `limits.stage_timeout_s` берётся по ключу этапа и действует на каждый экземпляр. `Job.stages` — ключи экземпляров вместо пайплайна (ключ этапа — экземпляр основного набора): так воркер пересоздаёт трассу этапа по ключам из `stage_results`, а `validate` проверяет шаблон. Как подставить значения набора в инструменты, решает языковой модуль.

Вердикт пайплайн не считает: это делает тот, кто владеет итоговым статусом, — CLI или ингестор — функцией `judge.core.verdict.aggregate`. Порядок: отмена, сбой платформы, первый `failed` по порядку этапов (`failure_kind` → статус), предупреждения, `accepted`. В `detail` — первый упавший этап и тест с тактом, вид лимита, этапы с предупреждениями, коды сбоев.

Попадёт ли Submit в рейтинг задачи, решает `judge.core.leaderboard.leaderboard_metrics(problem, results)` — его часть условия FR-LB-02: у задачи есть `leaderboard`, у каждого экземпляра этапов `pipelines.practice.submit` (при каждом наборе параметров этапа) есть результат `passed` или `warning` (нет результата — не пройден) и каждая метрика `leaderboard.order` — число; метрики берутся у экземпляра основного набора, его ключ — ключ этапа. Возвращает метрики формулы `<stage>.<metric>` → значение или `None`. Для SV это и есть «пройдена симуляция нетлиста» (FR-JDG-13): `judge validate` не пропустит пакет, где за `synth` не идёт `netlist_sim`, а этапы формулы обязаны быть в `submit` (схема `problem.yaml`). Автора, эпоху и профиль тулчейна проверяет ингестор (T3.4). Там же — `sort_values(leaderboard, metrics)`: метрики в порядке формулы, у `desc` с обратным знаком, чтобы место считалось сравнением массивов по возрастанию, и `ast_hash(results)`: метрика `ast_hash` этапа языка, который её отдаёт (у SV — `precheck`), для групп совпадающих решений (FR-LB-04).

## Исполнители

Оба исполнителя выполняют команды плана по порядку до первого ненулевого кода выхода и соблюдают общие для плана правила:

- **Таймаут** `timeout_s` — на весь план, а не на команду; по истечении команда убивается, `timed_out`.
- **Лимит вывода** `output_limit` — байты строк обоих каналов; при превышении команда убивается, строки сверх лимита не передаются, `output_limited`.
- **Отмена** — проверяется каждые 50 мс; команда убивается, `cancelled`.
- **Файлы**: `inputs` записываются в каталог этапа — свежий или, с `reuse_dir`, оставшийся от прошлого прогона этого этапа; файлы из `executable` — с правами `0755`, остальные — `0644`; из `collect` читаются существующие файлы не больше `collect_limit` байт, более крупные попадают в `oversized` и не читаются. Пути — только относительные внутри каталога этапа.

`ContainerExecutor` исполняет планы одной отправки в её контейнере песочницы — один контейнер на отправку с флагами specs/07 §5.1 (`sandbox_flags`); память, CPU и число процессов берутся из класса ресурсов. С контейнером он работает через интерфейс `Container`: короткая команда без TTY (`run`), команда этапа с TTY (`start`), `kill_all`. Реализаций две: `DockerContainer` (docker CLI) для `LocalDockerExecutor` — `judge run`, `judge validate`, CI — и контейнер `apx-sandboxd` для `SandboxExecutor` воркера ([architecture.md](architecture.md#песочница-apx-sandboxd)). Поэтому `judge run` и воркер ведут себя одинаково.

- Каталог этапа — `/work/<ключ экземпляра>`, чистый для каждого этапа (кроме повторного прогона того же этапа).
- Входные файлы загружаются tar-потоком через `exec` со stdin: `docker cp` не пишет в tmpfs.
- Выходные файлы читаются через `head -c` с ограничением.
- Команды этапа идут через `exec` с TTY и `apx-run`: TTY даёт построчный вывод, `apx-run` помечает строки stderr.
- Убить клиент `exec` недостаточно, поэтому при таймауте, лимите, отмене и после каждого плана выполняется `kill -KILL -1` от пользователя песочницы: фоновый процесс этапа не доживает до следующего (S6).
- PID 1 контейнера — `apx-init` из образа: ядро не доставляет ему `kill -1`, а он забирает убитые процессы, так что зомби не занимают лимит процессов.
- Если после плана `kill` сообщает, что песочница потеряна (`SandboxLostError`), файлы не собираются. Песочница, убитая лимитом памяти (под gVisor OOM-killer забирает весь Sentry), даёт `memory_exceeded`, и конвейер завершает этап с `limit` = `memory` без интерпретации этапом. План, остановленный по времени, выводу или отмене, сохраняет свой исход. Иначе — `ExecutorError`, этап `error` ([security.md](security.md#apx-sandboxd)).

`HostExecutor` — подпроцессы во временном каталоге на хосте (`judge --no-docker`, тесты ядра). Изоляции нет; stdout и stderr читаются раздельно, на POSIX при убийстве завершается вся группа процессов.

## SystemVerilog: `precheck`

Этап `precheck` (`judge/languages/systemverilog/stages/precheck.py`, specs/07 §2.1) — первый в пайплайне. Код решения разбирает pyslang, а это код атакующего, поэтому сама проверка выполняется в песочнице:

1. План загружает в каталог этапа `solution.sv` (код пользователя как есть), `job.json` (модуль, параметры, наборы параметров — основной и дополнительные со значениями всех параметров — и порты из `problem.yaml`, лимиты из `PrecheckConfig`) и раннер `sandbox/precheck_runner.py` и запускает `python3 -I precheck_runner.py job.json solution.sv`. Раннер — один файл на стандартной библиотеке и pyslang из образа; меняется вместе с судьёй, профиль образа для этого не нужен.
2. Раннер по шагам: лимиты размера; лексер ищет директивы препроцессора (до разбора — ни одна директива не выполняется); разбор; канонический текст без комментариев (символы комментариев заменены пробелами, строки и колонки сохраняются); белый список видов узлов slang и правила поверх него; элаборация с лимитами шагов, объём состояния и интерфейс — при каждом наборе параметров пакета, основной первым (значения задачи из `problem.yaml`, а не значения по умолчанию из решения). `precheck` по наборам не раскрывается: один этап проверяет все наборы, а замечание при дополнительном наборе начинается с «при наборе параметров narrow (WIDTH=1, DEPTH=2): ». `module` и `state_bits` в метриках — основного набора; лимит состояния действует при каждом. Первый шаг (и первый набор) с замечаниями останавливает проверку. Результат — `result.json` и `canonical.sv`.
3. Судья читает оба файла как недоверенные (строгая схема `RunnerResult`, лимит размера) и решает: замечания → `failed` (`forbidden`, `compile` или `limit` с видом `size`/`memory`) с диагностиками по-русски и стабильными кодами; без замечаний → `passed`, канонический текст уходит следующим этапам как `solution.sv`, метрики `precheck/v1`: `code_hash` (sha256 канонического текста, судья считает его сам), `ast_hash` и `normalization_version` (ниже), `module`, `ports_ok`, `state_bits`. Таймаут, лимит вывода и гибель от нехватки памяти — `limit`; падение раннера без результата — `error` с `TOOL_FAILED`, неверный `result.json` — `OUTPUT_INVALID`.

Белый список видов узлов и таблица пояснений для частых запрещённых конструкций — в раннере; имена видов проверяются при загрузке модуля (`SyntaxKind.__members__[name]`), поэтому опечатка или вид, исчезнувший в новой версии slang, — ошибка импорта, а не пропущенное правило. Лимиты — поля `PrecheckConfig` (`stages.<key>` в `problem.yaml`), по умолчанию из NFR-LIM-01.

**Нормализованный AST-хэш** (specs/07 §6) считает раннер для прошедшего решения (`normalize_tokens`, `ast_hash`): поток токенов без trivia, имена модуля, портов и параметров из `problem.yaml` сохраняются, прочие идентификаторы — `_1`, `_2`, … по первому появлению, литералы с основанием свёрнуты в hex. Формат — `n<версия>:<sha256>`, версия — `NORMALIZATION_VERSION` раннера; любая правка нормализации увеличивает её, хэши разных версий не сравниваются. Хэш нужен только для группировки одинаковых решений в рейтинге и подсказки модератору; ключ кэшей — `code_hash`. Что хэш игнорирует и что различает, фиксирует `judge/tests/test_ast_hash.py`.

## SystemVerilog: `lint`

Этап `lint` (`judge/languages/systemverilog/stages/lint.py`, specs/07 §2.2) берёт канонический `solution.sv` из `outputs` предыдущего этапа (`stages/common.py`: без `precheck` перед ним этап не запускается) и выполняет `verilator --lint-only` с SARIF-выводом в файл. `LintConfig.flags` — только опции предупреждений `-W…` (по умолчанию `-Wall -Wno-UNUSEDPARAM`), `-Wno-DECLFILENAME` и `-Wno-fatal` этап добавляет сам. Консольный вывод Verilator идёт в лог этапа как есть, а решение принимается по SARIF: ошибки → `failed`/`compile`, предупреждения → `warning` (или `failed` при `warnings_fail`), иначе `passed`. В `summary.diagnostics` — до 200 диагностик (первая строка сообщения, правило, позиция в `solution.sv`), метрики `lint/v1` считают все. Verilator 5.052 пишет невалидный SARIF при пустом списке правил; `parse_sarif` вставляет пропущенную запятую ровно в этом месте и разбирает снова (фикстуры `judge/tests/data/lint/` — настоящий вывод Verilator из образа).

## SystemVerilog: `sim`

Этап `sim` (`judge/languages/systemverilog/stages/sim.py`, specs/07 §2.3) собирает и запускает тестбенч задачи. `SimConfig`: `testbench` (id из `testbenches`), `groups`, `max_cycles`, `design` (`<stage>.<output>` — симулировать выход другого этапа, например нетлист, вместо решения; берётся выход экземпляра того же набора параметров: `netlist_sim@narrow` — нетлист `synth@narrow`), `trace` и окно `trace_before`/`trace_after` (по умолчанию 64/16 тактов), `build_jobs` (по умолчанию 1).

1. Сборка: исходники тестбенча из пакета (`pkg/…`, только внутри каталога пакета), канонический `solution.sv` (или `design.v`) и одна команда — `apx-verilate` с `apx_tb_pkg` первым и флагами `-G<параметр>=<значение>` для верхнего модуля тестбенча: значения набора экземпляра, у основного набора тоже (`param_values` в `stages/common.py`; только числовые литералы). Тестбенч, у верхнего модуля которого нет `parameter` для параметра задачи (или он `localparam`), Verilator не собирает (`Parameters from the command line were not found in the design`) — это ошибка задачи: `error` с `TB_PARAMS_MISSING` и именами параметров в подписи, для решения и для нетлиста. План забирает бинарник `obj_dir/V<tb.top>` (до 32 МиБ, `BINARY_LIMIT`), и этап кладёт его в кэш сборки **до первого запуска**: прогон не может подменить то, что получат следующие проверки. Бинарник крупнее лимита не кэшируется, но запускается.
2. Прогон — второй план в том же каталоге: `obj_dir/V<tb.top>` с сидом отправки, группами, новым nonce, лимитом тактов и случайной инициализацией. Сборка и прогон делят лимиты этапа: прогон получает таймаут за вычетом времени сборки и лимит вывода за вычетом её вывода.
3. Кэш: ключ — `plan_key` плана сборки, то есть команда (с флагами `-G` набора), тестбенч и дизайн (для решения — канонический текст, его sha256 и есть `code_hash`); сид и группы — аргументы прогона, поэтому Run и Submit одного кода собирают бинарник один раз. При попадании первый план этапа — сразу прогон: бинарник из кэша записывается в чистый каталог исполняемым, в консоль идёт строка `simulator from the build cache: this code was built earlier`, а у этапа `cached = true`; время и вывод — целиком прогону.
4. Фильтр строк прогона: строки прогресса `@@apx` с nonce этого прогона становятся событиями `test`; скрытые тесты в них анонимны (`hidden-N`); служебная строка `$finish` из `apx_tb_pkg` скрыта. Событие конца теста несёт имя и группу из его начала: клиент заменяет тест по `id` целиком.
5. Итог по файлу результатов (`tbproto.parse_result`): упавший тест → `wrong`; `suite_abort` по `max_cycles` → `limit`/`cycles`; ошибка тестбенча → `error`/`TB_ERROR`; число тестов в группе не совпало с `testbenches[].groups` → `error`/`TB_GROUPS_MISMATCH`; нет итога (симуляция упала) → `wrong`; нарушение протокола → `error`/`OUTPUT_INVALID`; сборка не прошла → `compile`; таймаут, вывод, память (код 137) → `limit`. `summary.tests` — открытые тесты с расхождениями и подсказками, `summary.hidden_tests` — счётчики скрытых, метрики `sim/v1`. Файл результатов первого прогона этап отдаёт артефактом `tb_result.jsonl` (для проверки детерминизма и автору в `judge run`); в нём значения скрытых тестов, поэтому пользователю прогона со скрытыми группами он не показывается.
6. Если упал открытый тест, `interpret` возвращает ещё один план: тот же бинарник, тот же сид, `+apx_trace_from/to` вокруг первого расхождения, в том же каталоге этапа. С `StageContext.trace = full_test` (`Job.trace`, задание воркера на весь тест, `judge run --full-trace`) окно — весь упавший тест: от его `start_cycle` до такта после `end_cycle`. Совпало первое расхождение — FST уходит в `artifacts` (`trace.fst`, не больше `fst_mb`), иначе `metrics.trace = nondeterministic` и окно не показывается.
7. Записанное окно описывают метрики: `trace_window` — такты от и до, `trace_cursor_ps` — время первого расхождения в FST (`$time` проверки в пикосекундах, из файла результатов), `trace_signals` — что показать в Surfer (ADR-0004). Список строится из интерфейса задачи по соглашению тестбенча ([problem-authoring.md](problem-authoring.md#тестбенч)): такт — порты с `role: clock`, а если их нет — `clk` тестбенча; затем остальные входы; затем каждый выход и `exp_<порт>`. Имена полные: `<tb.top>.<сигнал>`. Сигнала, которого нет в FST, Surfer молча не покажет.
8. **Симуляция нетлиста** (`netlist_sim`, specs/07 §2.5): с `design: <stage>.netlist_generic` вместо решения собирается нетлист этапа `synth` (`stages/netlist.py`). Модуль нетлиста — `<top>__netlist` без параметров; этап дописывает в `design.v` обёртку `top` с параметрами и портами интерфейса (значения по умолчанию — те, с которыми шёл синтез: значения набора экземпляра, `param_values`) и для каждого параметра — `if (P != <значение>) $fatal(…)`. К сборке добавляется `-Werror-USERFATAL` сразу после `-Wno-fatal`, иначе этот `$fatal` остался бы предупреждением (S4). `design` другого этапа, не `synth`, — ошибка плана (`STAGE_CRASHED`). Сборка не прошла — ошибка задачи или платформы, а не решения: `error` с `NETLIST_PARAMS_MISMATCH` (в выводе `%Error-USERFATAL`: тестбенч задаёт другие значения параметров) или `NETLIST_BUILD_FAILED`. Упавший тест — `failed`/`wrong` с подписью «синтезированная схема ведёт себя иначе, чем исходный код: тест …, такт …» и диагностикой `info` `NETLIST_MISMATCH` с типичными причинами. Трасса не пишется. Кэш — кэш сборки: ключ включает нетлист с обёрткой, поэтому тот же код с тем же синтезом не собирается заново.

## SystemVerilog: `synth`

Этап `synth` (`judge/languages/systemverilog/stages/synth.py`, specs/07 §2.4, ADR-0007) синтезирует канонический `solution.sv` в Yosys со встроенным sv-elab и оценивает задержку в OpenSTA. Параметры синтеза — значения набора экземпляра: у `synth` — основного, то есть значения по умолчанию из `problem.yaml`, у `synth@<id>` — дополнительного (`param_values`; только числовые литералы, потому что значения попадают в скрипт Yosys). Скрипт с другими значениями — другой ключ кэша этапа. `SynthConfig`: `clock_period_ns` (по умолчанию 2,0), `forbid_latches` (по умолчанию да); поля `params` больше нет (ADR-0014). Нелитеральное значение параметра или больше одного порта с ролью `clock` — ошибка задачи (план падает, этап `error` с `STAGE_CRASHED`; `judge validate` ловит их раньше — правилами пакета и на эталонах).

1. Один план из двух команд, `cache = true`: `yosys -qq -w .* -s synth.ys` и `sta -no_init -no_splash -exit sta.tcl`. Оба скрипта этап пишет сам и кладёт во входные файлы рядом с решением, поэтому они входят в ключ кэша. `-qq -w .*` оставляют в консоли только ошибки: одного `-qq` мало — предупреждения `check` внутри `synth` печатаются по блоку на каждый бит петли и могут исчерпать лимит вывода; в отчётах `tee` они остаются строками `Suppressed Warning: …`.
2. Скрипт Yosys: `read_liberty -lib`; `read_slang --no-synthesis-define --no-default-translate-off-format` с `-G` для каждого параметра; `check` до синтеза (`check_rtl.txt`: `synth` «разрешает» конфликт драйверов константой, и после него конфликт не виден); `synth -top <top> -flatten`; число латчей (`select -count`, `latches.txt`) и их места (`printattrs`, `latch_sources.txt` — строка блока `always`); `check` после синтеза (`check.txt`: петли через вентили — на уровне слов `check` дал бы ложные петли через сумматоры); нетлист на внутренних вентилях Yosys с модулем `<top>__netlist` (`netlist_generic.v`); `dfflibmap` и `abc` на Nangate45, `hilomap`, `splitnets -ports`, `opt_clean -purge`; `stat -liberty -json` (`stat.json`); `ltp -noff` без триггеров liberty (`ltp.txt`); нетлист ячеек для OpenSTA (`netlist.v`, не забирается).
3. Скрипт OpenSTA: клок с периодом `clock_period_ns` на порт с ролью `clock`, без такого порта — виртуальный; задержки входов и выходов 0, `set_driving_cell BUF_X1` на входы данных, нагрузка выходов — ёмкость `DFF_X1/D`; отчёт о худшем пути идёт в консоль, худший слэк — в `sta.json`. Библиотека и ограничения — `Liberty` (`NANGATE45`): путь, ячейки констант, ведущая ячейка, вывод нагрузки и шаблоны имён триггеров (`DFF*`, `SDFF*` — ровно ячейки с группой `ff`, это проверяет тест образа).
4. Разбор (все файлы недоверенные, каждый до 16 МиБ): таймаут и вывод → `limit`; код выхода 137 → `limit`/`memory`; Yosys упал с сообщениями `ERROR:` → `compile` с диагностиками `SYNTH_ERROR` (место в `solution.sv`, если оно есть; общая строка «Design elaboration failed» отбрасывается, когда есть конкретные); упал без сообщений → `error`/`TOOL_FAILED`. Затем, до результатов OpenSTA: латчи при `forbid_latches` → `LATCH` по одной диагностике на блок; петли при `forbid_latches` → `LOGIC_LOOP` по одной на сигнал со строкой его объявления; конфликт драйверов → `MULTIPLE_DRIVERS` всегда; отчёт `check` больше лимита → `SYNTH_CHECK`. Всё это — `failed`/`compile` с подписью «латчи в схеме», «комбинационная петля» или «решение не синтезируется». OpenSTA упал → `TOOL_FAILED`; нетлист больше лимита → `limit`/`output`; файл не по формату → `error`/`OUTPUT_INVALID`.
5. Метрики `synth/v1`: `critical_path_ns = clock_period_ns − WNS` (0 — путей нет: OpenSTA отдаёт огромный слэк), `fmax_mhz = 1000 / critical_path_ns` только при порте `clock`, `area_um2` (пустой дизайн — 0), `cells`, `flops`, `latches`, `logic_depth`, `liberty` (`nangate45`) и `cells_by_type`. Задержка округлена до 1 пс (`DELAY_DIGITS`), площадь — до 0,01 мкм² (`AREA_DIGITS`), частота считается по округлённой задержке: точнее инструмент не различает, и рейтинг сравнивает те же числа, что видит пользователь (ADR-0006). Подпись блока — «0,246 нс, 36,18 мкм², ячеек 23». `outputs.netlist_generic` — вход этапа `netlist_sim` (`design: synth.netlist_generic`, раздел `sim`). Артефактов (нетлисты, отчёты) этап пока не отдаёт.

Под TTY этапа Yosys раскрашивает сообщения ANSI-кодами: фильтр строк убирает их из консоли вместе с хвостом «; see full log for details» (лога Yosys этап не хранит), разбор ошибок — тоже без них.

## События

События — те же, что в стриме отправки воркера (specs/07 §4.1), без поля `attempt`: `stage_start`, `log` (`ch`: `out`, `err`, `sys`; одна строка без перевода строки), `heartbeat`, `test`, `truncated`, `stage_end`, `done`. Пайплайн сам не шлёт `heartbeat`: его шлёт приёмник воркера, пока этап молчит. `ConsoleSink` печатает события для человека (в заголовке экземпляра с набором — значения параметров: `── sim_full@narrow · WIDTH=1, DEPTH=2`), `JsonlSink` пишет по событию в строке (`events.jsonl`), `FanoutSink` раздаёт нескольким приёмникам. Приёмник Valkey Stream — в воркере (Ф1). Что воркер добавляет к событиям в стриме отправки — [api.md](api.md#события-проверки).

## Лимиты

`config/resource-classes.yaml` задаёт для каждого класса ресурсов (`light`, `heavy`; NFR-LIM) CPU, память, число процессов, лимит вывода, размер FST, таймауты этапов по типу, таймаут по умолчанию, верхнюю границу таймаута и `max_param_sets` — сколько дополнительных наборов параметров может объявить задача (ADR-0014). `limits` в `problem.yaml` переопределяют память, вывод, FST и таймауты по ключу этапа; таймаут выше границы класса — ошибка. `sandbox_limits` даёт лимиты контейнера, `stage_limits` — лимиты этапа по его ключу (`ctx.limits`, одни на все экземпляры), `check_param_sets` проверяет число наборов (его вызывают `judge validate` и `run_pipeline`), `check_timeout_s` — лимит попытки: сумма таймаутов этапов пайплайна, каждого столько раз, сколько у него наборов, плюс 30 с.

## CLI: validate, run, pack, new

`judge/src/judge/cli.py` собирает исполнитель (`LocalDockerExecutor` с лимитами класса ресурсов задачи или `HostExecutor` с `--no-docker`) и вызывает части ядра:

- **`validate`** — `judge.core.validate.PackageValidator`. Первые три проверки останавливают проверку пакета: схема `problem.yaml`; языковой модуль, плагины и конфиги этапов, лимиты и число наборов параметров класса ресурсов, правила пакета языка (`LanguageModule.package_rules`; для SV — `judge/languages/systemverilog/rules.py`: за каждым `synth` в `submit` идёт `sim` с `design: <synth>.netlist_generic`, а `design` берёт нетлист этапа `synth`, который идёт раньше в том же пайплайне, и только при наборах параметров, которые есть у этого `synth`; у `precheck` нет `param_sets`; значения по умолчанию и значения наборов — числовые литералы); файлы манифеста существуют внутри пакета. Дальше: условие в UTF-8 и рендерится так же, как на сайте (`judge.core.statement`): с `--statement-check COMMAND` (или `JUDGE_STATEMENT_CHECK`) validate запускает `COMMAND <каталог пакета> <файлы условия>`; команда печатает по проблеме на строку и выходит с 0 (всё рендерится), 1 (проблемы — проверка `FAIL` со списком) или другим кодом (не запустилась — тоже `FAIL`). В репозитории команда — `pnpm -C web --silent statement:check` (`web/scripts/statement-check.ts`: KaTeX, WaveDrom, картинки из `assets/`, [frontend.md](frontend.md#условие-задачи)); её передают `just validate-problems` и CI. Без опции рендер не проверяется (строка `--`); шаблон проходит экземпляры этапов `LanguageModule.template_checks` (для SV — `precheck`), запущенные через `Job.stages`; каждый эталон — `accepted` на `--seeds` сидах (по умолчанию 3) при всех экземплярах этапов `submit` — так же ловится `tb_top` без `parameter` для параметров задачи (`TB_PARAMS_MISSING`, specs/06 §3.1); каждый мутант — вердикт `expect` на первом сиде от этапа из `caught_by` или более раннего в `submit` (FR-PKG-02; экземпляр при любом наборе засчитывается своему этапу). С `--determinism` (так запускает CI) первый прогон каждого эталона повторяется с тем же сидом: результаты этапов без времени (`started_at`, `duration_ms`) и артефакты должны совпасть побайтно; FST не сравнивается — в его заголовке дата (ADR-0004). Для SV в артефактах — `sim/tb_result.jsonl`, поэтому сравнение побайтное по протоколу тестбенча, как требует specs/07 §7. Каждый прогон — отдельный контейнер, как у настоящей отправки. Сиды — первые 8 байт `sha256("<id>@<version>#<n>")`, сдвинутые до 63 бит.
- **Число тестов в группах** проверяет сам этап `sim`: в законченном прогоне (`suite_end`) тесты каждой выбранной группы, включая пропущенные, должны совпасть с `testbenches[].groups`, иначе `error` с `TB_GROUPS_MISMATCH` и подписью вида «в группе hidden тестов: 1, в problem.yaml: 2». Неверное число ловит прогон эталона в `validate`.
- **`run`** — `run_pipeline` с `ConsoleSink` и `JsonlSink`, артефакты через `on_artifact` в `out/<stage>/`, вердикт — `aggregate`, строка причины — `validate.describe`.
- **`pack`** — `judge.core.pack`: файлы пакета по пути (без файлов и каталогов на `.` и `__pycache__`, символические ссылки — ошибка), `content_hash` — sha256 списка в формате `sha256sum`, архив — PAX tar с mode 0644, mtime 0 и без имён владельцев, сжатый zstd (уровень 19): одинаковые файлы дают одинаковые байты.
- **`new`** — `judge.core.scaffold`: копия `LanguageModule.package_template` с подстановкой `__slug__`, `__top__` (slug через `_`, с префиксом `m_`, если начинается с цифры) и `__number__` (следующий номер среди пакетов каталога). Шаблон SV — `judge/languages/systemverilog/package_template/`: регистр с синхронным сбросом, модель, тестбенч на `apx_tb_pkg` (2 открытых теста и 1 скрытый), наборы параметров `narrow` и `wide` у симуляции, синтеза и симуляции нетлиста, рейтинг по задержке и площади, эталон и четыре мутанта: один ловят только скрытые тесты, другой (жёстко заданная разрядность) — только набор `wide`; пакет проходит `judge validate` как есть.
