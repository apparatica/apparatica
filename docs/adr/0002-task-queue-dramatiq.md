# ADR-0002. Очередь проверок: Redis + Dramatiq

- Статус: Принято
- Дата: 2026-10-24
- Связано: бриф §5.2, §7.2; 07 §3; NFR-REL-01

## Контекст
Нужны подтверждения, ретраи, таймауты, dead-letter, несколько очередей (`judge.light`, `judge.heavy`), обнаружение умерших воркеров. Задача воркера — долгие блокирующие подпроцессы (сборка Verilator, Yosys), а не асинхронный ввод-вывод. Отмена и позиция в очереди нужны продукту.

## Решение
Dramatiq ≥ 2.2 (в 2.0 несовместимо изменён Redis-брокер) с `RedisBroker` на отдельном инстансе `valkey-queue` (`noeviction`, AOF).
- Актор `judge_submission(submission_id, payload)`, очередь по `resource_class`. Один пул воркеров слушает обе очереди; выделение пула под `heavy` — конфиг деплоя (`--queues judge.heavy`).
- Актор `judge_waveform(waveform_id, payload)` (T1.17a) — пересоздание FST завершённой проверки (FR-WAV-05) в тех же очередях и слотах, с теми же правилами: без повторов, аренда и попытки по id заявки.
- **Один владелец перезапуска.** Подтверждение после завершения; перепостановку сообщений умерших воркеров выполняет только брокер (heartbeats). Middleware `Retries` выключен (`max_retries=0`), watchdog ингестора ничего не перепоставляет. Дубли отсекаются арендой `lease:<id>` (`SET NX`), число попыток ограничено счётчиком `attempts:<id>` (не более 2), после чего — `internal_error` (specs/07 §3).
- Собственные таймауты этапов в оркестраторе (middleware `TimeLimit` Dramatiq не используется: он прерывает поток, но не убивает песочницу).
- Отдельная очередь `judge.rejudge` с отдельным лимитом слотов на воркер: приоритеты Dramatiq не гарантируют, что массовая перепроверка не вытеснит живых пользователей.
- Позиция в очереди — отдельный sorted set `queue:<class>`.
- Отмена — ключ `cancel:<id>` + pub/sub-канал; оркестратор убивает контейнер.
- API ставит задачи через `actor.send` в пуле потоков (`anyio.to_thread`), вызов короткий.

## Последствия
- Простая модель потоков в воркере: каждый слот — поток, блокирующий на подпроцессах.
- Позиция в очереди и отмена — свой небольшой код поверх брокера.
- Брокер привязан к Redis; при переходе на Kubernetes это не мешает.

## Альтернативы
- **Celery** — тяжелее, сложнее конфигурация ack/visibility для Redis (visibility timeout должен превышать максимальную проверку, иначе дубли), больше «магии».
- **Taskiq** — async-нативный, но воркеру async не нужен, а гарантии доставки Redis-брокеров менее зрелые.
- **arq / RQ** — нет dead-letter и heartbeats из коробки.
- **Голый Redis Streams с consumer groups** — всё перечисленное пришлось бы писать самим.
