# Как написать задачу

Руководство для авторов задач Apparatica. Задача — пакет в каталоге `problems/<id>/`: условие, стартовый шаблон, тестбенч, эталонное решение и мутанты. Пакет проверяет `judge validate` — так же, как платформа проверяет решения. Формальное описание формата — [specs/06](../specs/06-problem-package.md), схема манифеста — [judge/schemas/problem.schema.json](../judge/schemas/problem.schema.json). Готовые примеры — [problems/mux4](../problems/mux4) (комбинационная схема) и [problems/counter-mod-n](../problems/counter-mod-n) (последовательная).

Содержимое `problems/` распространяется под [CC BY-SA 4.0](../problems/LICENSE): присылая задачу, вы соглашаетесь с этой лицензией.

## Быстрый старт

Нужны окружение разработки ([development.md](development.md)), Docker и образ тулчейна (`just toolchain-build`).

```sh
poetry -C judge run judge new my-task --dir ../problems        # пакет из шаблона
poetry -C judge run judge validate ../problems/my-task         # полная проверка
poetry -C judge run judge run ../problems/my-task --solution ../problems/my-task/reference/my_task.sv
```

`judge new` создаёт рабочую задачу — регистр с синхронным сбросом, — которая сразу проходит `validate`. Замените условие, интерфейс, тестбенч, эталон и мутантов своими и проверяйте пакет после каждого шага.

## Структура пакета

```
problems/my-task/
  problem.yaml        манифест
  statement.md        условие
  template.sv         стартовый код: модуль с интерфейсом задачи и пустым телом
  tb/
    model.sv          эталонная модель — модуль <top>_model
    tb_top.sv         верхний модуль тестбенча
  reference/
    my_task.sv        эталонное решение
    my_task.md        пояснение к эталону (показывается после Accepted)
  mutants/
    m01_….sv          неверные решения, которые тестбенч обязан поймать
```

Имена файлов, кроме `problem.yaml`, произвольны — их перечисляет манифест. Все пути относительные и не выходят за каталог пакета.

## Манифест `problem.yaml`

Первая строка подключает схему — редактор подсказывает поля и подчёркивает ошибки:

```yaml
# yaml-language-server: $schema=../../judge/schemas/problem.schema.json
```

Главное:

- `id` совпадает с именем каталога и становится адресом задачи; переименовать задачу нельзя.
- `number` — номер в каталоге, уникален среди задач. `judge new` берёт следующий свободный.
- `version` — целое, растёт на 1 при любом изменении опубликованной задачи; опубликованная версия неизменяема. Что изменилось — в `changelog`. Если результаты старых версий несравнимы с новыми (поменялись тесты или метрики рейтинга), увеличьте и `leaderboard_epoch`.
- `difficulty` и `tags` — пока произвольные строки; справочники уровней (`config/difficulties.yaml`) и тегов (`problems/tags.yaml`) появятся вместе с каталогом задач.
- `resource_class` — `light` для обычных задач, `heavy` для тяжёлых (больше памяти и времени, отдельная очередь). Лимиты классов — [config/resource-classes.yaml](../config/resource-classes.yaml); `limits` в манифесте может их уточнить.
- `top` — имя модуля решения.
- `interface` — параметры и порты решения: имя, направление, ширина выражением от параметров (`"WIDTH"`, `"$clog2(DEPTH)+1"`), знаковость, роль (`clock`, `reset`). Решение обязано совпасть с интерфейсом при значениях параметров по умолчанию: это проверяется до компиляции, а пользователь видит сообщение вроде «порт q: ожидается ширина WIDTH (8), объявлено 7».
- `testbenches` — тестбенчи: `top`, исходники в порядке компиляции, число тестов в каждой группе (`groups`).
- `stages` и `pipelines` — какие этапы выполняются на Run и на Submit. Типовой набор:

```yaml
stages:
  precheck: {type: precheck}
  lint: {type: lint}
  sim_run: {type: sim, testbench: main, groups: [public], max_cycles: 10000}
  sim_full: {type: sim, testbench: main, groups: [public, hidden], max_cycles: 10000}
pipelines:
  practice:
    run: [precheck, lint, sim_run]
    submit: [precheck, lint, sim_full]
```

Run проверяет только открытые тесты, Submit — открытые и скрытые. `max_cycles` — лимит тактов на прогон: превышение даёт «Превышен лимит». Остальные настройки этапов (флаги линта, окно трассы и т. п.) — в [judge.md](judge.md).

## Условие

`statement.md` — Markdown с формулами KaTeX (`$…$`) и временными диаграммами в блоках ` ```wavedrom `. Хорошее условие отвечает на вопросы, которые иначе зададут в обсуждении: что происходит по фронту и в каком порядке приоритетов, какой сброс (синхронный или асинхронный, активный 0 или 1), когда меняются выходы — сразу или на следующем такте, что при граничных значениях. В конце — таблица портов. Проверка, что условие отображается без ошибок KaTeX и WaveDrom, появится вместе со страницей задачи (T1.10); пока `validate` проверяет только кодировку UTF-8.

## Стартовый шаблон

`template.sv` — то, что пользователь видит в редакторе: модуль `top` с интерфейсом задачи и пустым телом. `validate` прогоняет шаблон через статическую проверку: он должен разбираться и совпадать с интерфейсом.

## Тестбенч

Тестбенч сравнивает решение с моделью и сообщает результаты через библиотеку `apx_tb_pkg` из образа тулчейна ([toolchain/sv/apx_tb_pkg.sv](../toolchain/sv/apx_tb_pkg.sv)). Схема, к которой стоит стремиться, — в `tb/tb_top.sv` демо-задач.

```systemverilog
module tb_top;
  import apx_tb_pkg::*;

  logic clk = 0;
  // ... входы, выходы решения и exp_<порт> модели
  my_task dut (...);
  my_task_model model (..., .q(exp_q));

  always #5 clk = ~clk;
  always @(posedge clk) apx_tick();        // счётчик тактов, окно трассы, лимит тактов

  initial begin
    apx_suite_begin();                     // сид, группы, файл результатов
    if (apx_test_begin("t1", "сброс и хранение", "public")) begin
      // стимулы...
      `APX_CHECK(q, exp_q)
      `APX_CHECK_MSG(q, exp_q, "Подсказка для баннера результата")
      apx_test_end();
    end
    apx_suite_end();                       // итог и $finish
  end
endmodule
```

Правила:

- **Модель — модуль `<top>_model`** с тем же интерфейсом в `tb/model.sv`. Выходы модели подключаются к сигналам `exp_<порт>`: на временной диаграмме они видны рядом с выходами решения.
- **Сначала сброс.** Судья случайно инициализирует все переменные решения и модели (сид отправки), поэтому до первого сброса их выходы различаются. Не проверяйте выходы до того, как сброс подействовал. Решение, которое полагается на начальное состояние вместо сброса, должно падать — так и задумано.
- **Стимулы — между фронтами.** Меняйте входы после заднего фронта, а проверяйте выходы перед следующим задним фронтом: так нет гонок с `always_ff` решения. Комбинационной схеме тоже нужен тактовый сигнал тестбенча — он задаёт темп векторов и считает такты для `apx_tick`.
- **Случайные стимулы — через `$urandom`/`$urandom_range`.** `apx_suite_begin` засевает генератор сидом отправки, поэтому прогон с тем же сидом повторяется такт в такт. `randomize()` с ограничениями работает, но медленнее.
- **Verilator двухзначный**: X и Z в симуляции не бывает, проверки «выход не X» бессмысленны.
- **Тесты и группы.** У каждого теста уникальный `id`, имя (его видит пользователь) и группа. Группа `public` — открытые тесты: пользователь видит имя, такт расхождения, ожидаемые и полученные значения, подсказку и временную диаграмму. Любая другая группа (обычно `hidden`) скрыта: только число пройденных и номер упавшего теста, без значений и диаграммы. Число тестов в каждой группе должно совпасть с `testbenches[].groups` — иначе любой прогон завершится ошибкой задачи `TB_GROUPS_MISMATCH`.
- **Первое расхождение.** `APX_CHECK` не останавливает тест: тест доигрывает тело, но в результат попадают сигналы только первого упавшего такта. После упавшего теста следующие не запускаются и помечаются «не запускался». Чтобы не тратить такты, проверяйте `apx_test_failed()` в длинных циклах.
- **Подсказки.** `APX_CHECK_MSG` с короткой подсказкой (до 500 символов) объясняет, что пошло не так, без раскрытия решения: «wrap = 1, когда count = N − 1 и en = 1».
- Тестбенч не должен использовать `$finish`, `$fatal` и запись файлов: результаты пишет только `apx_tb_pkg`. Неправильное использование библиотеки (тест внутри теста, проверка вне теста, повторный `id`) — ошибка задачи `TB_ERROR`.

## Эталонное решение

Эталон пишется в том же подмножестве, что и решения пользователей: один синтезируемый модуль без `initial`, задержек, вложенных модулей и директив препроцессора (полный список — [specs/07 §2.1](../specs/07-judge-pipeline.md)). `validate` прогоняет каждый эталон через все этапы Submit на трёх сидах и требует `accepted` — без предупреждений линта. Пояснение (`explanation`) рассказывает, почему решение устроено именно так и какие есть альтернативы.

## Мутанты

Мутант — правдоподобно неверное решение: ошибка на единицу, перепутанные входы, забытое условие, неполный `case`. Мутанты проверяют, что тесты действительно ловят типичные ошибки.

- Нужно **не меньше трёх мутантов**, и **хотя бы один ловят только скрытые тесты** — иначе скрытая группа ничего не добавляет к открытой.
- `expect` — ожидаемый вердикт: `wrong_answer`, `compile_error` (например, не тот интерфейс), `forbidden_construct` (запрещённая конструкция), `limit_exceeded`.
- `caught_by` — этапы, которые должны поймать мутанта; поймать раньше (ранний этап Submit) тоже допустимо, позже — нет. Без `caught_by` годится любой этап.
- `note` — что сломано: видно на ревью и в выводе `validate`.

`validate` проверяет вердикт и этап каждого мутанта, но не проверяет, что мутант «только для скрытых» проходит открытые тесты. Проверьте это сами прогоном Run — он должен закончиться `accepted` (или `accepted_with_warnings`, если мутант задевает линт):

```sh
poetry -C judge run judge run ../problems/my-task --solution ../problems/my-task/mutants/m02_….sv
```

## Формальные свойства

Этап формальной проверки (SVA-свойства в `formal/props.sv`, подключаемые через `bind`) появится в Ф5. Допустимое подмножество SVA определит спайк S1 и зафиксирует ADR-0005; до тех пор задачи проверяются только симуляцией.

## Проверка и отладка

`judge validate` печатает строку на каждую проверку: `ok`, `FAIL` с причиной или `--` (пропущено). Сид каждого прогона эталона виден в строке; упавший прогон повторяется:

```sh
poetry -C judge run judge run ../problems/my-task --kind submit --seed <сид> --solution <файл>
```

`judge run` печатает консоль, как на сайте, и пишет в `./out`: `events.jsonl` (события прогона), `result.json` (сид, вердикт, этапы с тестами и расхождениями) и, если упал открытый тест, окно временной диаграммы `out/<этап>/trace.fst` — от 64 тактов до расхождения до 16 после. FST открывается в Surfer или GTKWave. `validate -v` показывает консоль всех этапов.

## Ревью

Задача приходит pull request'ом: ветка `problem/<id>`, коммит `feat: add <id> problem` (правила — [CONTRIBUTING.md](../CONTRIBUTING.md)). Перед PR:

- [ ] `judge validate` проходит;
- [ ] мутанты для скрытых тестов проходят Run;
- [ ] условие однозначно: порядок приоритетов, тип сброса, момент изменения выходов, граничные случаи;
- [ ] подсказки помогают найти ошибку, но не подсказывают решение;
- [ ] у опубликованной задачи увеличены `version` и записан `changelog`.

В PR CI запускает `judge validate --determinism` для изменённых пакетов (workflow `Problems`): кроме проверок выше, первый прогон эталона повторяется с тем же сидом и должен дать побайтно тот же результат. Недетерминированный тестбенч — например, зависящий от порядка процессов `always` без синхронизации по фронту — не пройдёт.
