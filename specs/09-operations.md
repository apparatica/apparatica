# 09. Эксплуатация, тестирование, юридический минимум

## 1. Окружения и деплой

| Окружение | Состав | Назначение |
|---|---|---|
| `dev` | `docker compose -f deploy/compose.yaml -f deploy/compose.dev.yaml up`: все сервисы, Garage, демо-задачи, `SANDBOX_RUNTIME=runc` по умолчанию | разработка, контрибьюторы (Linux, macOS, Windows + WSL2) |
| `staging` | как production, один хост приложения + один хост воркера, gVisor | проверка релиза, регрессия на реальном тулчейне |
| `production` | AEZA, Нидерланды. VPS приложения: proxy, web, api, ingest, postgres, Valkey ×2, Garage; отдельные VPS воркеров (gVisor, `apx-sandboxd`). Резервные копии — в объектное хранилище другого провайдера в ЕС | — |

- Docker compose на старте; разделение на сервисы и отсутствие локального состояния (кроме БД и S3) позволяют позже перейти в Kubernetes без изменений кода.
- Релиз: тег → CI собирает образы `web`, `api` (он же `ingest`), `worker`, `toolchain` → staging → ручное подтверждение → production.
- Миграции Alembic применяются отдельным одноразовым контейнером до переключения трафика. Миграции только совместимые вперёд (expand → migrate → contract) — откат приложения на предыдущую версию без отката схемы.
- Откат: предыдущие теги образов; процедура описана в `deploy/RUNBOOK.md`.
- Воркеры и ингестор останавливаются мягко: доделывают текущие проверки (`SIGTERM` → перестать брать задачи → дождаться ≤ 10 мин).

## 2. Обновление тулчейна

1. Новый образ `toolchain:<profile-id>` (версии в `toolchain/versions.lock`).
2. Регрессионный набор (§4.1) на новом образе в CI; выход метрик синтеза за допуск (по умолчанию ±2% площади, ±3% задержки) — сигнал на ревью, а не автоматический отказ.
3. Запись `toolchain_profiles` (не по умолчанию), пакетный rejudge принятых решений текущих эпох (низкий приоритет очереди).
4. Переключение `is_default`; рейтинги переходят на новый профиль; старые результаты остаются доступными в отправках.

## 3. Бэкапы, почта, бюджет, мониторинг

- **Postgres:** WAL-G (или pgBackRest) — ежедневный полный бэкап + непрерывный архив WAL в S3-хранилище на другой площадке; хранение 30 дней. Еженедельная автоматическая проверка: восстановление в отдельный контейнер, `SELECT count(*)` по ключевым таблицам, алерт при неуспехе.
- **S3-артефакты** допускают потерю: пакеты задач восстанавливаются импортом из git, FST и логи — повторным прогоном (сид и профиль сохранены). Код отправок хранится в Postgres.
- **Почта:** SMTP из конфига (`SMTP_URL`), SPF/DKIM/DMARC для домена отправителя; шаблоны писем — через i18n.
- **Нагрузка и бюджет** (ОВ-8): на старте ≤ 20 активных пользователей в месяц и заметно меньше одной задачи на пользователя в день — порядка сотен проверок в месяц; через год — ×10, порядка нескольких тысяч проверок в месяц и единиц проверок в минуту в пике. Этого с запасом хватает двум VPS: приложения (2 vCPU, 4 ГБ: proxy, web, api, ingest, postgres, Valkey ×2, Garage) и воркера (4 vCPU, 8 ГБ, 2 слота проверки). Масштабирование — добавление VPS воркеров; до него, по прогнозу, дело не дойдёт в первый год. Стоимость = фиксированная часть (2 VPS + хранилище бэкапов) + CPU-секунды на проверку (замер S2). Квоты задаются в `config/limits.yaml` и защищают от злоупотреблений, а не от нехватки мощности.
- **Мониторинг:** Prometheus + Grafana (дашборд в `deploy/grafana/`), GlitchTip опционально, алерты из NFR-OBS-04 через Alertmanager (email/Telegram).

## 4. Тестирование платформы

### 4.1 Регрессия судьи
Для каждой задачи: эталоны (ожидается `accepted`, метрики в допуске относительно `problems/<id>/expected-metrics.json`) и мутанты (ожидается `expect`). Детерминизм: эталон дважды с одним сидом — побайтно одинаковые результаты. Запускается в CI при изменениях `judge/`, `toolchain/`, `problems/`.

Реализация (T0.13) — workflow `problems.yml`: `judge validate --determinism` в образе тулчейна той же ревизии. Изменённый пакет проверяется сам; изменение судьи, образа или классов ресурсов проверяет все пакеты; полная регрессия — ещё и раз в неделю. Детерминизм сравнивает результаты этапов (без времени) и артефакты, кроме FST, — для SV это `tb_result.jsonl`. Допуск метрик (`expected-metrics.json`) появится вместе с метриками синтеза (Ф3): метрики `sim` и так входят в побайтное сравнение.

### 4.2 Безопасность песочницы — `tests/security/`
Каждый случай — решение + ожидаемый вердикт + проверка, что хост не пострадал:

| Случай | Ожидание |
|---|---|
| `$c("system(...)")`, `$system`, DPI-импорт, `` `systemc_header `` | `forbidden_construct`, Verilator не запускался |
| `$fopen`, `$readmemh("/etc/passwd")`, `` `include "/etc/passwd" `` | `forbidden_construct` |
| `$value$plusargs`, `$root.tb_top...`, `import apx_tb_pkg::*` | `forbidden_construct` |
| поддельные строки `@@apx:` из `$display` | не влияют на вердикт |
| бесконечный цикл в `always_comb`, симуляция без `$finish` | `limit_exceeded` (time) |
| `$display` в каждом такте | `limit_exceeded` (output) |
| огромный параметр/массив (`logic [2**30-1:0] m`) | `limit_exceeded` (memory) или `compile_error`, хост цел |
| глубокая рекурсия `generate` | `compile_error` или `limit_exceeded` (time) на `precheck` |
| fork-bomb через сгенерированный C++ невозможен из-за запретов; дополнительно — бинарь с `fork` в образе теста | `pids-limit` срабатывает |
| попытка сетевого доступа из песочницы (тестовый бинарь) | нет сети |
| запись вне `/work` | read-only ФС |
| `` `ifdef SYNTHESIS `` / `` `ifdef VERILATOR `` / `` `define `` в любом виде | `forbidden_construct` (препроцессор запрещён) |
| `// synthesis translate_off`, `// xilinx translate_off`, `/* verilator public */` вокруг кода | комментарии отброшены каноническим текстом; синтез и симуляция видят один и тот же код |
| `$fdisplay` по дескриптору, открытому тестбенчем | `forbidden_construct` (нет в белом списке) |
| `initial` вместо сброса; `#` задержки; `fork` | `forbidden_construct` |
| решение без сброса, прошедшее бы тесты при нулевой инициализации | `wrong_answer` (случайная инициализация по сиду) |
| решение, у которого нетлист ведёт себя иначе, чем RTL (тестовая подмена нетлиста) | `wrong_answer` на `netlist_sim`, в рейтинг не попадает |
| фоновый процесс, оставленный бинарником симуляции и переписывающий файлы следующих этапов | процессы уничтожены между этапами, результаты синтеза не изменены |
| гигантский или некорректный `tb_result.jsonl` / `stat.json` | этап `error` с кодом `OUTPUT_INVALID`, оркестратор не падает |
| результат в `judge:results` с чужим `submission_id` или без токена задания | отброшен ингестором |

Набор запускается в CI на GitHub-hosted раннерах с установленным gVisor. Собственные (self-hosted) раннеры для PR внешних контрибьюторов не используются: тестбенчи пакетов задач не проходят статическую проверку и исполнялись бы на нашем сервере. Прогон на staging — только по метке, которую ставит мейнтейнер.

### 4.3 Бэкенд
pytest; Postgres и Valkey через testcontainers; Garage — в контейнере. Уровни: unit (сервисы, агрегирование вердикта, нормализация), интеграционные (API + БД + Redis), контрактные (ответы валидируются по `openapi.json`, schemathesis на основных эндпоинтах). Ингестор — тесты идемпотентности и порядка доставки.

### 4.4 Фронтенд
Vitest + Testing Library: доменные компоненты во всех состояниях, машина состояний проверки (`useSubmission`) на записанных SSE-сценариях (нормальный, обрыв, отмена, лимит, внутренняя ошибка). Playwright e2e против compose-стенда с реальным воркером:
1. гость решает задачу (Run с ошибкой → волны → исправление → Submit → Accepted);
2. вход (email magic link через MailHog/Mailpit) и импорт гостевых решений;
3. Submit с попаданием в рейтинг и отображением места;
4. «Поделиться» и OG-картинка;
5. жалоба на задачу и её появление в админке.
Плюс axe-проверка доступности и визуальные снимки ключевых экранов в обеих темах для сверки с макетами.

### 4.5 Нагрузка
k6: сценарии «просмотр каталога и условий», «Run», «SSE-подписки» (сотни одновременных соединений). Перед публичным запуском (Ф6), цель — NFR-PERF-08.

## 5. Юридический минимум (до запуска аутентификации, Ф2)

- **Пользовательское соглашение:** публичность принятых решений и их лицензия — MIT-0 (ADR-0012), согласие при отправке, правила поведения, основания скрытия контента и блокировки, отсутствие гарантий, порядок жалоб.
- **Политика обработки ПДн** и согласие при регистрации (FR-AUTH-06). Состав ПДн — NFR-PRIV-01. Цели, сроки, права субъекта, контакты оператора.
- **GDPR** (хостинг AEZA, Нидерланды; аудитория международная): политика конфиденциальности по ст. 13 GDPR (оператор и контакты; цели и правовые основания — исполнение договора для аккаунта, законный интерес для rate limit и защиты от злоупотреблений; сроки хранения; права субъекта; право жалобы в надзорный орган), реестр обработки, договоры обработки данных (DPA, ст. 28) с хостингом и SMTP-провайдером — обычно это стандартный DPA провайдера, принимаемый вместе с условиями сервиса (наличие у AEZA — ОВ-20), порядок уведомления об утечке в течение 72 часов.
- **152-ФЗ** — применимость к пользователям из РФ (в том числе требование локализации) зависит от статуса оператора и ориентации сервиса на РФ: вынесено в ОВ-18, нужна консультация юриста до запуска входа (Ф2).
- **Возраст:** минимальный возраст регистрации — 16 лет (GDPR ст. 8) или по ответу юриста.
- **Удаление и экспорт** — FR-USR-05; публичные решения удалённого пользователя анонимизируются (решение ОВ-12).
- **Cookie** — только необходимые, баннер согласия не требуется; страница с перечнем cookie.
- Тексты хранятся в репозитории (`web/content/legal/*.md`), версия документа фиксируется в согласии пользователя.
