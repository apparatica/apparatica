# ADR-0008. Стриминг логов: PTY → Redis Streams → SSE

- Статус: Принято
- Дата: 2026-10-24
- Связано: бриф §5.1; FR-CON-*; 07 §4

## Контекст
Вывод инструментов должен приходить в браузер построчно и в реальном времени, переживать обрывы и перезагрузку страницы, не зависеть от того, какой процесс API обслуживает клиента, и не давать песочнице сетевого доступа.

## Решение
- Процессы в песочнице запускаются с TTY (`docker exec -t`), чтобы stdio не буферизовался блоками.
- Оркестратор (вне песочницы) склеивает вывод порциями ~75 мс / 8 КБ, считает лимиты и пишет события в Redis Stream `sub:<id>` (`XADD MAXLEN ~ 5000`). Структурные события (`stage_start`, `stage_end`, `heartbeat`, `test`, `queue`, `done`) идут в тот же стрим — у клиента один упорядоченный источник.
- API отдаёт SSE: ID записи стрима = `id` события, клиент переподключается с `Last-Event-ID`. Любой экземпляр API может обслуживать любой стрим.
- После завершения — `EXPIRE 600` на стриме и полный журнал событий в S3; SSE-эндпоинт прозрачно переключается на S3.
- Proxy без буферизации, keepalive-комментарии каждые 15 с, HTTP/2.

## Последствия
- Повторяемый просмотр завершённой проверки тем же клиентским кодом, что и живой.
- Redis-queue хранит стримы только активных проверок: объём ограничен.
- При TTY stderr сливается со stdout — канал `err` определяется разбором строк и обёрткой `apx-run` (07 §4.3).

## Альтернативы
- Redis pub/sub — теряет сообщения при обрыве, нельзя дочитать.
- WebSocket — двунаправленность не нужна, сложнее прокси и переподключение.
- `stdbuf -oL` вместо PTY — не работает со статически слинкованными бинарниками.
