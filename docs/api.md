# API

HTTP API платформы: где лежит контракт, как его менять и как его использует фронтенд. Требования к API и список эндпоинтов по фазам — [specs/05](../specs/05-api.md).

## Контракт

Источник правды — код бэкенда: Pydantic-схемы (`schemas.py` модулей) и роуты FastAPI (`api.py`). Из них FastAPI строит документ OpenAPI 3.1, а он коммитится в двух видах:

| Файл | Что это | Чем создаётся |
|---|---|---|
| `backend/openapi.json` | документ OpenAPI | `apparatica openapi` |
| `web/src/lib/api/schema.d.ts` | типы TypeScript для клиента | `openapi-typescript` из `openapi.json` |

Оба файла пересоздаёт одна команда:

```sh
just openapi
```

Вручную файлы не правятся. Устаревший файл ловят проверки:
- `backend/tests/test_openapi.py` сравнивает `openapi.json` с документом, построенным из кода (`just test`, job Python в CI);
- `just check-api` сравнивает `schema.d.ts` с `openapi.json` (job JS в CI);
- `just typecheck-js` находит код фронтенда, который не совпадает с новыми типами.

Работающий сервер отдаёт тот же документ на `/api/v1/openapi.json` и интерактивную документацию на `/api/v1/docs`.

## Как изменить API

1. Измените схемы и роуты в коде бэкенда.
2. Выполните `just openapi`.
3. Закоммитьте код вместе с `openapi.json` и `schema.d.ts`. На ревью дифф `openapi.json` показывает изменение контракта.

Фаза с новыми эндпоинтами начинается с PR контракта (`T<фаза>.0`, specs/05 §0): схемы, роуты-заглушки с ответом `501 NOT_IMPLEMENTED`, `openapi.json`, типы клиента и моки. Заглушка проверяет параметры (`422`) и уходит, когда задача реализации влита.

## Что объявляется в коде явно

FastAPI не выводит из кода всё, что нужно клиенту:

- **Ошибки.** Все ошибки — `application/problem+json`. В компонентах OpenAPI схема ошибки называется `Error`; имя `Problem` занято задачами. Любая операция может вернуть `500 INTERNAL`: этот ответ добавляется ко всем роутерам при подключении в `apparatica.main`. Остальные ошибки роут перечисляет сам: `responses=problem_responses(ErrorCode.NOT_FOUND, …)` из `apparatica.core.errors`. Роут с параметрами объявляет `VALIDATION_ERROR` (422), иначе FastAPI вставит в схему свой ответ 422 в другом формате; тест падает, если в документе есть ошибка не в формате `problem+json`.
- **Поток SSE.** `GET /submissions/{id}/events` объявлен с классом ответа `EventStreamResponse` (`apparatica.core.http`) и `responses={200: {"model": SubmissionEvent}}`. Так `text/event-stream` в документе ссылается на компонент `SubmissionEvent`, и в TS-клиенте есть типы событий. Встроенный `fastapi.sse.EventSourceResponse` не подходит: с ним обработчик обязан быть генератором и не может ответить ошибкой `problem+json` до начала потока.
- **Фаза.** Каждая операция помечается `openapi_extra={"x-phase": N}`.
- **Имена операций.** `operationId` — имя функции-обработчика (`list_problems`, `create_submission`). Переименование обработчика меняет контракт.

## Общие правила

Описаны в specs/05 §1–2 и реализованы так:

- **Префикс** `/api/v1`, JSON, `snake_case`, время — ISO 8601 с часовым поясом, идентификаторы — UUIDv7 строкой.
- **Числа больше 2⁵³** передаются строкой: так передаётся `seed` отправки (63 бита).
- **Ошибки.** `code` — стабильный машинный код. По нему фронтенд показывает текст из `messages/ru.json`, подставляя `params`. Поля `title` и `detail` — английские и предназначены для разработчиков. В теле ошибки есть все поля схемы `Error`; незаданные равны `null`, как и описывают типы клиента.
- **Кэш.** Публичные данные отдаются с `ETag` и `Cache-Control: public, max-age=60, stale-while-revalidate=300`; на `If-None-Match` сервер отвечает 304. Версия задачи неизменяема: `public, max-age=31536000, immutable`. Ответы про отправки — `private, no-store`.

## Отправки (Ф0)

`POST /api/v1/submissions` создаёт Run или Submit и отвечает `202` с отправкой и заголовком `Location`. В Ф0 воркеров нет: отправка остаётся в статусе `queued`.

1. **Размер кода** проверяется по `limits.solution` из `config/limits.yaml`, то есть по тем же значениям, что отдаёт `GET /config`. Байты считаются в UTF-8, строки — по `\n`. Превышение — `413 CODE_TOO_LARGE`, в `params` лимиты и фактические значения. Код с символом NUL или с одиночным суррогатом — `422`.
2. **Версия задачи.** Отправить можно только на текущую версию опубликованной задачи. Иначе `409 PROBLEM_VERSION_OUTDATED` с `params.current_version`; неизвестная задача — `404`.
3. **Профиль тулчейна.** Отправка проверяется профилем по умолчанию для языка задачи. Если такого профиля нет — `503 JUDGE_UNAVAILABLE`. Профили регистрирует `apparatica-admin toolchain add` ([development.md](development.md#профили-тулчейна)).
4. **Сид.** Для каждой отправки выбирается случайное 63-битное число. Версия задачи, профиль и сид вместе делают прогон воспроизводимым (specs/04 §1).
5. **Очередь.** После коммита отправка уходит в очередь `judge.<resource_class>` заданием для воркера: код, сид, пакет, образ тулчейна, токен задания ([architecture.md](architecture.md#очередь-проверок)). Пока отправка ждёт, `queue_position` — её место в очереди, начиная с 1. Оценка ожидания `eta_s` пока не считается: для неё нужна медиана длительности проверок от ингестора. Если очередь недоступна — `503 JUDGE_UNAVAILABLE`, а отправка сохраняется как `internal_error` с кодом `QUEUE_UNAVAILABLE`. Без `APX_QUEUE_URL` (разработка без воркеров) задание только пишется в лог.

**Токен задания** (specs/07 §5.3) — подписанные HMAC-SHA256 поля `{submission_id, attempt_max, exp}` в формате `v1.<payload>.<mac>` (base64url). Ключ — `APX_JOB_TOKEN_KEY`, срок жизни — `APX_JOB_TOKEN_TTL_S` ([configuration.md](configuration.md)). Ингестор (Ф1) примет результат воркера только с действительным токеном этой отправки.

`GET /api/v1/submissions/{id}` возвращает отправку с этапами (в порядке конвейера) и артефактами. В списке артефактов только виды, которые можно скачать: `log`, `events`, `fst`. Файл результатов тестбенча (`tb_result`) не показывается: в нём ожидаемые значения скрытых тестов (specs/07 §4.4). Сначала идут логи и журнал событий, затем по одному FST на этап в порядке конвейера ([артефакты](#артефакты-и-волны)). Отправку видит только её автор ([гости](#гости-и-лимиты-ф1)).

## Отправки (Ф1): контракт

PR контракта Ф1 (T1.0) объявил эндпоинты Ф1, теперь все они реализованы. Фронтенд работает с ними и через моки ([frontend.md](frontend.md#моки-для-разработки)).

| Эндпоинт | Ответ | Реализация |
|---|---|---|
| `GET /submissions?problem=&cursor=&limit=` | `SubmissionPage`: свои отправки, новые первыми, `next_cursor` и остаток квот `quota`, см. [гости](#гости-и-лимиты-ф1) | работает (T1.7a) |
| `GET /submissions/{id}/events` | поток событий проверки, см. ниже | работает (T1.5) |
| `POST /submissions/{id}/cancel` | `202` без тела; итог приходит событием `finalized` со статусом `cancelled`. Завершённая отправка — `409 SUBMISSION_FINISHED`, нет Valkey — `503 JUDGE_UNAVAILABLE`. Как работает — [architecture.md](architecture.md#отмена) | работает (T1.6) |
| `GET /submissions/{id}/artifacts/{kind}?stage=` | `302` на presigned URL файла; истёкший файл — `404`, см. [артефакты](#артефакты-и-волны) | работает (T1.17a) |
| `POST /submissions/{id}/waveform` | `202` с артефактом FST, см. [артефакты](#артефакты-и-волны) | работает (T1.17a) |
| `GET /captcha/challenge` | задача ALTCHA `CaptchaChallenge`, см. [капча](#капча) | работает (T1.7b) |

Что изменилось в эндпоинтах Ф0:

- `POST /submissions` принимает `captcha`: решённую задачу ALTCHA после ответа `428 CAPTCHA_REQUIRED`. Добавлены ошибки `429 RATE_LIMITED` и `403 HEAVY_NOT_ALLOWED` ([гости](#гости-и-лимиты-ф1)). Ответ `SubmissionCreated` — это отправка и остаток квот `quota` после неё.
- В отправке появилось поле `eta_s`: оценка ожидания в очереди в секундах.
- `verdict_detail.first_failure` (первый непройденный этап) кроме `stage`, `test` и `cycle` несёт `test_number` — номер упавшего открытого теста в порядке прогона, с 1; `hidden` — сводку скрытых тестов (`total`, `passed`, `failed_index`), если упал скрытый; `diagnostic` — первую ошибку этапа (`Diagnostic`: файл, строка, сообщение). Этого хватает для краткой причины в списке отправок без чтения этапов (FR-PRB-06). У вердиктов, записанных раньше, этих полей нет.
- В отправке появилось поле `waveview_url`: страница просмотрщика волн профиля тулчейна этой отправки, для изолированного iframe; `null`, если у профиля нет просмотрщика или не задан `APX_WAVEVIEW_URL` ([waveview.md](waveview.md)).
- У артефакта вместо `expired` теперь `state`: `ready`, `expired` (удалён по сроку хранения), `pending` (FST пересоздаётся), `failed`. Поле `size_bytes` равно `null`, пока файла нет. `waveform` у FST описывает трассу: тест, `scope` (`failure_window` — окно вокруг первого расхождения, `full_test` — весь тест), такты от и до, такт и время курсора, сигналы для просмотрщика.

**Квоты** (`QuotaStatus`): `checks` — проверки, `waveforms` — пересоздания и полные трассы волн. В каждом окне `limit` и `remaining` считаются за час. `reset_at` — когда освободится следующая попытка; пока попытки есть, оно равно `null`. Остаток квот приходит в ответах `POST /submissions` и `GET /submissions`: этого хватает и для счётчика «Проверок: 3 из 10 в час», и для панели «Лимит исчерпан» с таймером (FR-GST-04).

### Артефакты и волны

**Список.** Логи (`log`, по одному на этап) и журнал событий (`events`, без этапа) показываются как хранятся. FST — один на этап: последний файл или, если после него запрошено пересоздание, его состояние (`pending` или `failed`, `size_bytes: null`). Что покрывает FST, API берёт из метрик этапа (`sim/v1`, [judge.md](judge.md)):

| Поле `waveform` | Что это |
|---|---|
| `test`, `scope` | упавший тест; `failure_window` — окно вокруг первого расхождения |
| `from_cycle`, `to_cycle` | такты окна: от 64 до расхождения до 16 после |
| `cursor_cycle`, `cursor_time_ps` | такт первого расхождения и его время в FST, в пикосекундах. Ось Surfer — время, а не такты: курсор ставится по времени |
| `signals` | что показать и в каком порядке: такт (`clock`), входы (`input`), затем каждый выход (`output`) и ожидаемое значение модели (`expected`, сигнал `exp_<порт>`). `path` — полное имя в FST, `port` — порт интерфейса задачи. У трасс, записанных до T1.17a, список пуст |

**Скачивание** (FR-WAV-06). `GET /submissions/{id}/artifacts/{kind}?stage=<этап>` — `302` на presigned URL последнего хранимого файла этого вида и этапа (у `events` этапа нет). Файл сохраняется как `<id>-<этап>.fst`, `<id>-<этап>.log.zst`, `<id>-events.jsonl.zst`: логи и события хранятся сжатыми zstd. URL подписан для адреса хранилища, по которому его видит браузер (`APX_S3_PUBLIC_URL`, на стенде `http://s3.localhost:8080`), и живёт `APX_ARTIFACT_URL_TTL_S` секунд (5 минут). Истёкший файл, чужая отправка, этап без файла — `404`; `tb_result` не скачивается (`422`).

**Пересоздание** (FR-WAV-05). `POST /submissions/{id}/waveform` с `scope: failure_window` пересоздаёт окно трассы упавшего открытого теста:

- FST ещё хранится или уже пересоздаётся — ответ `202` с ним как есть, квота не тратится;
- иначе (файл истёк, прошлое пересоздание не удалось) тратится квота `waveforms`, в очередь задачи уходит задание `judge_waveform` ([architecture.md](architecture.md#очередь-проверок)), ответ — FST в состоянии `pending`;
- готовность клиент узнаёт, опрашивая `GET /submissions/{id}`, пока `state` не станет `ready` или `failed`: стрим событий к этому времени давно истёк, а его архив неизменяем;
- нет такой отправки, она не завершена или окна трассы в ней нет (тест прошёл, упал скрытый тест, тестбенч недетерминирован) — `404`; квота исчерпана — `429` с `params.quota: waveforms`; очередь недоступна — `503 JUDGE_UNAVAILABLE`, заявка сохраняется как `failed`.

`scope: full_test` (весь тест) — только для вошедших; до Ф2 он всегда отвечает `401 UNAUTHENTICATED`.

### События проверки

`GET /submissions/{id}/events` — поток Server-Sent Events (specs/07 §4). Каждое событие приходит в трёх полях:

```
id: 1793003352739-1
event: stage_start
data: {"type":"stage_start","stage":"lint","stage_type":"lint","ordinal":1,"attempt":1}
```

`id` — ID записи Valkey Stream (миллисекунды и номер), по нему клиент дочитывает поток после обрыва (`Last-Event-ID` или `?from=`; если есть оба, берётся заголовок). `event` — тип события, `data` — событие `SubmissionEvent`, объединение по полю `type`:

| `type` | Кто пишет | Что значит |
|---|---|---|
| `queue` | API | позиция в очереди и оценка ожидания; раз в 2 с, пока отправка ждёт; без `id:` — в стриме его нет, и при переподключении оно не дочитывается |
| `stage_start`, `stage_end` | воркер | этап начат; этап завершён с результатом `StageResult` |
| `log` | воркер | целые строки консоли, каждая с переводом строки, склеенные за ~75 мс или до 8 КБ |
| `heartbeat` | воркер | раз в секунду, пока этап молчит (сборка C++, ABC, SAT) |
| `test` | воркер | тест начат или завершён; тест заменяется по `id` целиком |
| `truncated` | воркер | вывод этапа превысил лимит, этап остановлен |
| `done` | воркер | конвейер попытки завершён |
| `finalized` | ингестор | итоговый статус и `verdict_detail` — последнее событие потока |

У событий воркера есть `attempt`. Событие с новым номером попытки значит, что проверка началась заново, и клиент сбрасывает результаты. Итоговый статус клиент берёт только из `finalized`.

Модели событий воркера — это события пайплайна `judge.core.events` с полем `attempt` (`apparatica.submissions.events`). Тест проверяет, что у каждого события пайплайна есть пара в потоке.

Как поток устроен на сервере (`apparatica.submissions.live`, `apparatica.submissions.streams`):

- **Живой поток.** Эндпоинт отдаёт записи стрима `sub:<id>` после ID клиента, затем новые — от единственного читателя стримов процесса (`StreamHub`: один `XREAD BLOCK` по всем стримам, у которых есть зрители; соединение Valkey на клиента не открывается). Поток заканчивается после `finalized`.
- **Ожидание.** Пока отправка в очереди и событий воркера ещё нет, раз в 2 с приходит `queue` с позицией.
- **Keepalive.** Комментарий `: keepalive` каждые 15 с без событий. Ответ несёт `Cache-Control: private, no-store` и `X-Accel-Buffering: no`: прокси не должен буферизовать поток.
- **Архив.** Когда проверка завершена, а стрим истёк (через 10 минут после `finalized`), события берутся из журнала `events.jsonl.zst` последней попытки в бакете `artifacts` с теми же ID, а `finalized` — из базы с ID после последнего события. Если журнала нет (проверка не запускалась, журнал удалён по сроку хранения), поток состоит из одного `finalized`.
- **Ошибки до потока.** `404 NOT_FOUND` — нет отправки; `503 JUDGE_UNAVAILABLE` — проверка не завершена, а Valkey не настроен (`APX_QUEUE_URL`).

## Гости и лимиты (Ф1)

До аккаунтов (Ф2) автор отправки — гость (FR-GST-01, ADR-0010).

**Cookie `ap_guest`.** Первая отправка без cookie создаёт гостя: случайный UUID, подписанный HMAC-SHA256 ключом `APX_GUEST_COOKIE_KEY` (`<uuid>.<mac>`, base64url). Cookie `HttpOnly`, `SameSite=Lax`, `Path=/`, срок — год; `Secure` выключается только для стенда по HTTP (`APX_COOKIE_SECURE`). Cookie с неверной подписью не принимается: запрос считается запросом без гостя, а следующая отправка создаёт нового. Код — `apparatica.auth.guests`.

**Доступ.** `GET /submissions/{id}`, его поток событий и отмену получает только автор. Чужая отправка и запрос без cookie получают `404 NOT_FOUND`, как будто отправки нет. `GET /submissions` без cookie — пустой список и полные квоты.

**Список.** `GET /submissions` — отправки гостя, новые первыми, с фильтром `problem` (slug). Страница — `limit` записей (по умолчанию 20, не больше 100) и `next_cursor`: его передают как `cursor` за следующей страницей; на последней странице он равен `null`. Курсор — непрозрачная строка; испорченный курсор — `422`.

**Квоты** (specs/07 §3, значения — `quotas.guest` в `config/limits.yaml`) проверяются при создании отправки, в таком порядке:

1. Тяжёлая задача (`resource_class: heavy`): гостю — `403 HEAVY_NOT_ALLOWED`; квота тяжёлых в сутки появится у пользователей.
2. Проверок в час — скользящее окно за последние 60 минут. Считаются отправки гостя в Postgres, кроме `internal_error`: сбой платформы попытку не тратит.
3. Одновременных проверок — отправки гостя в `queued` и `running`. Незавершённый Run той же задачи не считается, если новая отправка — Run: новый Run его вытесняет (FR-JDG-10).
4. Капча, если она нужна ([ниже](#капча)).
5. Проверок с одного адреса в час (`checks_per_ip`, ниже) — на случай гостя, который сбрасывает cookie.

Отправки одного гостя создаются по очереди: проверка квот и запись идут в одной транзакции под advisory lock гостя, поэтому два параллельных запроса не займут одну последнюю попытку. Остаток квот (`QuotaStatus`) приходит в ответах `POST` и `GET /submissions`. Квота волн (`waveforms`) — скользящее окно в `valkey-cache`; её тратит `POST /submissions/{id}/waveform`, когда ставит задание.

**Rate limit** (NFR-SEC-06, `config/rate-limits.yaml`) защищает платформу от злоупотреблений: скользящие окна библиотеки `limits` в `valkey-cache`. Изменяющие эндпоинты (`POST /submissions`, `/cancel`, `/waveform`) ограничены числом запросов с одного адреса и от одного гостя. Адрес — IPv4 или сеть IPv6 /64, после прокси (`--forwarded-allow-ips`). Хранится только HMAC-SHA256 адреса с солью `APX_IP_HASH_SALT` (NFR-PRIV-01); он же записывается в `submissions.client_ip_hash`. Счётчики могут пропасть (кэш вытесняет ключи), а при недоступном `valkey-cache` запросы проходят с предупреждением в логе: эти окна не обещают пользователю точных чисел. Без `APX_CACHE_URL` (разработка) счётчики живут в памяти процесса. Код — `apparatica.core.ratelimit`, `apparatica.auth.throttle`.

**Ответ `429 RATE_LIMITED`.** В `params.quota` — какой лимит исчерпан, в `params.limit` — его значение:

| `quota` | Что исчерпано | `window_s`, `retry_after_s` |
|---|---|---|
| `checks` | проверки гостя в час | да |
| `concurrent` | одновременные проверки | нет: попытка освободится, когда закончится проверка |
| `checks_per_ip` | проверки с одного адреса | да |
| `requests` | запросы к изменяющим эндпоинтам с адреса или от гостя | да |
| `waveforms` | пересоздания волн в час | да |

Если `retry_after_s` есть, тот же срок в секундах приходит в заголовке `Retry-After`.

**Срок хранения.** Завершённые гостевые отправки удаляются через 14 дней вместе с артефактами (ОВ-13), хэш адреса в отправке обнуляется через 30 дней (NFR-PRIV-01); сроки — в `config/retention.yaml`, удаляет ингестор ([architecture.md](architecture.md#ingest)). Черновики и история гостя остаются в браузере.

### Капча

ALTCHA (FR-GST-05, ADR-0010): задача proof-of-work без сторонних сервисов и cookie. Код — `apparatica.captcha`.

**Когда нужна.** С флагом `captcha` — перед каждой проверкой гостя. Без флага — когда гость или адрес уже отправили `captcha.per_guest` / `captcha.per_ip` проверок за окно (по умолчанию 3 и 10 за минуту, `config/rate-limits.yaml`). Окна — скользящие, в `valkey-cache`, как rate limit: при недоступном кэше капча не требуется. Пока окно заполнено, капчу просит каждая следующая проверка. Если капча не нужна, поле `captcha` не проверяется.

**Протокол.** На `POST /submissions` без нужной капчи — `428 CAPTCHA_REQUIRED` с `params.challenge_url` (`/api/v1/captcha/challenge`) и `params.reason`: `always` (флаг), `frequent` (частые проверки), `invalid` (решение неверное, истёкшее или уже использованное). Если капчу просят частые проверки, `params.retry_after_s` — через сколько секунд освободятся все заполненные окна и капча станет не нужна (и у `frequent`, и у `invalid` в этом случае); у `always` его нет. Клиент берёт задачу `GET /captcha/challenge`, виджет ALTCHA находит число и отдаёт решение — base64 JSON `{algorithm, challenge, number, salt, signature}` (виджет v3 добавляет `took`, сервер его не читает); клиент повторяет отправку с ним в поле `captcha`.

**Задача.** `challenge = sha256(salt + number)` в hex для случайного `number ≤ maxnumber` (`captcha.max_number`, 100 000 — доли секунды в браузере); соль заканчивается на `?expires=<unix time>` (`captcha.expires_s`, 10 минут); `signature` — HMAC-SHA256 задачи ключом `APX_CAPTCHA_KEY`. Сервер не хранит выданные задачи: решение проверяется по подписи, хэшу и сроку. Повтор закрыт окном `captcha:used:<signature>` в `valkey-cache` на срок задачи: решение принимается один раз.

## Клиент во фронтенде

`web/src/lib/api/client.ts` создаёт типизированный клиент `openapi-fetch` по типам из `schema.d.ts`:

```ts
import { createApiClient } from "./lib/api/client"; // путь от web/src

const api = createApiClient();
const { data, error } = await api.GET("/api/v1/problems/{slug}", {
  params: { path: { slug: "sync-fifo" } },
});
// data — ProblemDetail, error — ApiError (problem+json)
```

Пути в схеме начинаются с `/api/v1`, поэтому `baseUrl` — origin API; пустая строка означает тот же origin, что у сайта. Готовые клиенты: `browserApi` (`browser.ts`) — для браузера, на origin сайта; `serverApi` (`server.ts`) — для серверных компонентов Next.js, по переменной окружения `API_URL` (в стенде `http://api:8000`, без неё — `http://localhost:8000`): сервер ходит в API напрямую, а не через Caddy. Схемы доступны как `Schemas["ProblemDetail"]`, ошибка — `ApiError`, коды — `ErrorCode`.
