# Безопасность: песочница и права компонентов

Как платформа исполняет код пользователя и что защищает остальную систему, если код или инструменты повели себя враждебно. Требования — NFR-SEC (specs/02), решения — [ADR-0003](adr/0003-sandbox-gvisor.md) (песочница), [ADR-0009](adr/0009-results-ingestion.md) (приём результатов), [ADR-0013](adr/0013-object-storage-garage.md) (хранилище).

## Модель угроз

Verilator превращает решение в C++ и исполняет его. Yosys, SymbiYosys и slang разбирают код атакующего и тоже могут быть уязвимы. Поэтому недоверенными считаются **все этапы проверки и все их выходные файлы** (NFR-SEC-10), а не только «запуск симуляции».

Что атакующий может попытаться сделать и что этому мешает:

| Попытка | Что мешает |
|---|---|
| Выйти из контейнера на хост | gVisor (`runsc`): системные вызовы обслуживает ядро gVisor, а не ядро хоста; контейнер без привилегий и capabilities |
| Сходить в сеть, к базе, к другим сервисам | контейнер без сети (`--network=none`) |
| Исчерпать ресурсы хоста | лимиты памяти без swap, CPU, числа процессов, размера tmpfs; таймаут каждого этапа; лимит вывода |
| Оставить процесс, который испортит следующий этап | чистый каталог на этап, `kill -KILL -1` после каждого этапа, `apx-init` забирает убитые процессы |
| Подделать вердикт выводом или файлами | выходные файлы разбираются как недоверенные (сначала размер, затем схема); вердикт по авторитетному файлу результатов тестбенча с nonce прогона; статическая проверка решения (specs/07 §2.1) |
| Получив управление разбором вывода, добраться до Docker | у оркестратора нет docker socket: контейнерами управляет `apx-sandboxd` с фиксированным набором операций |
| Через скомпрометированный воркер испортить чужие результаты, данные или очереди | у воркера нет доступа к Postgres; свои ключи хранилища и пользователь Valkey с доступом только к своим ключам; результаты принимаются только с токеном задания |

## Контейнер песочницы

Один контейнер на отправку из образа тулчейна ([toolchain/README.md](../toolchain/README.md)). Флаги задаёт `judge.core.executor.sandbox_flags` — одни и те же для `judge run` и воркера:

- `--network=none`, `--read-only`; `/work` — tmpfs 512 МБ (`exec`), `/tmp` — tmpfs 64 МБ;
- пользователь `sandbox` (UID 10001), `--cap-drop=ALL`, `--security-opt=no-new-privileges`;
- `--memory` и `--memory-swap` одинаковые (без swap), `--cpus` и лимит процессов — из класса ресурсов задачи (`config/resource-classes.yaml`);
- лимит процессов под `runsc` — `--ulimit nproc`: его соблюдает ядро gVisor внутри песочницы, а `--pids-limit` хоста — втрое больше плюс 64. Хостовый лимит считает потоки Sentry, около двух на процесс песочницы, и при его исчерпании погибает вся песочница, а не один `fork` (T1.8: 254 процесса — 540 потоков хоста). Под `runc` — `--pids-limit`: `ulimit nproc` без пространства имён пользователей считал бы процессы этого UID во всех контейнерах хоста;
- без `--rm`: состояние погибшего контейнера (`OOMKilled`) читается до `destroy`;
- рантайм `runsc` (gVisor, платформа `systrap`); `runc` — только для разработки, и воркер с ним не стартует, если не настроен явно (`APX_SANDBOX_RUNTIME`);
- PID 1 — `apx-init`: ядро не доставляет ему `kill -1`, а он забирает осиротевшие процессы и не завершается (S6).

Секретов в контейнере нет: ни переменных окружения, ни ключей, ни сокетов.

## Между этапами

Этапы одной отправки идут в одном контейнере, но не доверяют друг другу (specs/07 §5.2):

- каждый этап работает в чистом каталоге `/work/<этап>`; входные файлы кладёт оркестратор tar-потоком;
- после каждого этапа — `kill -KILL -1` от пользователя песочницы: фоновый процесс этапа не доживёт до следующего (убить клиент `docker exec` недостаточно, S6);
- выходные файлы читаются с ограничением размера (`head -c`), затем разбираются по схеме; ошибка разбора — этап `error` с кодом `OUTPUT_INVALID`, а не `wrong`;
- вывод этапа ограничен; превышение останавливает этап.

## `apx-sandboxd`

Единственный процесс на хосте воркера с доступом к Docker ([architecture.md](architecture.md#песочница-apx-sandboxd)). Он слушает unix-сокет с правами `0660` и группой пользователя оркестратора. Группа `docker` оркестратору не нужна.

- **Только фиксированные операции:** `create`, `exec`, `kill`, `destroy`, `info`. Произвольных флагов Docker в протоколе нет.
- **Решения политики принимает демон, а не запрос:** рантайм, разрешённые репозитории образов, потолки ресурсов, число контейнеров. Лимиты сверх потолков отклоняются.
- **Аргументы `exec`** — список строк. Они идут после имени контейнера и не могут стать флагами Docker. `cwd` — только внутри `/work`.
- **Имена контейнеров** клиент не видит: он получает непрозрачный ID и может ссылаться только на контейнеры, созданные этим демоном.
- **Уборка.** Контейнеры старше срока жизни удаляются. Остатки прошлого запуска демона удаляются при старте. `destroy` контейнера, которого уже нет, — не ошибка: демон забывает песочницу и не держит её слот.
- **Потерянная песочница.** Если `kill` после этапа не прошёл, демон смотрит состояние контейнера. Под gVisor превышение `--memory` убивает OOM-killer'ом хоста весь Sentry, а не один процесс: `kill` отвечает `lost` с `oom`, и этап завершается `limit_exceeded` (memory), а не ошибкой платформы. Контейнер, в котором `kill` не может запуститься (например, процессы заняли весь лимит), демон останавливает целиком. Этап, остановленный по времени или выводу, сохраняет свой исход; в остальных случаях потеря песочницы — ошибка платформы. Дальше в такой песочнице ничего не запускается.

На стенде демон работает в контейнере `sandboxd` от root с docker socket хоста, то есть с правами root на хосте, но без сети; воркер — в своём контейнере без сокета Docker, а сокет демона они делят через том ([stand.md](stand.md#воркер-и-песочница)). Разрешён только репозиторий образа тулчейна стенда.

## Права компонентов

| Компонент | Postgres | Хранилище | Valkey (`valkey-queue`) | Docker |
|---|---|---|---|---|
| `api` | да | `packages` — запись; `artifacts` — presigned URL, чтение журналов событий | пользователь `api`: очереди Dramatiq, позиции в очереди, чтение (без записи) `sub:*`, запись `cancel:*` и публикация в `judge:cancel` | нет |
| `worker` | нет | `packages` — чтение; `artifacts`, `build-cache` — запись | пользователь `worker`: очереди Dramatiq, снятие позиций, `lease:*`, `attempts:*`, запись (без чтения) в `sub:*` и `judge:results`, чтение `cancel:*` и подписка на `judge:cancel` (без `PUBLISH`) | нет, только через `apx-sandboxd` |
| `ingest` | да | `artifacts` — чтение и удаление истёкших файлов (в Garage это право `write`) | пользователь `ingest`: `judge:results` (группа `ingest`), запись (без чтения) в `sub:*`, `leader:ingest`, чтение `lease:*`, подписка на `judge:cancel` (без `PUBLISH`) | нет |
| `apx-sandboxd` | нет | нет | нет | да |

**Valkey.** Пользователи и их ключи описаны в `deploy/valkey/queue-users.acl.in`. Каждый пользователь видит только свои шаблоны ключей; административные команды (`@dangerous`: `FLUSHALL`, `CONFIG`, `KEYS`, `ACL`…) закрыты всем. Пользователь по умолчанию может только `PING` — это проверка здоровья контейнера. Пароли передаются переменными окружения. Компонент, у которого появляются новые ключи (стримы событий, отмена, ингестор), добавляет их в шаблон в той же задаче. Проверка — `worker/tests/test_valkey_acl.py`: API, воркер и ингестор делают свою работу с этими правами, а чужие ключи и административные команды им недоступны.

**Хранилище.** Ключи доступа выдаются на бакет (ADR-0013): в Garage нет прав по префиксу. Права проверяет `just stand-check`.

**Токен задания.** API подписывает `{submission_id, attempt_max, exp}` своим ключом и кладёт токен в задание ([api.md](api.md#отправки-ф0)). Воркер прикладывает его к каждой записи `judge:results` ([architecture.md](architecture.md#стримы-проверки)). Ингестор принимает результат только с действительным токеном этой отправки ([architecture.md](architecture.md#ingest)); без `APX_JOB_TOKEN_KEY` он не запускается. Скомпрометированный воркер может испортить только те проверки, которые получил сам.

## Просмотрщик волн

FST пишет код пользователя, а разбирает его Surfer в браузере: файл недоверенный (ADR-0004). Поэтому Surfer живёт на отдельном origin (`waveview`) и открывается в iframe с `sandbox="allow-scripts"` без `allow-same-origin`. Origin фрейма — `null`: ошибка в разборе FST не даёт доступа к cookie, DOM, хранилищу и сети сайта. CSP origin `waveview` разрешает только свои скрипты и WASM, без сети наружу (`connect-src 'self'`), а встраивать его может только сайт (`frame-ancestors`). Страница задачи сама скачивает FST по presigned URL и передаёт байты; адаптер принимает сообщения только от родителя. Подробно — [waveview.md](waveview.md).

## Набор атак `tests/security/`

Вредоносные решения и попытки выхода из песочницы (specs/09 §4.2, NFR-SEC-04). Набор проверяет путь воркера: конвейер судьи с `SandboxExecutor` поверх настоящего `apx-sandboxd`, Docker и образа тулчейна; демон поднимается в процессе теста с политикой хоста воркера, у каждой проверки своя песочница.

- `solutions/*.sv` — решения задачи-счётчика `counter/` (не из каталога). Ожидание записано в самом файле строкой `// expect: status=<вердикт> [stage=<этап>] [limit=<лимит>] [code=<код диагностики>]`: вердикт, этап, на котором проверка падает первой (после него ничего не запускается — запрещённое решение не доходит до Verilator), и код ошибки этого этапа. Новый случай — новый файл.
- `test_outputs.py` — тестбенч, захвативший файл результатов: записи не по протоколу и файл больше лимита дают `internal_error` с `OUTPUT_INVALID`, а не вердикт.
- `test_sandbox.py` — то, что может код, захвативший инструмент: команды в песочнице, как у этапа. Нет привилегий, секретов и сокета Docker; нет сети; корневая ФС только для чтения; диск и память ограничены (под gVisor превышение памяти — `memory_exceeded`, а не ошибка); fork-бомба упирается в лимит процессов и песочница переживает её; фоновый процесс этапа не доживает до следующего и не переписывает его файлы, его сироты не занимают лимит процессов; рантайм песочницы — тот, что задан.

После каждого теста хост должен быть цел: созданные им песочницы удалены, демон создаёт новую и она работает.

Набор запускает workflow `toolchain.yml` под `runsc` на каждое изменение судьи, образа, воркера, классов ресурсов или самого набора; провал не даёт опубликовать образ. Локально `just security-test` идёт под рантаймом Docker по умолчанию (`runc`); под gVisor — с `JUDGE_SANDBOX_RUNTIME=runsc`.
