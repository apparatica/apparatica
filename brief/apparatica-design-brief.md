# Apparatica — бриф для дизайна (мокапы)

> Входные данные для создания мокапов в Claude Design. По мокапам фронтенд-агент будет реализовывать интерфейс, поэтому они должны опираться на реальный стек и покрывать не только «красивые» состояния, но и рабочие: загрузку, ошибки, очередь, пустые экраны.
>
> Продуктовый и технический контекст — в основном брифе `rtl-judge-brief.md`. Здесь только то, что нужно дизайну.

---

## 1. Продукт в двух словах

Apparatica — бесплатный open source тренажёр по RTL-разработке на SystemVerilog, «LeetCode для цифровой логики». Пользователь читает условие, пишет модуль в браузере, запускает проверку (линт → симуляция → синтез → формальные проверки), смотрит консоль инструментов, временные диаграммы и метрики синтеза. Все принятые решения публичны и ранжируются по качеству (задержка, площадь).

**Аудитория:** студенты профильных вузов и начинающие/средние RTL-инженеры. Язык интерфейса — русский.

## 2. Характер и визуальное направление

- **Инженерный инструмент, а не игра.** Точность, спокойствие, плотность информации там, где она нужна (страница задачи), и воздух там, где человек ориентируется (дашборд, каталог).
- **Дружелюбно к новичку.** Ничего не должно пугать: сложные метрики подаются с пояснениями, ошибки — с подсказкой, что делать дальше.
- **Без** геймерского неона, кислотных градиентов, «детской» геймификации и стоковых иллюстраций с роботами.
- **Ориентиры по ощущению:** LeetCode — раскладка страницы задачи; Linear, Vercel — аккуратность и типографика; VS Code — привычность редактора и панелей.
- **Айдентика:** словесный знак Apparatica плюс простой знак. Мотивы на выбор дизайнера: логический вентиль, фронт тактового сигнала, фрагмент временной диаграммы, ячейка/кристалл. Знак должен читаться в 16×16 (фавикон).

**Начать с 2–3 визуальных направлений**, показанных на одном экране — странице задачи — в светлой и тёмной темах. После выбора направления развернуть остальные экраны.

## 3. Ограничения стека (важно для реализуемости)

- React / Next.js, **Tailwind + shadcn/ui (на Radix)**, иконки **Lucide**, анимации Motion.
  → Мокапы собираются из примитивов shadcn/ui: Button, Tabs, Table, Dialog, Sheet, DropdownMenu, Tooltip, Badge, Card, Command, Resizable и т. д. Кастомный компонент рисуем, только когда стандартного нет (см. раздел 6).
- **Редактор кода — Monaco.** Дизайнится тема подсветки и рамка вокруг редактора, а не сам редактор.
- **Временные диаграммы — Surfer** (встраивается через iframe, у него свой UI и настраиваемые темы). Дизайнится контейнер, тулбар и пустые/загрузочные состояния; цвета Surfer подстраиваются под нашу палитру.
- **Светлая и тёмная темы равноправны** с первого дня. Многие будут работать в тёмной — она не должна быть автоматической инверсией светлой.
- **Шрифты обязаны полноценно поддерживать кириллицу.** Sans для интерфейса (например, Inter, IBM Plex Sans, Golos) и моноширинный для кода, логов и метрик (например, JetBrains Mono, IBM Plex Mono). Цифры в таблицах и метриках — табличные (tabular nums).
- Все значения — в виде **дизайн-токенов** (раздел 8), которые переносятся в тему Tailwind / CSS-переменные.

## 4. Семантика статусов (общая для всего продукта)

Единая палитра и иконки для статусов проверки. Статус никогда не передаётся только цветом — всегда цвет + иконка + текст (дальтонизм).

| Статус | Значение |
|---|---|
| Принято (Accepted) | все этапы пройдены |
| Неверный ответ | тесты или свойства не прошли |
| Ошибка компиляции | Verilator/slang не собрали решение |
| Предупреждения линта | решение принято, но есть замечания |
| Превышен лимит | время, память или объём вывода |
| Запрещённая конструкция | статическая проверка не пропустила код |
| В очереди | с позицией в очереди |
| Выполняется | с текущим этапом и прошедшим временем |
| Отменено | пользователем или новым запуском |
| Внутренняя ошибка | сбой платформы, не вина пользователя |

Уровни сложности: Easy / Medium / Hard — три спокойных различимых цвета, согласованных со статусами (не путать «Hard» с «ошибкой»).

## 5. Экраны (в порядке приоритета)

### 5.1 Страница задачи — главный экран
Раскладка из трёх изменяемых по размеру панелей (desktop):
- **Слева — информация о задаче.** Вкладки: «Условие», «Мои отправки», «Решения», «Рейтинг», «Эталон» (заблокирован до своего Accepted — показать замок и пояснение). Шапка: название, сложность, теги, процент принятых, кнопки «Поделиться» и «Пожаловаться».
  - Условие содержит Markdown, формулы, таблицу портов, встроенную временную диаграмму WaveDrom, блок кода.
- **Справа сверху — редактор.** Тулбар: сброс к шаблону, индикатор автосохранения, переключатель режима «Практика / Индустриальный» (только если задача его поддерживает), кнопки **Run** и **Submit** с подсказками горячих клавиш (Ctrl+Enter / Ctrl+Shift+Enter).
- **Справа снизу — панель результатов.** Вверху — **конвейер этапов** (линт → симуляция → синтез → формал) со статусом и временем каждого этапа. Вкладки: «Консоль», «Тесты», «Временные диаграммы», «Синтез», «Формал».
  - **Консоль:** потоковый вывод, разделители по этапам, цвета stdout/stderr, кликабельные ссылки «файл:строка» → переход в редактор, кнопки «копировать» и «прокрутка за выводом».
  - **Тесты:** список тест-кейсов; у упавшего — такт первого расхождения, «ожидалось / получено», кнопка «показать на диаграмме».
  - **Временные диаграммы:** контейнер Surfer с курсором на такте ошибки.
  - **Синтез:** карточки метрик (задержка критического пути и эквивалентная частота, площадь, число ячеек, триггеров), сравнение с эталоном и с лучшим решением в рейтинге, место в рейтинге после Submit.
  - **Формал:** список свойств со статусом; для нарушенного — глубина контрпримера и кнопка «открыть трассу».
- **Итоговый вердикт** после Submit — заметный, но не перекрывающий работу баннер, с действиями «Поделиться», «Смотреть рейтинг», «Сравнить с эталоном».

### 5.2 Каталог задач
Таблица/список: статус пользователя (решено / пробовал / не начато), название, сложность, теги, процент принятых. Фильтры (сложность, теги, статус), поиск, сортировка. Сверху — компактная сводка прогресса по уровням.

### 5.3 Дашборд (главная)
- **Гость:** короткий оффер продукта, «задача дня», популярные задачи, топ рейтинга, призыв войти — без давления, решать можно сразу.
- **Пользователь:** прогресс по уровням и темам, календарь активности (heatmap), место в общем рейтинге, «продолжить» незаконченную задачу, последние отправки, свежие лучшие места в рейтингах решений.

### 5.4 Публичная страница решения
Код только для чтения, автор, дата, метрики, место в рейтинге задачи, статус «совпадает с решением N» (если применимо), кнопки «Поделиться» и «Открыть задачу».

### 5.5 Рейтинг решений задачи
Таблица: место, автор, задержка, площадь, ячейки, триггеры, дата. Сортировка по колонкам; основная метрика визуально выделена. Группа совпадающих решений сворачивается в одну строку со счётчиком.

### 5.6 Общий рейтинг пользователей
Таблица с позицией, ником, очками, числом решённых задач по уровням; выделение собственной строки.

### 5.7 Профиль пользователя
Аватар, ник, статистика, heatmap активности, решённые задачи, лучшие места в рейтингах, список публичных решений.

### 5.8 Вход
Кнопки провайдеров: VK ID, Яндекс ID, Telegram, GitHub, Google и вход по email. Пояснение, что без входа решать можно, но решения не попадут в рейтинг.

### 5.9 Модальные окна и мелкие поверхности
- «Поделиться»: ссылка, кнопки VK, Telegram, X, копирование.
- **OG-карточка** 1200×630 для превью ссылок: название задачи, сложность, метрики решения, ник, логотип.
- «Пожаловаться на задачу»: категория + текст.
- «Импортировать гостевые решения» после первого входа.
- Баннер гостя и капча при превышении лимитов.

### 5.10 Индустриальный режим (концепт, низкий приоритет)
Пошаговый сценарий поверх страницы задачи: степпер шагов (микроархитектура → RTL → строгий линт → свой тестбенч → assertions → синтез с целевой частотой → итоговый отчёт), заблокированные будущие шаги, метрики покрытия и mutation score для тестбенча. Достаточно одного-двух экранов, показывающих идею.

### Не проектировать
Админку (используется готовая SQLAdmin), переключатель языка, оплату и тарифы (их нет).

## 6. Компоненты, требующие отдельного дизайна

Конвейер этапов проверки; бейдж вердикта; бейдж сложности и чипы тегов; карточка метрики (значение, единица, сравнение, пояснение по наведению); консоль; список тестов с расхождением «ожидалось / получено»; контейнер временной диаграммы; таблица рейтинга; heatmap активности; просмотрщик кода; тема подсветки SystemVerilog для Monaco (светлая и тёмная); OG-карточка.

## 7. Состояния, которые обязаны быть в мокапах

- Загрузка (скелетоны), пустые состояния (нет отправок, нет решений, ничего не найдено).
- Проверка: в очереди (с позицией), выполняется (текущий этап, прошедшее время, долгий «молчаливый» этап вроде компиляции), отменена, превышен лимит вывода, внутренняя ошибка.
- Обрыв соединения со стримом логов и переподключение.
- Гость: ограничения, капча.
- Ошибки сети и 404 для задачи/решения.

## 8. Адаптивность и доступность

- **Desktop-first:** основная ширина от 1280 px, корректно до 1024 px.
- **Мобильные (~380 px):** просмотр условия, каталога, решений, рейтингов, профиля и дашборда. Редактирование кода на телефоне — не цель: страница задачи показывает условие и предлагает открыть на компьютере, но код решений читать можно.
- Контраст не ниже WCAG AA в обеих темах, видимые состояния фокуса, всё управляемо с клавиатуры.

## 9. Что должно получиться на выходе

1. Дизайн-система: токены цветов (с семантическими ролями для статусов и сложности), типографика, отступы, радиусы, тени, иконки, тема подсветки кода — в светлом и тёмном вариантах.
2. Ключевые экраны из раздела 5 в обеих темах, страница задачи — в нескольких состояниях (пустой редактор, идёт проверка, неверный ответ с диаграммой, Accepted с метриками).
3. Отдельные мокапы компонентов из раздела 6 со всеми состояниями.
4. Мобильные варианты каталога, условия задачи и дашборда.

## 10. Реалистичный контент для мокапов

Используйте правдоподобные данные, а не lorem ipsum — так макет честнее показывает плотность информации.

**Задача:** «Синхронный FIFO», Medium, теги: FIFO, память, указатели. Принято 41%.

**Шаблон кода:**
```systemverilog
module sync_fifo #(
  parameter int WIDTH = 8,
  parameter int DEPTH = 16
) (
  input  logic             clk,
  input  logic             rst_n,
  input  logic             push,
  input  logic [WIDTH-1:0] wdata,
  input  logic             pop,
  output logic [WIDTH-1:0] rdata,
  output logic             full,
  output logic             empty
);
  // Ваше решение
endmodule
```
