# 02. Нефункциональные требования

Числа — целевые значения для типовой задачи класса `light` на эталонном железе воркера (8 vCPU, 16 ГБ). Уточняются по итогам спайка S2.

## PERF — производительность

| ID | Фаза | Требование |
|---|---|---|
| NFR-PERF-01 | Ф1 | Run на типовой задаче (от нажатия до вердикта, без очереди): p50 < 10 с, p95 < 20 с |
| NFR-PERF-02 | Ф3 | Submit с синтезом (без формала): p50 < 25 с |
| NFR-PERF-03 | Ф1 | Создание отправки `POST /submissions`: p95 < 300 мс |
| NFR-PERF-04 | Ф1 | Задержка строки лога от песочницы до браузера: p95 < 1 с |
| NFR-PERF-05 | Ф1 | Публичные страницы (каталог, условие): TTFB p95 < 400 мс из кэша, LCP < 2,5 с на десктопе |
| NFR-PERF-06 | Ф1 | Страница задачи интерактивна (редактор готов) < 3 с на десктопе при холодном кэше; Monaco и Surfer грузятся лениво |
| NFR-PERF-07 | Ф3 | Рейтинг обновлён ≤ 10 с после принятого Submit |
| NFR-PERF-08 | Ф6 | Нагрузочный тест с запасом ×10 к прогнозу на конец первого года (ОВ-8): 50 одновременных пользователей и 10 проверок в минуту на одном VPS воркера (4 vCPU) без ошибок, p95 Run < 30 с с учётом очереди |

| NFR-LIM-05 | Вывод этапа | 1 МБ | 4 МБ |
| NFR-LIM-06 | FST | 16 МБ | 64 МБ |

| NFR-LIM-08 | Квоты | гость 10/ч, пользователь 60/ч, одновременно 1/2 | 20 в сутки, гостям недоступно |

## SEC — безопасность

| ID | Требование |
|---|---|
| NFR-SEC-01 | Код пользователя исполняется только в песочнице (07 §5): gVisor, без сети, read-only rootfs, без секретов. |
| NFR-SEC-02 | Статическая проверка (`precheck`) выполняется до компиляции и отвергает конструкции из 07 §2.1. |
| NFR-SEC-03 | Воркеры не имеют доступа к Postgres, секретам API и docker socket (контейнерами управляет `apx-sandboxd`); доступ к хранилищу — отдельные ключи на бакеты (`packages` — чтение, `artifacts` и `build-cache` — запись); доступ к Valkey — по ACL. Результаты принимаются только с токеном задания, подписанным API. |
| NFR-SEC-10 | Все этапы проверки и их выходные файлы считаются недоверенными (07 §5): чистая директория на этап, уничтожение процессов между этапами, проверка размера и схемы перед разбором. |
| NFR-SEC-04 | Набор вредоносных решений (`tests/security/`) прогоняется в CI на каждое изменение судьи, образа или песочницы; каждое получает ожидаемый вердикт, хост не страдает. |
| NFR-SEC-05 | Сессии: httpOnly, Secure, SameSite=Lax; токены в БД только хэшами; CSRF — проверка `Origin` + заголовок `X-CSRF-Token` (double submit) для изменяющих запросов. |
| NFR-SEC-06 | Rate limit на все изменяющие эндпоинты и вход (по пользователю, `guest_id` и IP); капча для гостей. |
| NFR-SEC-07 | Markdown условий и пояснений санитизируется; CSP без `unsafe-eval` на всех страницах. Surfer разбирает пользовательский FST, поэтому работает на отдельном origin в iframe с `sandbox="allow-scripts"` (без `allow-same-origin`); управление и передача файла — через `postMessage`. Свой CSP с `wasm-unsafe-eval` — только у этого origin. |
| NFR-SEC-08 | Ошибки API не раскрывают трассировки и внутренние пути; у внутренних ошибок — код сбоя для поддержки. |
| NFR-SEC-09 | Зависимости проверяются в CI (Dependabot/Renovate, `pip-audit`, `pnpm audit`), образы сканируются (Trivy). |

## PRIV — приватность

| ID | Требование |
|---|---|
| NFR-PRIV-01 | Собирается минимум ПДн: ID у провайдера, ник, email (если дан), аватар. IP хранится только хэшем с солью и только для rate limit/модерации, 30 дней. |
| NFR-PRIV-02 | Cookie только необходимые (сессия, CSRF, `guest_id`, тема); без сторонних трекеров. Аналитика — опционально, самохостинг без cookie (Umami/Plausible). |
| NFR-PRIV-03 | Удаление аккаунта и экспорт данных (FR-USR-05). |
| NFR-PRIV-04 | Хостинг в ЕС (Нидерланды): обработка ПДн соответствует GDPR — правовые основания, права субъекта (доступ, исправление, удаление, переносимость — через FR-USR-05), реестр обработки, договоры с обработчиками (хостинг, SMTP), уведомление об утечке за 72 часа. Применимость 152-ФЗ к пользователям из РФ — ОВ-18. |
| NFR-PRIV-05 | ПДн и резервные копии хранятся в ЕС. OAuth-провайдеры вне ЕС получают только то, что пользователь сам передаёт им при входе. |

## A11Y — доступность

| ID | Требование |
|---|---|
| NFR-A11Y-01 | Контраст не ниже WCAG 2.2 AA в обеих темах (токены из handoff уже проверены; новые токены — только через дизайн). |
| NFR-A11Y-02 | Статус никогда не передаётся только цветом: цвет + иконка + слово. |
| NFR-A11Y-03 | Всё управляется с клавиатуры; `:focus-visible` — контур 2 px `--ac` со смещением 2 px; ловушки фокуса только в модальных окнах. |
| NFR-A11Y-04 | `prefers-reduced-motion` отключает анимации. |
| NFR-A11Y-05 | Консоль — `role="log"` с `aria-live="polite"` (с ограничением частоты объявлений); итоговый вердикт объявляется. |
| NFR-A11Y-06 | Автоматическая проверка axe в e2e-тестах ключевых страниц без нарушений уровня serious/critical. |

## REL — надёжность

| ID | Требование |
|---|---|
| NFR-REL-01 | Ни одна отправка не теряется: при падении воркера — перепостановка (до 2 раз), затем `internal_error`. |
| NFR-REL-02 | Ингестор идемпотентен: повторная доставка результата не меняет итог. |
| NFR-REL-03 | Отказ valkey-cache не ломает работу (деградация до запросов в БД); отказ valkey-queue останавливает приём проверок с понятной ошибкой `JUDGE_UNAVAILABLE`, остальной сайт работает. |
| NFR-REL-04 | RPO Postgres ≤ 5 мин (WAL-архив), RTO ≤ 2 ч; восстановление проверяется автоматически еженедельно. |
| NFR-REL-05 | Доступность сайта 99,5% в месяц (без учёта плановых работ). |

## DET — детерминизм

| ID | Требование |
|---|---|
| NFR-DET-01 | Повтор с тем же кодом, версией задачи, профилем и сидом даёт тот же вердикт, такты и метрики. |
| NFR-DET-02 | Метрики синтеза одного решения совпадают между прогонами и воркерами (проверяется регрессией). |

## MAINT — сопровождаемость

| ID | Требование |
|---|---|
| NFR-MAINT-01 | Contract-first, источник правды — код: `backend/openapi.json` генерируется FastAPI из Pydantic-схем и роутов, коммитится, CI проверяет актуальность; TS-клиент генерируется из него. Каждая фаза с новыми эндпоинтами начинается с PR контракта (specs/05 §0). |
| NFR-MAINT-02 | Типизация: mypy (strict) для Python, `strict` TypeScript; ruff, eslint, prettier в CI. |
| NFR-MAINT-03 | Покрытие тестами: судья ≥ 85% строк, бэкенд ≥ 80%, доменные компоненты фронтенда — тесты на все состояния. |
| NFR-MAINT-04 | Ядро платформы без SV-специфики: правило import-linter «`apparatica.*` и `judge.core` не импортируют `judge.languages.*`, кроме реестра». |
| NFR-MAINT-05 | Все строки UI через next-intl (локаль `ru`); даты и числа через `Intl`; ошибки API — коды. Линтер запрещает кириллицу в JSX-литералах вне `messages/`. |
| NFR-MAINT-06 | Полный стенд с демо-задачами поднимается `docker compose up` на чистой машине Linux за ≤ 15 мин (с загрузкой образов). |
| NFR-MAINT-07 | Все зависимости — с открытыми лицензиями, совместимыми с лицензией проекта; проверка лицензий в CI. **Единственное явное исключение — liberty Nangate45** (распространение разрешено с сохранением уведомления, но лицензия запрещает сравнение библиотеки с другими и помечена «not intended for commercial use»; не OSI-совместима). Её `LICENSE` лежит в образе рядом с файлами, исключение записано в конфиге проверки лицензий со ссылкой на ADR-0007. |

## OBS — наблюдаемость

| ID | Требование |
|---|---|
| NFR-OBS-01 | Структурированные логи (JSON) с `request_id` и `submission_id` во всех процессах. |
| NFR-OBS-02 | Метрики Prometheus: длина очередей, время проверки по этапам (p50/p95), загрузка слотов воркеров, доля `internal_error` по этапам, ошибки API, задержка стрима. |
| NFR-OBS-03 | Ошибки — GlitchTip (самохостинг), опционально. |
| NFR-OBS-04 | Алерты: очередь > N дольше 5 мин, доля внутренних ошибок > 2% за 15 мин, место на диске < 15%, возраст бэкапа > 26 ч. |
