# Бриф: Apparatica — онлайн-тренажёр по RTL-разработке на SystemVerilog

> Рабочее название: **Apparatica**. Документ — входные данные для ИИ-агента, который должен подготовить **спецификацию и план разработки** (Spec-Driven Development). Это не спецификация: здесь зафиксированы цели, состав фич, ключевые технические решения и ограничения. Всё, что помечено как «рекомендация», агент может пересмотреть с обоснованием (ADR). Всё, что помечено как «открытый вопрос», агент выносит на согласование, а не решает молча.

---

## 1. Продукт в одном абзаце

LeetCode для цифровой логики: пользователь открывает задачу, пишет модуль на SystemVerilog в браузере, запускает проверку и получает вердикт (линт → компиляция → симуляция на Verilator → синтез в Yosys → формальные проверки), консольный вывод инструментов и временные диаграммы (waveforms) своего решения. Каждое корректное решение публично и попадает в рейтинг решений задачи по метрикам качества (PPA). Решать можно без регистрации; регистрация даёт историю, дашборд, место в рейтингах.

**Аналоги и чем отличаемся:** HDLBits (Verilog, Icarus, без PPA-рейтинга), chipdev.io и подобные, BitForBytes (Yosys в WASM, OpenLane). Наши отличия: SystemVerilog как основной язык, Verilator, **рейтинг решений по результатам синтеза**, формальная проверка свойств, открытые решения всех участников.

**Модель проекта:** строго open source и полностью бесплатный. Оплаты, платных тарифов и закрытых функций нет и не планируется. Квоты и лимиты существуют только для защиты ресурсов, а не как монетизация.

**Аудитория:** студенты профильных вузов, джуны/мидлы RTL/верификации, готовящиеся к собеседованиям. Язык интерфейса и задач — только русский. Мультиязычность (переводы, переключатель языка, англоязычные задачи) в первые фазы не входит, но код должен быть к ней готов — см. принцип 6 в разделе 8.

## 2. Функциональные требования (верхний уровень)

Агент должен развернуть каждый пункт в требования с ID и критериями приёмки.

### 2.1 Задачи
- **Каталог задач:** список с фильтрами (уровень, теги, статус «решено/пробовал/не начато»), поиск, процент принятых решений.
- **Уровни сложности:** Easy / Medium / Hard (набор уровней — в конфиге, не захардкожен). Теги по темам: комбинационная логика, FSM, счётчики, FIFO, арифметика, конвейеры, CDC, протоколы (AXI/APB) и т. п.
- **Условие задачи:** Markdown + формулы (KaTeX) + временные диаграммы в условии (WaveDrom) + картинки/схемы. Интерфейс модуля (порты, параметры) задан в условии и в шаблоне кода.
- **Редактор SV:** подсветка синтаксиса, автосохранение черновика, сброс к шаблону, горячие клавиши Run/Submit. Позже — диагностика в реальном времени через language server.
- **Run vs Submit** (как на LeetCode):
  - *Run* — быстрый прогон на открытых тестах, сразу времянки и консоль.
  - *Submit* — полный прогон: скрытые тесты + синтез + формальные проверки → вердикт и попадание в рейтинг.
- **Консоль:** потоковый вывод Verilator и Yosys (stdout/stderr каждого этапа), с подсветкой ошибок и ссылками «ошибка → строка в редакторе».
- **Временные диаграммы решения** на основе трассировки Verilator в формате **FST** (сжатый бинарный; VCD не используется): при падении теста — окно вокруг первого расхождения, сигналы «ожидаемое vs фактическое» рядом.
- **Оценки решения (этапы проверки):**
  1. Линт (Verilator `--lint-only`, опционально Verible lint) — предупреждения не валят решение, но видны и могут влиять на «стиль».
  2. Компиляция и симуляция (Verilator) — корректность на тестах.
  3. Синтез (Yosys) — метрики: площадь/число ячеек, логическая глубина / задержка критического пути, число триггеров; признаки несинтезируемого кода, латчей.
  4. Формальные проверки (SymbiYosys) — свойства (SVA), заданные автором задачи. Формальная эквивалентность эталону **не используется**: на мелких задачах она избыточна (тесты и так почти исчерпывающие), на крупных — шумная (свобода микроархитектуры, don't-care выходы, ложные контрпримеры без ручных ограничений).
- **Референсные решения:** одно или несколько эталонных решений с пояснением; видимость — после успешного решения (политику доступа см. открытые вопросы).
- **Рейтинг решений задачи:** все принятые решения публичны (код + метрики). Сортировка по метрике, которую задаёт задача (по умолчанию: задержка критического пути → площадь → время отправки). Одна лучшая запись на пользователя в рейтинге, остальные — в списке решений. Решения с одинаковым нормализованным AST (см. 5.3) группируются: приоритет у самого раннего автора, остальные помечаются «совпадает с решением N» без штрафа.
- **Поделиться:** ссылка на задачу/решение, кнопки VK, Telegram, X, копирование ссылки; OG-превью (картинка с названием задачи и метриками решения).
- **Жалоба на задачу:** категории (ошибка в условии, неверный/слабый тест, проблема инструментов, другое) + текст; привязка к версии задачи; очередь модерации в админке.

- Очередь жалоб, скрытие решений/пользователей, перепроверка (rejudge) задачи или отдельной отправки.
- Мониторинг очереди проверок.

### 2.5 Индустриальный режим (опциональный)

Дополнительный режим прохождения задачи, приближенный к реальному флоу разработки IP-блока. Обычный режим («Практика») остаётся режимом по умолчанию и не усложняется: новичок видит только «написал модуль → получил вердикт».

- **Включение:** явный выбор пользователя на странице задачи; доступен только для задач, где автор его подготовил. Отдельный значок/достижение за прохождение и **отдельный рейтинг** — результаты режимов не смешиваются.
- **Шаги** (набор задаётся задачей, порядок фиксирован, следующий шаг открывается после предыдущего):
  1. Чтение спецификации, микроархитектурное решение (короткая форма: интерфейсы, структура, ожидания по латентности/пропускной способности);
  2. RTL;
  3. Строгий линт по стайлгайду (расширенный набор правил Verible/Verilator);
  4. **Собственный тестбенч пользователя** — оценивается по покрытию (Verilator coverage) и по **mutation score**: тестбенч прогоняется против мутантов из пакета задачи и должен их поймать;
  5. Собственные assertions — проверяются на эталоне (не должны ложно срабатывать) и на мутантах;
  6. Синтез с ограничениями: целевая частота задана, решение обязано её достичь (timing closure), отчёт по площади;
  7. Итоговый отчёт в стиле sign-off.
- **Архитектурно** режим — это альтернативный профиль пайплайна в `problem.yaml` плюс новые типы этапов. В модель данных добавляется миграцией (поле `mode` со значением по умолчанию `practice`); благодаря обобщённым `StageResult` новые этапы не меняют схему.

## 3. Ключевые сущности (эскиз доменной модели)

`User`, `Identity` (привязанные OAuth-аккаунты), `Problem`, `ProblemVersion`, `Tag`, `Difficulty`, `Submission` (код, тип run/submit, режим practice/industrial, версия задачи, профиль тулчейна), `StageResult` (этап, статус, логи, метрики, артефакты), `Artifact` (waveform, netlist, логи — в объектном хранилище), `LeaderboardEntry`, `ReferenceSolution`, `Report` (жалоба), `Draft`, `ToolchainProfile`.

Принципы:
- Результаты проверки хранятся **обобщённо**: список `StageResult` с `stage_type`, `status`, `metrics` (JSON со схемой, версионированной по типу этапа). Добавление нового этапа (например, power или STA) не должно менять схему БД.
- Каждая отправка помнит **версию задачи** и **профиль тулчейна** (версии Verilator/Yosys/PDK). Метрики сравнимы только в пределах одного профиля; при обновлении тулчейна — пакетный rejudge.

## 4. Пакет задачи (центральный контракт)

Задачи живут **как код** в отдельном git-репозитории (или каталоге монорепо), а платформа их импортирует. Это позволяет писать и ревьюить задачи с помощью ИИ-агентов и проверять их в CI.

Рекомендуемая структура (агент уточняет и описывает схему манифеста):

```
problems/fifo-sync/
  problem.yaml          # id, version, title, difficulty, tags, интерфейс, лимиты,
                        # набор этапов, метрика рейтинга, политика видимости эталона
  statement.md          # условие (Markdown + KaTeX + WaveDrom); позже допускаются statement.<lang>.md
  template.sv           # стартовый код с интерфейсом модуля
  tb/                   # тестбенч(и) на SV (Verilator --timing / --binary)
    tb_public.sv        # открытые тесты (Run)
    tb_hidden.sv        # скрытые тесты (Submit)
  formal/               # SVA-свойства (bind) и конфиг SBY
  reference/            # эталонные решения + пояснения
  mutants/              # заведомо неверные решения для проверки качества тестов
```

Обязательный инструмент: **CLI судьи** (`judge validate <problem>`), который локально и в CI прогоняет эталон (должен проходить все этапы) и мутантов (каждый должен быть пойман хотя бы одним этапом). Тот же код судьи используется воркером на сервере — одна реализация пайплайна.

Протокол результатов тестбенча: стандартизированный машиночитаемый вывод (например, JSON-файл с результатами тест-кейсов и временем первого расхождения), чтобы UI мог показать «тест N упал на такте T».

Задел на будущее (не реализовывать сразу, но не закрывать архитектурно): тестбенчи на cocotb, несколько модулей в решении, задачи «напиши тестбенч/assertion», VHDL.

## 5. Пайплайн проверки (judge)

```
отправка → очередь → воркер → [проверка интерфейса и запрещённых конструкций]
        → lint → build+sim (Verilator) → synth (Yosys) → formal (SBY)
        → агрегирование вердикта → запись результатов → обновление рейтингов
```

- Этапы — **плагины** с единым интерфейсом (вход: рабочая директория + конфиг этапа из `problem.yaml`; выход: статус, логи, метрики, артефакты). Набор и порядок этапов задаёт задача.
- Логи стримятся в UI в реальном времени: воркер пишет в Redis Stream, API отдаёт клиенту через SSE.
- Ранняя остановка: если симуляция провалена, синтез/формал для Submit не запускаются (но для Run можно показать синтез по запросу — решить в спеке).
- Синтез: SystemVerilog читать через **yosys-slang** (плагин `read_slang`, поддерживает синтезируемое подмножество SV 1800-2017/2023; родной фронтенд Yosys для SV слаб). Для ASIC-метрик — маппинг на liberty открытой PDK (sky130 / Nangate45 / ASAP7 — выбрать), `stat -liberty` для площади; задержка — ABC с liberty или OpenSTA по смапленному нетлисту; `ltp` для логической глубины как дешёвый вариант.
- Корректность в симуляции: тестбенч сравнивает выходы решения с **эталонной моделью** (scoreboard); стимулы — constrained-random с **новым сидом на каждую отправку** плюс фиксированные направленные тесты. Сид сохраняется в отправке, поэтому любой прогон воспроизводим. Так открытость тестбенчей не позволяет подогнать решение под известные стимулы.
- Формал: только свойства SVA от автора задачи (протокольные инварианты, end-to-end свойства с checker-моделью) через SBY. Эквивалентность эталону не используется. **Риск:** открытый Yosys поддерживает SVA ограниченно (полная поддержка — в коммерческом Verific). Агент должен исследовать, что реально поддерживает связка yosys-slang + SBY, и определить допустимое подмножество SVA для авторов задач.
- Детерминизм: сид каждой отправки сохраняется, версии инструментов закреплены в образе — любой прогон можно повторить бит-в-бит.
- Производительность: компиляция Verilator — узкое место (секунды на сборку). Предусмотреть ccache, пул прогретых воркеров, лимиты на размер дизайна. Ориентир: Run на типовой задаче — p50 < 10 с.

### 5.1 Логи и прогресс в реальном времени

Цепочка: **процесс в песочнице → PTY/pipe → оркестратор воркера → Redis Stream → API (SSE) → `EventSource` в браузере.**

- **Буферизация.** Инструменты и бинарник симуляции запускаются под псевдотерминалом (PTY), иначе stdio буферизует вывод блоками и `$display`/лог Yosys приходят пачкой в конце. `stdbuf -oL` — запасной вариант, но он не работает для статически слинкованных бинарников.
- **Граница песочницы.** В Redis пишет только оркестратор вне песочницы; у процесса в песочнице сети нет.
- **Формат стрима.** Один стрим на отправку (`logs:{submission_id}`). В нём два вида событий:
  - текстовые порции (этап, канал stdout/stderr, текст), склеенные с интервалом ~50–100 мс;
  - структурные события: этап начат/завершён, статус, метрики, а также heartbeat с прошедшим временем этапа для долгих «молчаливых» шагов (компиляция C++, ABC, SAT-решатель).
- **Переподключение.** ID записи в Redis Stream используется как `Last-Event-ID` в SSE. Клиент после обрыва или при повторном открытии страницы дочитывает лог с места разрыва; уход со страницы не прерывает проверку.
- **Лимиты вывода.** `MAXLEN` на стриме и лимит на суммарный объём лога этапа. При превышении — обрезка с маркером, остановка процесса, вердикт «превышен лимит вывода». Уровень подробности логов Yosys задаётся в конфиге этапа (полный лог — в артефакт, в консоль — сокращённый).
- **Жизненный цикл.** По завершении полный лог сохраняется в S3 как артефакт, стрим получает TTL (минуты). Страница отправки после этого читает лог из S3.
- **Инфраструктура.** В обратном прокси — `proxy_buffering off` / `X-Accel-Buffering: no`, heartbeat-комментарии SSE раз в ~15 с, HTTP/2 (на HTTP/1.1 лимит в 6 соединений на домен блокирует остальные запросы при нескольких вкладках).

### 5.2 Задел под тяжёлые задачи

Сейчас задачи учебные и проверяются за секунды, но архитектура должна без переделок принять задачи, где синтез или формал идут минуты (крупные конвейеры, кэши, интерконнекты, глубокий BMC).

- **Классы задач по весу.** В `problem.yaml` указывается класс ресурсов (например, `light` / `heavy`) и лимиты времени/памяти **на каждый этап**. Имя очереди выводится из класса. **На старте один пул воркеров слушает все очереди** — отдельные пулы не строятся. Когда появятся тяжёлые задачи, выделение пула для `heavy` — это изменение конфигурации деплоя, а не кода.
- **Таймауты очереди согласованы с лимитами этапов.** Visibility timeout / ack-deadline задачи больше максимальной длительности проверки; плюс heartbeat воркера, по которому watchdog отличает «долго работает» от «воркер умер» и перезапускает задачу.
- **Отмена.** Пользователь может отменить проверку; новый Run той же задачи отменяет предыдущий незавершённый Run. Отмена корректно убивает дерево процессов в песочнице.
- **Асинхронный UX.** Проверка живёт независимо от вкладки: позиция в очереди и оценка времени ожидания, статус в списке отправок, уведомление о завершении (в интерфейсе; позже — Telegram/email).
- **Частичные результаты.** Метрики и вердикты завершённых этапов сохраняются и показываются сразу, не дожидаясь конца всего пайплайна.
- **Квоты.** Ограничение числа одновременных и суточных тяжёлых проверок на пользователя; гостям тяжёлые задачи недоступны или доступны в урезанном виде (решить в спеке).
- **Кэширование результатов этапов** по ключу (хэш нормализованного AST + версия задачи + профиль тулчейна): повторная отправка эквивалентного по AST кода (отличия только в пробелах, комментариях, именах) не перезапускает синтез и формал. Симуляция со случайным сидом кэшируется только для детерминированных этапов.

### 5.3 Нормализованный AST-хэш (slang)

На этапе статической проверки решение парсится через pyslang; строится нормализованное синтаксическое дерево (без пробелов и комментариев, с каноническим переименованием локальных идентификаторов и единым форматом литералов) и от него берётся хэш.

Применения:
- ключ кэша результатов (5.2);
- группировка совпадающих решений в рейтинге с приоритетом раннего автора (2.1);
- сигнал для модерации о копировании — только как подсказка модератору, не как автоматический отказ.

Ограничения (зафиксировать в спеке):
- **Это не проверка корректности.** Совпадение AST с эталоном ничего не доказывает о неэквивалентных по тексту решениях и не заменяет тесты.
- **На мелких задачах совпадения легитимны:** независимые авторы пишут одинаковый `assign y = a & b;`. Поэтому никаких санкций по факту совпадения.
- Точный хэш обходится перестановкой независимых операторов или заменой `assign` на `always_comb`. Для детекции копирования на крупных задачах позже можно добавить нечёткое сходство (winnowing по токенам или хэши поддеревьев, как в MOSS).
- Нормализация версионируется вместе с профилем тулчейна: изменение правил нормализации меняет хэши.

## 6. Безопасность исполнения (критично)

Verilator превращает пользовательский код в C++ и исполняет его — это исполнение недоверенного кода.
- Статическая проверка до компиляции (парсинг через slang/pyslang): запрет `$c`/`$cpure` и прочих вставок C++, метакомментариев `verilator` и `` `systemc_* ``, DPI (`import "DPI-C"`), файлового ввода-вывода (`$fopen`, `$readmem*`, `$system`), `include` чужих файлов; проверка, что объявлен ровно требуемый модуль с требуемым интерфейсом.
- Изоляция: каждая проверка — в одноразовом контейнере под gVisor (или nsjail/Firecracker), без сети, read-only rootfs, tmpfs рабочая директория, лимиты CPU/RAM/времени/числа процессов/размера вывода и waveform.
- Воркеры отделены от БД и секретов; общаются только через очередь и объектное хранилище с ограниченными правами.
- Rate limiting по пользователю и IP; капча для гостей.

### 7.2 Роли Redis, кэширование, воркеры

- **Очередь и кэш — разные инстансы Redis.** У них несовместимые политики памяти: очереди нужны `noeviction` и персистентность (AOF), кэшу — `allkeys-lru` без персистентности. На одном инстансе при нехватке памяти кэш либо вытеснит задачи, либо упрётся в OOM.
- **Неизменяемое кэшируется без инвалидации.** Версия задачи после публикации не меняется, поэтому её условие, шаблон и метаданные кэшируются in-process по ключу `(problem_id, version)`.
- **Рейтинги** считаются в Redis sorted sets; источник правды — Postgres, кэш восстанавливается из БД.
- **Публичные страницы** (каталог, условия, решения) — HTTP-кэш (`Cache-Control`/`ETag`) и кэш на уровне Next.js/CDN.
- **Воркеры** — отдельный процесс/образ с тулчейном, без доступа к Postgres и секретам API. Получают из очереди код решения и ссылку на пакет задачи. Результаты возвращают через очередь или внутренний эндпоинт, артефакты (waveform, нетлист, логи) загружают в S3 по presigned URL. Воркеры масштабируются независимо от API.
- **Хранение waveforms.** Трассы пишутся только в FST и только для окна вокруг первого расхождения (для Run — по запросу целиком, с лимитом размера). Поскольку прогоны детерминированы (сохранённый сид + закреплённый тулчейн), FST хранится ограниченное время, а для старых отправок пересоздаётся по запросу повторным прогоном.

## 8. Принципы future-proof (требования к архитектуре)

1. **Contract-first:** Pydantic-схемы API — источник правды. Сгенерированный `openapi.json` коммитится в репозиторий, CI проверяет его актуальность, TS-клиент генерируется из него. Контракт эндпоинтов фазы фиксируется до начала её реализации, чтобы фронтенд шёл параллельно с бэкендом.
2. **Модель данных растёт по фазам через миграции Alembic.** Спекулятивные таблицы и поля под будущие фазы не создаются. Обязательны с Ф0 только инварианты, которые дорого менять задним числом: неизменяемые версии задач; отправка хранит версию задачи, профиль тулчейна и сид; результаты проверки — обобщённые `StageResult` с метриками в JSONB (раздел 3).
3. **Этапы проверки и метрики рейтинга — расширяемые** (плагины + конфиг задачи), без изменений схемы БД.
4. **Версионирование всего, что влияет на вердикт:** версия задачи, профиль тулчейна, формула рейтинга.
5. **Одна реализация судьи** для CLI, CI задач и серверных воркеров.
6. **Feature flags** с первого дня. **Готовность к i18n без самой i18n:** все строки UI — через i18n-библиотеку (например, next-intl) с единственной локалью `ru`; даты и числа — через `Intl`; тексты ошибок API — коды + сообщения, а не только русский текст. Переводов, переключателя языка и таблиц переводов в БД нет. Схема пакета задачи допускает позднее добавление `statement.<lang>.md` и словаря заголовков без изменения существующих пакетов.
7. **Модульный монолит** на бэкенде (явные границы модулей: problems, judge, submissions, leaderboards, users, moderation) + отдельные воркеры; без микросервисов на старте.
8. Документация для агентов в репозитории (`AGENTS.md`/`CLAUDE.md`, ADR, глоссарий).
9. **Open source и самохостинг.** Все зависимости — с открытыми лицензиями, совместимыми с лицензией проекта; никаких обязательных проприетарных SaaS (OAuth-провайдеры и капча — опциональные и отключаемые в конфиге). Полный стенд поднимается одной командой (`docker compose up`) с демо-задачами — для контрибьюторов и для желающих развернуть свой инстанс (например, вуза).
10. **Ядро платформы не зависит от языка и тулчейна.** Пользователи, задачи, отправки, очередь, песочница, стриминг логов, рейтинги и UI результатов ничего не знают о SystemVerilog. Всё специфичное для языка живёт в отдельном модуле судьи (`judge/languages/systemverilog/`): статическая проверка и проверка интерфейса (slang), нормализация AST и хэш, реализации этапов (Verilator, Yosys, SBY), язык подсветки в редакторе. В `problem.yaml` есть поля `language` и `kind` (сейчас только `systemverilog` и `design`; позже — `vhdl`, задачи на верификацию). Цель — чтобы VHDL (GHDL/NVC, ghdl-yosys-plugin), задачи «напиши тестбенч/assertions» или вообще другой язык добавлялись новым модулем и профилем тулчейна, без правок ядра.
    **Без оверинжиниринга:** реализуется только SystemVerilog. Обязательны чистые границы модулей и отсутствие SV-логики в ядре; универсальные абстракции «под все языки» заранее не проектируются — интерфейсы выделяются по потребностям SV и уточняются, когда появится вторая реализация.
11. **Документация для контрибьюторов:** `CONTRIBUTING.md`, руководство автора задач, шаблон пакета задачи, описание процесса ревью задач через PR.

## 9. Предварительная разбивка на фазы

Агент уточняет состав и критерии приёмки. Порядок выбран так, чтобы поздние фазы только добавляли функциональность.

- **Ф0. Фундамент.** Монорепо, CI, docker compose, образ тулчейна, формат пакета задачи + CLI `judge validate`, модель данных и API ядра (задачи, версии, отправки, результаты этапов), 3–5 задач-образцов.
- **Ф1. Ядро решения (без аккаунтов).** Каталог, страница задачи, редактор, Run/Submit, линт + симуляция, потоковая консоль, временные диаграммы, гостевые черновики, песочница и rate limit.
- **Ф2. Пользователи.** Аутентификация, история отправок, дашборд, профиль, импорт гостевых решений.
- **Ф3. Качество решений.** Синтез и метрики, рейтинг решений задачи, публичные решения, референсные решения, общий рейтинг пользователей, шеринг с OG-превью.
- **Ф4. Формал и модерация.** Формальные проверки, жалобы, админка модерации, rejudge.
- **Ф5. Контент и масштаб.** Наполнение задачами (цель — 50+), LSP в редакторе, схемы нетлиста, нагрузочное тестирование.
- **Ф6. Индустриальный режим.** Пошаговый флоу, пользовательские тестбенчи с покрытием и mutation score, assertions, синтез с целевой частотой, отдельный рейтинг (см. 2.5).
- **Позже (не проектировать в деталях, но не закрывать):** мультиязычность (EN), соревнования, курсы/треки, обсуждения, достижения, cocotb, выбор PDK, ИИ-подсказки.

## 10. Юридический минимум, эксплуатация, тестирование

### 10.1 Юридический минимум
- **Пользовательское соглашение:** публичность принятых решений и их лицензия (открытый вопрос 6), правила поведения, основания для скрытия контента и блокировки.
- **Политика обработки персональных данных** и согласие на обработку при регистрации. Собирается минимум: идентификатор у провайдера, ник, email, аватар.
- **При хостинге в РФ** (открытый вопрос 1): локализация ПДн и уведомление Роскомнадзора об обработке ПДн до её начала.
- **Удаление аккаунта** по запросу и экспорт своих данных. Судьба публичных решений удалённого пользователя — удаление или анонимизация — решается в спеке.
- **Cookie:** только необходимые (сессия, CSRF), без сторонних трекеров. Продуктовая аналитика, если нужна, — только самохостинг без cookie (Umami, Plausible).
- Документы публикуются до запуска аутентификации (Ф2).

### 10.2 Эксплуатация
- **Резервные копии Postgres:** ежедневные полные + архив WAL для восстановления на момент времени (pgBackRest или WAL-G), хранение вне основного сервера, **автоматическая регулярная проверка восстановления**. Артефакты в объектном хранилище допускают потерю — они пересоздаются повторным прогоном.
- **Почта:** SMTP-провайдер для magic link и уведомлений, настроенные SPF/DKIM/DMARC; провайдер задаётся в конфиге (самохостинговые инстансы подключают свой).
- **Бюджет и лимиты:** стоимость хостинга оценивается от замеренных CPU-секунд на проверку (замер — в спайке). Квоты и rate limit по умолчанию выводятся из бюджета.
- **Мониторинг и алерты:** длина очередей, время проверки p50/p95, загрузка воркеров, доля внутренних ошибок по этапам, место на дисках, возраст последнего успешного бэкапа.
- **Деплой:** staging и production; миграции применяются при деплое; процедура отката.
- **Обновление тулчейна:** новый `ToolchainProfile` → регрессионный набор (10.3) → пакетный rejudge → переключение по умолчанию.

### 10.3 Тестирование платформы
- **Регрессионный набор эталонных отправок:** для каждой задачи эталон (ожидается Accepted, метрики синтеза в допуске) и мутанты (ожидаются конкретные вердикты). Прогоняется в CI при изменениях кода судьи, пакетов задач и тулчейна. Выход метрик за допуск — сигнал на ревью.
- **Тесты безопасности песочницы:** набор вредоносных решений — `$c`, DPI, файловый ввод-вывод, бесконечная симуляция, гигантский вывод и трасса, огромные параметры, глубокая рекурсия `generate`. Каждое должно получить ожидаемый вердикт без вреда хосту.
- **Бэкенд:** unit и интеграционные тесты на pytest (Postgres и Redis через testcontainers), контрактные тесты на соответствие `openapi.json`.
- **Фронтенд:** компонентные тесты (Vitest + Testing Library) и e2e на Playwright для ключевых сценариев: гость решает задачу, вход, Submit с попаданием в рейтинг, поделиться, жалоба.
- **Нагрузочный тест** API и очереди проверок перед публичным запуском (k6 или Locust).

## 12. Открытые вопросы (вынести на согласование)

1. **Хостинг и персональные данные.** Если основная аудитория в РФ — хранение ПДн по 152-ФЗ требует размещения в РФ (Yandex Cloud / Selectel / VK Cloud). Это влияет на выбор провайдеров OAuth, почты, капчи, мониторинга.
2. **Видимость чужих решений и эталона до решения задачи** — открыто всем или только после своего Accepted (спойлеры)?
3. **Формула рейтинга решений:** только задержка/площадь или взвешенная оценка; учитываются ли предупреждения линта; какая PDK.
4. **Формула общего рейтинга пользователей:** очки за сложность, бонусы за топ-места в PPA-рейтинге.
5. **Модель авторства задач:** при открытом репозитории задач естественный путь — задачи от сообщества через PR с ревью мейнтейнеров. Нужен ли дополнительно редактор задач на сайте?
6. **Лицензии.** Код платформы: пермиссивная (MIT/Apache-2.0) или AGPL-3.0 (не даёт делать закрытые хостинговые форки). Контент задач: например, CC BY-SA 4.0. Решения пользователей: лицензия фиксируется в пользовательском соглашении при отправке. Совместимость с зависимостями (Surfer — EUPL-1.2) проверить.
7. **Скрытые тесты в открытом проекте.** Если репозиторий задач публичный, тестбенчи и эталоны тоже публичны. Рекомендация: принять это. Защита от подгонки — constrained-random стимулы с новым сидом на каждую отправку, сравнение с эталонной моделью и свойства SVA. Эталонные решения в открытом репозитории неизбежно доступны; рейтинг от копирования защищают группировка по AST-хэшу и приоритет раннего автора. Альтернатива — закрытый сабмодуль со скрытыми тестами — противоречит принципу «строго open source».
8. **Ожидаемая нагрузка** на старте и через год — для расчёта числа воркеров и бюджета на хостинг.
