# ADR-0006. Формула и хранение рейтингов

- Статус: Принято (ОВ-3а, ОВ-4 — решения заказчика, 2026-10-24)
- Дата: 2026-10-24
- Связано: бриф §2.1, §5.3, §7.2; FR-LB-*

## Контекст
Рейтинг решений задачи сортируется по метрике задачи (по умолчанию: задержка → площадь → время отправки), одна запись на пользователя, совпадающие по AST решения группируются с приоритетом раннего автора. Метрики сравнимы только в пределах профиля тулчейна. Бриф предлагает считать рейтинги в Redis sorted sets.

## Решение
**Рейтинг решений задачи**
- Ключ рейтинга: `(problem_id, leaderboard_epoch, toolchain_profile_id, formula_version)`; показывается профиль по умолчанию и текущая эпоха.
- Формула — лексикографический порядок `leaderboard.order` из `problem.yaml`. Решения с равными значениями всех метрик делят одно место (стандартное соревновательное ранжирование: 1, 2, 2, 4; решение ОВ-3а о равных метриках); внутри места строки упорядочены по времени отправки. Значения хранятся в `leaderboard_entries.sort_values numeric[]`; Postgres сравнивает массивы лексикографически, индекс покрывает сортировку.
- Метрики округляются до точности инструмента перед сравнением (задержка — 1 пс, площадь — 0,01 µm²), чтобы шум не создавал ложных различий. Округляет этап, который их отдаёт (`synth`), поэтому показанные метрики совпадают с теми, по которым считается место.
- В режиме «Практика» предупреждения линта на место **не влияют**. В индустриальном режиме (Ф7) у рейтинга своя формула: по умолчанию первый ключ — число предупреждений строгого линта (меньше — выше), затем метрики синтеза (решение ОВ-3а).
- Группировка: ведущая запись группы — самая ранняя с данным `ast_hash`; остальные получают `group_leader_entry_id` и не занимают места. Санкций нет.
- Места (`rank`, функция `RANK()`) пересчитываются ингестором одним SQL-запросом с оконной функцией при каждом принятом Submit задачи (сотни–тысячи строк — миллисекунды). Ответы API кэшируются в valkey-cache с инвалидацией по задаче.

**Общий рейтинг пользователей**
- Очки по формуле из конфига с версией (`config/rating.yaml`): Easy 1, Medium 3, Hard 6 за решённую опубликованную задачу + 3/2/1 за 1–3 место в текущем рейтинге задачи (решение ОВ-4); при общем месте бонус получают все его участники. Решение, совпадающее по AST с более ранним, места не занимает и бонуса не получает (решение заказчика при T3.9): иначе копия решения лидера приносила бы бонус.
- При равных очках выше тот, кто набрал их раньше. Момент берётся из данных — самая поздняя из отметок того, что сейчас даёт очки: `first_solved_at` засчитанных задач и время отправки решений, держащих призовые места (решение заказчика при T3.9). Пересчёт — чистая функция таблиц: повторный ничего не меняет, начальное заполнение не зависит от времени запуска. Оставшиеся равенства разбивает id пользователя: места уникальны.
- `user_ratings` в Postgres — единственное хранилище: очки, решено по уровням, момент и место (`rank`). Ингестор пересчитывает его одним запросом с `row_number()` под advisory-блокировкой транзакции — после принятого Submit (вслед за рейтингом задачи), после удаления аккаунта и периодически (новые версии, смена профиля по умолчанию или формулы); пишутся только изменившиеся строки. «Позиция N из M» и «вокруг меня» — чтение по индексу `rank`. Снимки мест на начало суток (`user_rating_snapshots`) дают колонку «за неделю».

**Отличие от брифа:** Redis sorted sets не используются ни для рейтинга задачи, ни для общего: у рейтинга задачи многоуровневый лексикографический ключ и группировка плохо ложатся на один `double`-score; общий рейтинг хранит готовые места в Postgres, а второе хранилище потребовало бы синхронизации и команды восстановления без выигрыша при наших объёмах (тысячи пользователей). Первоначальный вариант этого ADR (sorted set `rating:global:<formula>` рядом с `user_ratings`) заменён при T3.9. Решение пересматривается при нагрузочном тесте (Ф6): тогда же — пересчёт только затронутых пользователей вместо полного.

## Последствия
- Изменение формулы задачи = новый `formula_version`, рейтинг пересчитывается, старый сохраняется.
- Смена профиля тулчейна требует rejudge (09 §2) перед переключением.

## Альтернативы
- Взвешенная оценка (например, `delay × area`) — одно число, но произвольные веса и непрозрачность для новичка; можно ввести как другую формулу задачи.
- Redis sorted sets с упакованным score — быстрее на больших объёмах, но хрупко и требует ограничений на диапазоны метрик.
