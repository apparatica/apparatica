# 01. Функциональные требования

Формат: `ID` · фаза · требование, затем критерии приёмки Given/When/Then. Фаза — момент, когда требование выполняется полностью. Ссылки на экраны — имена макетов из `brief/apparatica-handoff/screens/`.

Префиксы: PKG — пакет задачи и CLI; JDG — судья; CAT — каталог; PRB — страница задачи и условие; EDT — редактор; RUN — Run/Submit; CON — консоль и стрим; TST — тесты; WAV — временные диаграммы; GST — гость; AUTH — вход; USR — пользователь, дашборд, профиль; SYN — синтез; LB — рейтинги; SOL — публичные решения; REF — эталоны; SHR — шеринг; FRM — формал; RPT — жалобы; ADM — администрирование; MOB — мобильные; IND — индустриальный режим.

## PKG — пакет задачи и CLI судьи

**FR-PKG-01** · Ф0 · Манифест `problem.yaml` валидируется Pydantic-моделью судьи (`judge.core.package`) — источником правды схемы; JSON Schema для редакторов и документации генерируется из неё (`judge/schemas/problem.schema.json`, CI проверяет актуальность).
- Given пакет с ошибкой в `problem.yaml` (неизвестное поле, неверный тип), When `judge validate`, Then команда завершается с кодом ≠ 0 и указывает путь к полю и причину.

**FR-PKG-02** · Ф0 · `judge validate` прогоняет эталоны и мутантов.
- Given корректный пакет, When `judge validate`, Then каждый эталон получает `accepted` на 3 разных сидах во всех этапах `submit`.
- Given мутант с `expect: wrong_answer`, When он не пойман ни одним этапом, Then validate падает с сообщением «мутант m01 не пойман».
- Given мутант с `caught_by: [sim_full]`, When он пойман только `sim_run`, Then validate проходит (пойман раньше — допустимо), а когда пойман только `synth` — падает.

**FR-PKG-03** · Ф0 · `judge validate` проверяет согласованность: шаблон парсится и соответствует интерфейсу; число тестов в группах равно `testbenches[].groups`; условие рендерится без ошибок KaTeX и WaveDrom.

**FR-PKG-04** · Ф0 · `judge run` локально исполняет Run или Submit для файла решения и печатает вывод в том же виде, что консоль сайта; с `--seed` воспроизводит прогон.
- Given отправка с сидом 41917 упала на такте 143, When `judge run --seed 41917` с тем же кодом, Then упал тот же тест на том же такте.

**FR-PKG-05** · Ф0 · CI репозитория прогоняет `judge validate` для каждого изменённого пакета в образе тулчейна; PR с невалидным пакетом не сливается.

**FR-PKG-06** · Ф0 · Импорт задач в платформу (`apparatica-admin problems import`) создаёт новую версию для новой `(slug, version)`, ничего не делает при совпадающем хэше и отклоняет изменённую опубликованную версию.
- Given опубликована `sync-fifo@3`, When импортируется пакет `sync-fifo@3` с изменённым `tests.sv`, Then импорт завершается ошибкой `VERSION_IMMUTABLE`, данные не меняются.

**FR-PKG-07** · Ф0 · В репозитории есть 3–5 демонстрационных задач (мультиплексор 4:1, счётчик по модулю N, сумматор с переносом, детектор последовательности, синхронный FIFO), каждая с ≥ 3 мутантами; они проходят `judge validate`.

## JDG — судья

**FR-JDG-01** · Ф0 · Этапы — плагины с единым интерфейсом; набор и порядок этапов задаёт `pipelines` задачи. Добавление этапа нового типа не требует изменений схемы БД и кода ядра.

**FR-JDG-02** · Ф0 · Статическая проверка (`precheck`) пропускает только синтезируемое подмножество по белому списку 07 §2.1, проверяет интерфейс и передаёт следующим этапам канонический текст без комментариев.
- Given решение с `` `ifdef SYNTHESIS `` или любой другой директивой препроцессора, When проверка, Then вердикт «Запрещённая конструкция» с указанием строки и подсказкой «используйте localparam».
- Given решение с комментарием `// synthesis translate_off` вокруг части кода, When проверка, Then код проходит дальше без комментария и синтез видит весь код.
- Given решение с блоком `initial` или задержкой `#5`, When проверка, Then вердикт «Запрещённая конструкция» с пояснением «не синтезируется».
- Given решение с `$system("ls")` в строке 12, When проверка, Then вердикт «Запрещённая конструкция», диагностика `$system в строке 12`, Verilator не запускался.
- Given решение с портом `rdata` шириной 4 при `WIDTH`, When проверка, Then вердикт «Ошибка компиляции» с сообщением «порт rdata: ожидается ширина WIDTH (8), объявлено 4».
- Given решение с двумя модулями, When проверка, Then «Ошибка компиляции» с сообщением «в решении должен быть ровно один модуль sync_fifo».

**FR-JDG-03** · Ф0 · Линт: ошибки Verilator → «Ошибка компиляции»; предупреждения не валят решение, видны в консоли и редакторе, этап «Предупреждение».

**FR-JDG-04** · Ф0 · Симуляция: тестбенч сравнивает выходы с эталонной моделью; сид новый на каждую отправку и сохраняется; первое расхождение останавливает прогон.

**FR-JDG-05** · Ф1 · При падении открытого теста записывается FST-трасса окна вокруг первого расхождения (повторный прогон с тем же сидом).

**FR-JDG-06** · Ф1 · Ранняя остановка: этапы после проваленного получают `skipped` с причиной.

**FR-JDG-07** · Ф1 · Вердикт агрегируется ядром по правилам `04-domain-model.md` §3.3.

**FR-JDG-08** · Ф1 · Лимиты времени, памяти, вывода и размера FST на этап; превышение → «Превышен лимит» с видом лимита.
- Given решение с `$display` в каждом такте без остановки, When вывод превысил 1 МБ, Then процесс убит, этап «лимит вывода», в консоли показаны начало и последняя строка, доступна кнопка «Скачать начало лога».

**FR-JDG-09** · Ф1 · Сбой платформы (воркер пропал, ошибка инфраструктуры) → автоматический перезапуск, всего не более 2 попыток, затем «Внутренняя ошибка» с кодом сбоя; отправка не расходует лимит. Одна и та же отправка никогда не выполняется двумя воркерами одновременно.
- Given воркер умер на этапе симуляции, When брокер перепоставил задачу, Then панель результатов показывает «попытка 2 из 2» и начинает вывод заново, без смешивания с выводом первой попытки.

**FR-JDG-10** · Ф1 · Отмена проверки пользователем и автоматическая отмена предыдущего незавершённого Run при новом Run той же задачи; дерево процессов в песочнице убивается.

**FR-JDG-11** · Ф3 · Кэш результатов детерминированных этапов (синтез, формал) по ключу `(code_hash, problem_version, toolchain_profile)`, где `code_hash` — sha256 канонического текста, переданного инструментам; кэш сборки симуляции — по тому же `code_hash`. AST-хэш ключом кэша не служит (07 §6).
- Given решение A принято, When тот же пользователь отправляет B, отличающееся только комментариями и пробелами, Then синтез не перезапускается (канонический текст совпадает), в логе этапа — «результат из кэша».
- Given решение B отличается от A именами локальных сигналов, When Submit, Then синтез выполняется заново (канонические тексты различны), а в рейтинге A и B группируются по AST-хэшу.

**FR-JDG-13** · Ф3 · Симуляция нетлиста (`netlist_sim`, 07 §2.5): синтезированная схема прогоняется тем же тестбенчем с тем же сидом; расхождение → «Неверный ответ». Решение без пройденной симуляции нетлиста не попадает в рейтинг.
- Given решение без сброса счётчика, которое прошло RTL-симуляцию благодаря удачной начальной инициализации, When Submit, Then RTL-симуляция или симуляция нетлиста падают (начальное состояние случайно и зависит от сида), вердикт «Неверный ответ» с подсказкой проверить сброс.
- Given решение, чьё поведение после синтеза отличается от RTL, When Submit, Then вердикт «Неверный ответ», ошибка у блока «Синтез»: «синтезированная схема ведёт себя иначе, чем исходный код: тест N, такт T».

**FR-JDG-12** · Ф5 · Rejudge: перепроверка отправки, задачи (эпохи) или всех принятых на новом профиле тулчейна; создаются новые отправки со ссылкой `rejudge_of`, старые сохраняются. Перепроверки идут в отдельную очередь с ограниченным числом слотов и не увеличивают ожидание живых пользователей больше чем на 10%.

## CAT — каталог задач (`Catalog`)

**FR-CAT-01** · Ф1 · Список задач: номер, статус пользователя (решено / пробовал / не начато), название, сложность, теги, процент принятых. Пагинация по 12 (настраивается).

**FR-CAT-02** · Ф1 · Фильтры: сложность (мультивыбор), теги (мультивыбор), статус; поиск по названию и тегу; сортировка по номеру, сложности, проценту принятых. Состояние фильтров — в URL.
- Given фильтр «Medium» и тег «FIFO», When обновить страницу, Then фильтры восстановлены из URL.
- Given запрос без совпадений, Then пустое состояние «Ничего не найдено» с кнопкой сброса фильтров (`PageErrors`).

**FR-CAT-03** · Ф1 · Сводка прогресса по уровням сверху («12 из 40»). Для гостя статусы берутся из локальной истории браузера; для вошедшего — с сервера (Ф2).

**FR-CAT-04** · Ф1 · Процент принятых = уникальные авторы с принятым Submit / уникальные авторы с хотя бы одним Submit (гости учитываются по `guest_id`), пересчёт не реже раза в 10 минут.

**FR-CAT-05** · Ф1 · Набор уровней сложности и их порядок — из `config/difficulties.yaml`, теги — из `problems/tags.yaml`; в коде фронтенда не захардкожены.

## PRB — страница задачи и условие (`Bench`)

**FR-PRB-01** · Ф1 · Раскладка: левая панель (вкладки «Условие», «Мои отправки», «Решения», «Рейтинг», «Эталон»), справа сверху редактор, справа снизу панель результатов. Размеры панелей изменяются и запоминаются в браузере.

**FR-PRB-02** · Ф1 · Шапка условия: название, сложность, теги, процент принятых, кнопки «Поделиться» (Ф3) и «Пожаловаться» (Ф5). Кнопки, чья фаза не наступила, скрыты feature flag.

**FR-PRB-03** · Ф1 · Условие: Markdown (GFM), формулы KaTeX, блоки ` ```wavedrom ` (рендер в SVG), картинки из `assets/`, подсветка кода SV, таблица портов из `interface` (имя, направление, ширина, описание). HTML в Markdown санитизируется.

**FR-PRB-04** · Ф1 · Страница задачи доступна по постоянному URL `/problems/<slug>`; SSR отдаёт условие и мета-теги (title, description, OG) без JS.

**FR-PRB-05** · Ф1 · Показывается текущая версия задачи. Если у пользователя открыт черновик для старой версии и шаблон изменился, показывается уведомление «Задача обновлена до версии N» со ссылкой на изменения (поле `changelog` версии).

**FR-PRB-06** · Ф1 · Вкладка «Мои отправки»: список отправок по этой задаче (новые сверху): статус, краткая причина, время; клик открывает код отправки в редакторе (с подтверждением, если черновик изменён) и её результаты. Пустое состояние — `LeftTabsB`.

**FR-PRB-07** · Ф3 · Вкладки «Решения» и «Рейтинг» (короткие версии рейтинга; ссылка на полный). «Решения» показывают код других участников только после собственного Accepted пользователя по этой задаче (решение ОВ-2); до этого — замок и пояснение (`LeftTabsB`). Рейтинг, метрики и авторы видны всегда.
- Given пользователь без Accepted по задаче, When открывает «Решения», Then видит список с метриками, но код закрыт замком; `GET /solutions/{id}` отдаёт `code: null`, `code_locked: true`.
- Given пользователь получил Accepted, When открывает «Решения», Then код всех публичных решений доступен без перезагрузки страницы.

**FR-EDT-01** · Ф1 · Monaco с языком SystemVerilog и темами `bench-light`/`bench-dark`, номер строки и столбца в строке состояния.

**FR-EDT-02** · Ф1 · Автосохранение черновика через 1 с после последнего изменения: гость — `localStorage`, вошедший — сервер (Ф2) и `localStorage` как резерв. Индикатор «Автосохранение HH:MM».
- Given пользователь написал код и закрыл вкладку, When снова открыл задачу, Then редактор содержит последний черновик.

**FR-EDT-03** · Ф1 · «Сброс к шаблону» с подтверждением; отменяется через Ctrl+Z.

**FR-EDT-04** · Ф1 · Горячие клавиши: Run — Ctrl+Enter, Submit — Ctrl+Shift+Enter (на macOS — Cmd), работают при фокусе в редакторе и вне его; подсказки на кнопках.

**FR-EDT-05** · Ф1 · Диагностики линта и `precheck` показываются маркерами Monaco (волнистое подчёркивание + иконка на полях + запись в списке диагностик).

**FR-EDT-06** · Ф6 · Диагностика в реальном времени через language server (Verible LS или slang-based) по WebSocket через `monaco-languageclient`.

## RUN — Run и Submit

**FR-RUN-01** · Ф1 · Run запускает `pipelines.practice.run` (по умолчанию precheck, lint, симуляция открытых тестов). Результат не влияет на рейтинги и статус «решено».

**FR-RUN-02** · Ф1 · Submit запускает `pipelines.practice.submit`. В Ф1 доступны этапы до симуляции включительно, синтез — с Ф3, формал — с Ф5 (по флагам); отсутствующие этапы не показываются в конвейере.

**FR-RUN-03** · Ф1 · После нажатия Run/Submit отправка создаётся сразу (ответ API ≤ 300 мс p95), кнопки показывают загрузку, панель результатов переходит в «В очереди · позиция N» (`BenchQueued`).

**FR-RUN-04** · Ф1 · Конвейер этапов показывает статус каждого этапа, время и подпись (8 состояний `PipelineStage`); ширина блоков пропорциональна времени; общее время справа.

**FR-RUN-05** · Ф1 · Итог показывается баннером под конвейером: вердикт, краткое объяснение и действия. Неверный ответ: «Тест 7 упал на такте 143: ожидалось 0x3A, получено 0x00» + «Показать на диаграмме». Accepted (Ф3): «Принято · место N из M» + «Поделиться», «Смотреть рейтинг», «Сравнить с эталоном» (`BenchAccepted`). Баннер вердикта появляется по событию `finalized` (после записи в БД и расчёта места), поэтому место в нём всегда совпадает с рейтингом. «Принято с замечаниями» показывает источник замечаний: линт или неопределённые свойства формала.

**FR-RUN-06** · Ф1 · Проверка живёт независимо от вкладки: при повторном открытии страницы панель результатов восстанавливает последнюю отправку и дочитывает стрим.

**FR-RUN-07** · Ф1 · Кнопка «Отменить» во время очереди и выполнения; состояние «Отменено» с пояснением (`ResultStates`).

**FR-RUN-08** · Ф1 · Уведомление о завершении проверки (toast), если пользователь в другой части приложения или вкладка не активна (заголовок вкладки меняется на вердикт).

## CON — консоль и стриминг

**FR-CON-01** · Ф1 · Потоковый вывод по этапам с разделителями `── lint ──`, цвета строк: информация, успех, предупреждение, ошибка; первые строки приходят в браузер не позже 1 с после их появления в песочнице (p95).

**FR-CON-02** · Ф1 · Ссылки «файл:строка[:столбец]» на файл решения кликабельны и ставят курсор в редакторе (`revealLineInCenter`). Ссылки на файлы тестбенча не кликабельны.

**FR-CON-03** · Ф1 · Управление: «Копировать», «Прокрутка за выводом» (вкл. по умолчанию, выключается ручной прокруткой вверх), «Вниз».

**FR-CON-04** · Ф1 · Для «молчаливых» шагов показывается прошедшее время («компиляция C++ · 4,2 с»), обновляемое по heartbeat.

**FR-CON-05** · Ф1 · Обрыв стрима: строка «соединение потеряно в HH:MM:SS», баннер «Связь с логом потеряна · переподключение через N с», кнопка «Подключиться сейчас»; после переподключения пропущенные строки дочитываются без дубликатов.
- Given стрим оборвался на событии 120, When клиент переподключился, Then получены события 121… и в консоли нет повторов.

**FR-CON-06** · Ф1 · После завершения проверки лог отправки читается из хранилища: открытие старой отправки показывает полный вывод.

## TST — тесты (`ResultTabs`)

**FR-TST-01** · Ф1 · Список тест-кейсов открытой группы: пройден (время), выполняется, упал (такт), не запускался; пройденные подряд сворачиваются в диапазон («Тесты 1–6»).

**FR-TST-02** · Ф1 · У упавшего теста раскрывается таблица «сигнал @такт / ожидалось / получено» и кнопка «Показать на диаграмме»; указан сид.

**FR-TST-03** · Ф1 · Скрытые тесты — одна строка с замком: на Run «запускаются только на Submit», на Submit — «пройдено N из M», для упавшего только номер, без значений.

## WAV — временные диаграммы

**FR-WAV-01** · Ф1 · Вкладка «Временные диаграммы» встраивает Surfer (iframe) с FST упавшего теста: тактовый сигнал, входы и выходы DUT, `exp_*` рядом с выходами, курсор (пунктир `er`) на такте расхождения.

**FR-WAV-02** · Ф1 · Пять состояний контейнера: норма, загрузка, «Волн пока нет», ошибка с «Повторить», «Слишком большой файл» с «Скачать FST». Шапка: «N тактов · FST X МБ».

**FR-WAV-03** · Ф1 · «Показать на диаграмме» из баннера или теста переключает вкладку и ставит курсор на такт.

**FR-WAV-04** · Ф1 · Тема Surfer соответствует палитре (фон `--ed`, такт `--ac`, шины `--in`) и переключается вместе с темой сайта.

**FR-WAV-05** · Ф1 · Если FST истёк по сроку хранения, кнопка «Пересоздать волны» запускает повторный прогон с сохранённым сидом. Он не расходует лимит проверок, но имеет отдельную квоту (07 §3); полная трасса теста — только для вошедших.

## GST — гостевой режим (`Guest`, `ModalsB`)

**FR-GST-01** · Ф1 · Гость может открыть любую задачу, сделать Run и Submit и получить вердикт. Идентификация — подписанная httpOnly-cookie `guest_id` (создаётся при первой отправке).

**FR-GST-02** · Ф1 · Баннер гостя «Вы решаете как гость. Черновики хранятся только в этом браузере, а решения не попадут в рейтинг» с «Войти» (с Ф2) и закрытием; после закрытия — чип «Гость» в шапке.

**FR-GST-04** · Ф1 · Rate limit гостя (10 проверок в час, значение в конфиге): счётчик «Проверок: 3 из 10 в час» при остатке ≤ 3, панель «Лимит проверок исчерпан» с таймером; код не теряется.

**FR-GST-05** · Ф1 · Капча (по умолчанию ALTCHA, самохостинг) при частых отправках гостя (допущение — 3 отправки за минуту) и по флагу для всех гостевых отправок; диалог `ModalsB`.

**FR-GST-06** · Ф4 · После первого входа — диалог «Перенести гостевые решения?» со списком задач из локальной истории; выбранные отправки и черновики привязываются к аккаунту, но не попадают в рейтинги.
- Given гость решил «Мультиплексор 4:1» (Accepted), When после входа перенёс решение, Then задача отмечена «решено» в каталоге и дашборде, но пользователя нет в рейтинге этой задачи.

## SYN — синтез и метрики (Ф3)

**FR-SYN-02** · Ф3 · Латчи при `forbid_latches` и несинтезируемый код → вердикт «Ошибка компиляции»; в конвейере ошибка у блока «Синтез», в баннере — объяснение и строка (решение ОВ-9).

**FR-SYN-03** · Ф3 · Вкладка «Синтез»: карточки метрик со сравнением с эталоном и лучшим решением («↓ 8% лучше эталона»), пояснение по наведению, место в рейтинге после Submit и полоса «лучше, чем у N% решений». До Submit — «сравнение появится после Submit».

**FR-SYN-04** · Ф3 · Метрики эталонов вычисляются при импорте версии задачи на профиле по умолчанию и при смене профиля.

## LB — рейтинги (Ф3)

**FR-LB-01** · Ф3 · Рейтинг решений задачи (`SolutionLB`): место, автор, задержка, площадь, ячейки, триггеры, дата. Порядок — `leaderboard.order` задачи (по умолчанию задержка → площадь). Решения с равными значениями всех метрик формулы делят одно место (1, 2, 2, 4); внутри места — по времени отправки. Основная метрика выделена. Пагинация, сортировка по колонкам (не меняет места).
- Given три решения с задержкой 0,71 нс и площадью 744 µm², When открыт рейтинг, Then все три на месте 1, следующее решение — на месте 4.

**FR-LB-02** · Ф3 · Одна лучшая запись на пользователя; остальные его принятые решения — в списке решений. Учитываются только Submit вошедших пользователей в текущей эпохе и на профиле тулчейна по умолчанию, у которых пройдена симуляция нетлиста (FR-JDG-13).

**FR-LB-03** · Ф3 · Карточки сверху: лучшее решение, эталон, ваше решение и место. Пояснение метрики. «К моей строке». Если места нет — «Вашего места пока нет».

**FR-LB-04** · Ф3 · Группировка совпадающих решений (одинаковый AST-хэш): место у самого раннего, остальные свёрнуты под ним со счётчиком «×N совпадающих» и пометкой «совпадает с решением #id», без штрафа; переключатель «Группировать совпадающие».
- Given A отправил решение 3 октября, B — то же решение с другими именами сигналов 18 октября, Then A занимает место, B показан в группе A с пометкой «совпадает с решением #A», B не получает отдельного места и не теряет «решено».

**FR-LB-05** · Ф3 · Общий рейтинг пользователей (`GlobalLB`): позиция, ник, очки, решено по уровням; своя строка выделена; разрыв «· · ·» между топом и окрестностью своей строки. Формула очков — конфиг с версией: Easy 1, Medium 3, Hard 6 за решённую задачу + бонус 3/2/1 за 1–3 место в рейтинге задачи (решение ОВ-4; при общем месте бонус получают все его участники).

**FR-LB-06** · Ф3 · Рейтинги обновляются не позже 10 с после завершения принятого Submit.
